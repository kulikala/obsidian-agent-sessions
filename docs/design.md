# Agent Sessions design

The principles behind the design, including which platform setups are supported and why, are in [`principles.md`](principles.md); how it is tested, with the smoke test and the UI checklist, is in [`testing.md`](testing.md).

## 1. Overview and components

Agent Sessions runs and manages [Claude Code](https://claude.com/claude-code), [Codex](https://github.com/openai/codex), and [OpenCode](https://opencode.ai) sessions as terminal tabs inside [Obsidian](https://obsidian.md). Four pieces make up the tool:

- **The daemon** (`agent-sessions daemon`) — a resident process that holds each session's PTY open. Only the plugin starts it.
- **The CLI / `json` output** (the `agent-sessions` binary) — all scanning and aggregation logic lives in Python; the plugin receives JSON and renders it.
- **Hooks and `statusLine`** (`agent-sessions hook` / `agent-sessions status`) — called from Claude Code's `settings.json`, they write state and token usage to files the plugin and CLI read.
- **The plugin** (Obsidian, TypeScript) — the session list, terminal rendering, tab management, restore-on-restart, notifications, and writing `sessions.json`.

Scanning, status detection, and aggregation live only in Python (`agentsessions/`). The plugin displays that JSON, writes `sessions.json`, and renders the PTY as a terminal. This split exists so the CLI, the TUI, and the plugin always see the same session list and the same numbers — there is exactly one place that decides what a session's status is or what a turn cost, and it is not TypeScript.

## 2. Processes and responsibilities

| Process | Started by | Responsibility |
|---|---|---|
| The plugin | Obsidian | Session list, terminal rendering, tab management, restore-on-restart, notifications, writing `sessions.json` |
| `agent-sessions daemon` | Only the plugin starts it (with `--detach`, when the socket doesn't respond). The CLI and TUI never start it | Holding PTYs, output buffering, attach/detach, launching and detecting the exit of `claude` |
| `agent-sessions json …` | Spawned by the plugin as needed | Scanning, last-activity, child-session detection, running sessions, recent prompt/response, token aggregation, account-wide statistics |
| `agent-sessions` (TUI) | The user | Pick a session, attach or launch it |
| `agent-sessions hook` / `status` | Claude Code (via `settings.json`) | The hook and statusLine receiving end |
| `agent-sessions setup` | `install.sh`, the plugin's install (§20.1), or run by hand | Reconciles the hooks and `statusLine` in `~/.claude/settings.json`; with `--opencode`, installs OpenCode's status plugin and status line (`--remove-opencode` removes only those two files) |

`sessions.json`:

```json
{
  "version": 1,
  "folded": ["Docs", "その他のセッション"],
  "archived": [{"id": "5778f81f-…", "name": "Release notes", "agent": "claude"}],
  "pendingRenames": {},
  "sessions": {"68d25490-…": {"agent": "claude", "cwd": "/path/to/vault"},
               "0199ccbc-…": {"agent": "codex", "daemon": "9d1f2e4a-…"}},
  "categoryColors": {"Docs": 0, "Infra": 3}
}
```

- `sessions` holds the `agent` and `cwd` of sessions the plugin itself started. A scan's own transcript-derived data takes priority once the transcript exists; this entry exists to show a brand-new session (before its transcript is written) in the list at all. For Codex and OpenCode, a session's key is its resolved *thread / session id* (its permanent identity — see §3.3), not the daemon-assigned uuid it was launched under; `agent` names the real agent, and `daemon` (instead of `cwd`) holds that launch-time uuid, so `json live`'s daemon-list merge can relabel it. Nothing is written here for such a session before it resolves (unlike Claude, which writes a `cwd`-only placeholder immediately) — there's no stable key to write it under yet. For OpenCode, which has no `/rename`, `sessions[<id>].name` also holds a name set through Rename; the session index shows it in place of OpenCode's own title. For Codex it holds the name given at creation (written when the session is linked); the session index shows it only while Codex's own title has no name (`Row.nameStored`).
- `archived`'s `name` is a cached copy for the manager's Archive section; the transcript remains the source of truth.
- `categoryColors` maps a category name (the part of `splitName`'s `Category: Name` split before the colon) to a palette index (0–11). Once assigned, an index never changes (§11).
- `pendingRenames` maps a daemon id to the name a not yet resolved Codex/OpenCode session waits for: `agent-sessions new --name` writes it for an OpenCode session (§5.1) and `linkAgentSession` (§7.7) moves it into `sessions[<real id>].name` and deletes it when the real id is known. Renames of running sessions go through `sendCommand` (§6) directly.

### 3.1 Locking `sessions.json`

The plugin (rename, archive, fold, new session, confirming a category color) and the `agent-sessions` TUI (folding) can write concurrently. A writer takes the lock by `mkdir`-ing `sessions.json.lock/` (Python `os.mkdir`, Node `fs.mkdirSync` — whoever succeeds holds the lock). On `EEXIST` it waits 50ms and retries, giving up with an error after 2 seconds (the plugin shows a `Notice`). A lock whose directory mtime is older than 10 seconds is treated as abandoned and removed with `rmdir` before retrying. Inside the lock: read → update → write to a temp file → rename → `rmdir`. Readers don't take the lock.

### 3.2 Vault resolution

Agent Sessions has no default vault. `agentsessions/config.py`'s `VAULT` (via `_resolve_vault()`, resolved once at import time) is decided in this order: the `AGENT_SESSIONS_VAULT` environment variable → the `vault` field in `~/.agents/sessions/vault.json` → `None` if neither is set. `STORE_DIR`, `STORE_PATH`, and `LOCK_DIR` are `None` too when `VAULT` is `None`, so importing the module never fails just because the vault isn't known yet.

- **The plugin** always sets `AGENT_SESSIONS_VAULT=<this.vaultPath()>` in the `env` it passes both to `agent-sessions json …` (`backend.ts`'s `runJson`, via `envWithVault`) and to the daemon's `start` (`main.ts`, `views/terminal.ts`). The daemon passes `env` straight through to `execvpe` (`daemon/server.py`'s `_op_start`), so `claude` itself and everything it spawns (hooks, statusLine) inherit it too. `vault.json` is written once, in `onload` (the vault doesn't change while Obsidian is running).
- **Python**: `config.require_vault()` returns `VAULT` or raises `VaultNotConfigured` with the message `"Agent Sessions could not find your vault. Enable the Agent Sessions plugin once in Obsidian, or set the AGENT_SESSIONS_VAULT environment variable."` The TUI's entry point (`tui.main()`) calls this before starting `curses`, so a missing vault fails cleanly (exit code 1, a message on stderr) rather than opening a blank screen. `store.load()` returns an empty `Store` when `path` is `None` rather than raising — `json scan` always expects the plugin to supply the env var, but staying alive without it is safer than crashing. `store.save()`/`store.update()` raise `VaultNotConfigured` when `path` is `None`, since silently discarding a write nobody asked for is worse than failing loudly.
- **`install.sh`**: the vault is optional — the first argument or `$AGENT_SESSIONS_VAULT`. Only with one does it also link the plugin into that vault (§20).

### 3.3 Multi-agent scanning (`agentsessions/agents/`)

`agentsessions/agents/<name>/` is an adapter per supported agent (`claude`, `codex`, `opencode`), each exposing the same small surface: `list_transcripts()`, `scan(paths, cache)`, `find_transcript(session_id)`, `read_detail_for(path)`, `live_sessions(sessions)`, `collect_usage(path)`, `summarize_usage(turns, from_ts, to_ts)`. `agentsessions/cli/json_output.py` loops over `agentsessions.agents.enabled_agents()` and merges each adapter's output; every session row carries `agent: "claude" | "codex" | "opencode"`, and a session id is the id each agent already assigns it (a Claude Code transcript's uuid, a Codex thread's id, an OpenCode `ses_…` id) — collision across agents isn't realistically possible, so `json detail`/`json usage` resolve a bare id by trying each enabled agent's `find_transcript` in turn.

`enabled_agents()` resolution order: env `AGENT_SESSIONS_AGENTS` (comma-separated, set by the plugin to match its Settings toggles) → `agents` array in `~/.agents/sessions/ui.json` (fallback for callers outside Obsidian) → `["claude"]` (the pre-multi-agent default). `agents.claude` wraps the pre-existing `sessions.scan`/`sessions.detail`/`sessions.live`/`usage.turns` (unchanged, and still used directly by code that predates the adapter layer — the TUI, `agentsessions.claude`'s hooks/setup/keybindings, statusLine). `agents.codex` reads Codex's own files:

- **Scan**: enumerates `$CODEX_HOME/sessions/**/rollout-*.jsonl` (`CODEX_HOME` from the environment, else from Codex's "environment variables" setting as `ui.json`'s `agentLaunch` mirrors it — so a command run outside a Codex session reads the same profile as the plugin's Codex tabs — else `~/.codex`; `rollout.codex_variable`); reuses `sessions.scan`'s `RACY_WINDOW`/cache-entry shape (both agents share one `scan-cache.json`, keyed by path, so no collision). `child` is `session_meta.payload.source != 'cli'` (a launch from vscode/exec/another tool, mirroring Claude's own child-session rule).

  Name resolution, highest priority first (`agents/codex/scan.py`/`rollout.py`): (1) `state_5.sqlite`'s `threads.name` — an explicit `/rename`, becomes `Session.name` (a "real" name, its own group, same as a Claude Code custom-title); (2) `threads.title` if non-empty — Codex's own auto-generated summary, becomes `Session.first_prompt` (an "Other"-section label, same as an untitled Claude Code session's first message — never `Session.name`, since it wasn't a deliberate rename); (3) the rollout's own extraction, itself tiered: `event_msg.item_completed` with `item.type == 'UserMessage'` (newer Codex CLI versions, e.g. 0.156.1), then `event_msg.user_message` (older versions — the two are mutually exclusive in every rollout checked so far), then `response_item`'s role=user as a last resort. Every rollout-derived candidate is filtered by `is_real_user_text` (skips an injection marker — `INJECTED_PREFIXES`: `# AGENTS.md instructions`, `<environment_context>`, `<user_instructions>`, `<permissions` — or a bare slash command like `/exit`), and a filtered-out candidate is skipped in favor of the next one found, never settled for. `state_5.sqlite` lives where Codex puts it (`names.sqlite_home`, Codex's own order): `sqlite_home` at the top level of `config.toml`, else `CODEX_SQLITE_HOME` (looked up like `CODEX_HOME`), else `CODEX_HOME`. sqlite is read via a `mode=ro` URI (never a write, never a lock) and re-queried fresh on every scan (not cached — unlike the rollout's own head, sqlite's state can change independent of the rollout file's mtime, e.g. a `/rename` doesn't touch it). A session where nothing survives this whole chain is still shown (unlike Claude), just nameless (in "Other") — the naive first line being unusable doesn't mean the session itself is empty.

  **Opening `state_5.sqlite` itself**: with no `codex` process running, `-wal`/`-shm` can be entirely absent, and a WAL-mode database opened `mode=ro` in that state fails outright ("unable to open database file") — sqlite normally needs to create `-shm` even just to read, and `mode=ro` forbids creating anything, so a lookup that just failed silently (`{}`) would make every Codex session's name disappear at once. `agents/codex/names.py`'s `_connect` tries, in order: plain `mode=ro` (works when `-wal`/`-shm` already exist); if that fails and there's no `-wal` file, `mode=ro&immutable=1` (telling sqlite the file won't change skips WAL/shared-memory setup entirely — safe, since there's nothing in a WAL to miss); if that still fails too (including a `-wal` that exists but couldn't be opened read-only for some other reason), copy `state_5.sqlite`/`-wal`/`-shm` to a private temp directory and open the copy without any read-only restriction (safe and always works, since nothing but this process ever sees that copy, deleted right after). If every strategy fails, `~/.agents/sessions/codex-names-cache.json` (a `{thread_id: {name, title}}` map, updated on every successful read, merged rather than overwritten so a lookup for a subset of ids never drops another id's cached entry) supplies the last known value instead of `{}` — a session's name disappearing is worse than it going briefly stale.
- **Live**: Codex has no status ledger file, so `agents/codex/live.py` reads the tail of the rollout itself. The most recent of `task_started`/`task_complete`/`turn_aborted`/an approval-request event decides `busy`/`idle`/`waiting`; a `task_complete`/`turn_aborted` tail is left out of `json live` entirely, matching Claude's "only list what's running" convention. The approval-request event names are from `codex-rs`'s source, not confirmed against real local data (no approval-gated session was available to check against) — worth revisiting. Process liveness (`pid`) is best-effort: a `codex` process from the process table (`procs.process_table`) is matched to a session by checking whether its args contain that session's `cwd` (on Windows the table holds executable names only, so `pid` stays `0` there).
- **Usage**: `agents/codex/usage.py` diffs successive `token_count` events' running totals (`info.total_token_usage`) into per-call deltas, bucketed into turns the same way `usage.turns.collect` splits on human prompts. Shape matches `Turn.to_dict()` field-for-field, plus `unknown_cost: bool` — a call on a Codex model not in `usage/pricing.py`'s `OPENAI_PRICES` gets no fabricated dollar figure (§13.3): it is counted in `unpriced_calls` and left out of `cost`, which is the priced calls only.
- **Stats**: `agents/codex/stats.py` computes `stats_output()['agents']['codex']['windows']` in the same `five_hour`/`seven_day` `W`-shaped form Claude's own `windows` uses (§13.2), from the rollouts' `token_count` events and `rate_limits` (window kind identified by each slot's own `window_minutes`, not its position — see §13.2 for why) — additive to the existing (Claude-only) top-level `windows` key, so a Claude-only deployment's `json stats` shape is unchanged.
- **New-session id resolution**: unlike Claude Code, Codex has no flag letting the caller pick its own session id, so a new Codex session is started under a daemon-assigned uuid like any other, and `agent-sessions json resolve codex --pid PID --since ISO_OR_EPOCH --cwd PATH` is polled afterward to learn the real thread id (`agents/codex/resolve.py`). It tries, in order: (1) an open-fd inspection (`lsof -a -p PID -Fn` on macOS, `/proc/PID/fd/*` on Linux; none on Windows) of `PID` and its descendants (Codex has been observed to re-exec or fork a wrapper before opening its rollout) for a currently-open rollout path — exact, no ambiguity; (2) a fallback scan for the newest rollout whose `session_meta` has `timestamp >= since`, matching `cwd` (`paths.same_folder`: equal strings on Unix; on Windows case, separators, a trailing backslash and a `\\?\` prefix are ignored), `source == 'cli'`, and a thread id not already linked to a *different* daemon session in `sessions.json` (`already_linked`, passed by `json_output.resolve_output`). `null`/`null` (not an error) means the rollout hasn't been written yet; the plugin is expected to retry. The daemon's own child pid, needed for `--pid`, was already in `list`'s response (`Session.to_dict()`'s `pid`) — no wire-protocol change was needed for this.

  Once resolved, the thread id becomes that session's permanent identity (matching how Claude Code already works, where the daemon uuid *is* the transcript id) — the plugin swaps the tab's own id and writes the `sessions[<thread id>] = {"agent": "codex", "daemon": "<uuid>"}` link above, but the daemon keeps running that session under its original uuid (it was never told otherwise). So `json live`'s daemon-list merge (`json_output._daemon_list`) relabels: for a daemon session whose `agent` isn't Claude, it looks up `sessions.json` for a link whose `daemon` matches that session's `id`, and if found, replaces `id` with the thread id in the response — the only place this indirection is needed, since `json scan`'s own Codex and OpenCode rows are already keyed by their real ids (§3.3, `agents/codex/scan.py`). A link whose `daemon` uuid no longer names a running daemon session (the daemon restarted; the plugin will resume the session by its real id and get a new uuid, rewriting the link) is simply never matched by this lookup — stale, not an error.

`agents.opencode` reads OpenCode's SQLite database and a status plugin:

- **Database** (`agents/opencode/db.py`): in `$XDG_DATA_HOME/opencode/` (default `~/.local/share/opencode/`, on Windows too: OpenCode takes its folders from `xdg-basedir`, which has no Windows branch), chosen by OpenCode's own rule (`db_path`): `OPENCODE_DB` when set (relative to that folder unless absolute; `:memory:` leaves nothing to read), else `opencode.db` for the release channels or with `OPENCODE_DISABLE_CHANNEL_DB` set to `1`/`true`, else `opencode-<channel>.db`. The channel is built into the binary, so of `opencode.db` and every `opencode-*.db` the one written last (the file or its `-wal`) is read. The plugin passes `OPENCODE_DB`/`OPENCODE_DISABLE_CHANNEL_DB` along with the XDG variables (§7.7). It is opened the same way as Codex's `state_5.sqlite`: plain `mode=ro` (both through `paths.sqlite_uri`, a percent-encoded `file:` URI, `file:/C:/…` on Windows); if that fails and there is no `-wal` file, `mode=ro&immutable=1`; if that fails too, a private temp copy of the database and its `-wal`/`-shm`. Nothing here ever writes. The schema drifts between OpenCode versions, so every query goes through `PRAGMA table_info` and treats a missing column as `NULL`. OpenCode has no transcript files: a session's "transcript" is the pseudo path `opencode:<ses_id>`, which is never `stat`ed and never stored in `scan-cache.json` (a few indexed queries cost less than the cache bookkeeping); `json_output`'s `_agent_roots` maps the `opencode:` prefix to this agent so cache pruning keeps working.
- **Scan**: a session is listed when it is top-level (`parent_id IS NULL` — sub-agent sessions are excluded), not archived (`time_archived IS NULL`), and has at least one user message (OpenCode creates an empty session row at every TUI launch). `cwd` is `session.directory`; `name` is `session.title` unless it still starts with `New session - ` (OpenCode's placeholder, replaced by a generated title after the first turn), in which case the name is empty; `first_prompt` is the first non-synthetic text part of the first user message; `last_activity` is `time_updated / 1000`; `model` is `<providerID>/<id>` from `session.model`, else from the latest assistant message. A session whose `session.permission` holds a deny rule for `question` was made by `opencode run` (nobody is there to answer), and is reported `child: true`, which the lists hide, like Codex `exec` and Claude `-p` sessions. Sessions created over OpenCode's HTTP API, `opencode acp`, or the SDK write rows indistinguishable from TUI ones and are listed.
- **Live**: the status plugin writes `~/.agents/sessions/opencode/<ses_id>.json` = `{"status": "busy"|"idle"|"waiting", "waiting_for": "permission"|"question"|"", "pid", "cwd", "updated_at"}`; `agents/opencode/live.py` reads them. A file whose `pid` is dead (a killed `opencode` cannot run its exit hook) is ignored and deleted. All three statuses are reported, `idle` included. The app's `Registry` (§6) reads the same folder directly and watches it with `fs.watch`, so OpenCode's state reaches the UI without going through `json live`. A session with no usable file falls back to the database: its latest message is an assistant message with neither `time.completed` nor `finish`, updated within the last 120 seconds, while some `opencode` process (`opencode.exe` on Windows) is running, is reported `busy` (with a `pid` only when exactly one such process exists). The fallback cannot see `waiting`. The candidates come from one indexed query (`id` and `time_updated` of top-level sessions updated within that window), not from a scan of every listed session.
- **The status plugin** (`agents/opencode/plugin_js.py`, installed by `agent-sessions setup --opencode`): plain JavaScript using only `node:fs`, loaded by OpenCode from its `plugins/` folder. From OpenCode's events it sets `busy` (`session.status` busy/retry), `idle` (`session.status` idle, `session.idle`), and `waiting` (`permission.asked`/`permission.updated` until `permission.replied`; `question.asked` until it is replied to or rejected); `session.created` of a top-level session writes an `idle` file at once (this process's pid), so the file exists from launch, before any prompt; `session.deleted` removes the file. Sub-agent sessions are ignored, files are written atomically (temp file + rename; on Windows, where a rename over a file another process is reading fails, it is retried a few times and then written in place), and nothing is allowed to throw into OpenCode. The source is a string in a `.py` module so the plugin's bundle (§20.1) carries it without a separate asset. The file's first line is `// managed by Agent Sessions`: only a file carrying that marker is ever overwritten or removed, and an existing file without it is reported and left alone.
- **Detail and usage**: `json detail` returns the latest user text, the latest assistant text, the tools called since the last user message, and `model`; for Claude Code it also returns `recent_user`, the last four human prompts oldest first (injected notifications, teammate messages and command echoes left out, the same filter as `last_user`), which Organize reads; `last_command` is always `null` (OpenCode's slash commands are not recorded as user text). `agents/opencode/usage.py` starts a turn at each user message and sums every assistant message after it: `tokens.input`, `.output`, `.reasoning`, `.cache.read`, `.cache.write`, and the `cost` OpenCode itself stored on the message (`0` for a local model). No price table is involved; an assistant message without a numeric `cost` makes its turn's `cost` `null` with `unknown_cost: true`. The shape otherwise matches Codex's (§13.1).
- **Stats**: none. OpenCode has no vendor rate-limit windows, so `stats_output()` has no `agents.opencode` entry.
- **New-session id resolution**: OpenCode's `--session` only resumes an existing session, so a new session is started under a daemon-assigned uuid like Codex's, and `agent-sessions json resolve opencode --pid PID --since ISO_OR_EPOCH --cwd PATH` (`agents/opencode/resolve.py`) is polled for the real `ses_…` id. It tries, in order: (1) a status file whose `pid` is `PID` or one of its descendants (the PTY child can be a wrapper) — exact, since the plugin writes the file when the session is created; (2) the top-level session whose `directory` is `cwd` (`paths.same_folder`), with `time_created >= since`, that isn't in `already_linked` and isn't an `opencode run` session (deny-`question` rule) — and only when exactly one such session exists: with several candidates nothing is returned, because guessing could tie a tab to another tab's session, and the caller polls again. The session row exists from TUI launch, so no user message is required. The link is written and relabeled exactly as for Codex above.

## 4. The daemon and its wire protocol

### 4.1 Why a daemon

Without something holding the PTY open, closing a terminal tab — or reloading Obsidian, which recreates every view — would kill the underlying `claude` process along with it. The daemon is a small resident process, started on demand by the plugin, whose only job is to keep each session's PTY alive independently of any tab or Obsidian instance being attached to it. A tab detaching (closing, or Obsidian restarting) doesn't touch the session; reattaching replays what was missed.

It's a single-threaded `select` loop over the listening socket, every open client connection, and every session's PTY master fd, with no blocking I/O anywhere (sockets and PTYs are non-blocking; each connection's output is flushed from its own queue whenever the socket is writable). `agentsessions/` as a whole — the daemon included — uses only the Python standard library: no dependency to install means the daemon can be launched by a plain `#!/usr/bin/env python3` script with nothing more than a working `python3`, on any machine that has one.

On macOS and Linux, communication happens over Unix domain sockets (`~/.agents/sessions/daemon.sock`, plus `plugin.sock` for the built-in editor) rather than TCP: both sides always run on the same machine, so a filesystem path is a strictly better address than a port — it can't collide with another process, access control follows filesystem permissions (the containing directory is 0700, the socket itself 0600), and there's nothing to accidentally expose on a network interface. Windows has no equivalent that both Node and Python can use portably, so there the same two endpoints are loopback TCP (§19.1).

### 4.2 Sockets and frames

`~/.agents/sessions/daemon.sock` (on Windows, a loopback TCP connection after the token line of §19.1). Both directions share the same frame format:

```
+------+----------------+---------+
| type | length (u32 BE)| payload |
| 1 B  | 4 B            | n B     |
+------+----------------+---------+
```

| type | direction | payload |
|---|---|---|
| `J` | both | JSON (UTF-8): requests, responses, events |
| `D` | both | Raw bytes: client→daemon is PTY input, daemon→client is PTY output |
| `R` | daemon→client | The replay buffer sent right after attach (possibly several frames); replay ends with `{"ev":"replayed"}` |

Requests (`J`, distinguished by `"op"`) and their responses (echoing the same `"seq"`):

| op | arguments | response |
|---|---|---|
| `hello` | `client` (`plugin`/`tui`/`cli`) | `{"ok":true,"version":1,"pid":…}` |
| `list` | — | `{"ok":true,"sessions":[{"id","agent","cwd","pid","startedAt","clients","exited":null or code,"exitedAt"}]}`. Exited sessions stay listed until `forget`-ten |
| `start` | `id`,`agent`,`cwd`,`argv`,`env`,`cols`,`rows` | `{"ok":true}`, or `{"ok":false,"error":"exists"}` if that `id` is already running |
| `attach` | `id`,`cols`,`rows` | `{"ok":true,"exited":null or code}` → `R`… → `{"ev":"replayed"}` → then `D` frames. For an already-exited session, `{"ev":"exit",…}` follows `replayed` immediately. `{"ok":false,"error":"no-session"}` if there is no such session |
| `detach` | — | `{"ok":true}` |
| `resize` | `cols`,`rows` | `{"ok":true}` |
| `kill` | `id`,`signal` (default `TERM`) | `{"ok":true}` |
| `forget` | `id` | Discards an exited session's record and buffer, `{"ok":true}`. `{"ok":false,"error":"running"}` if it's still running |
| `shutdown` | — | `{"ok":true}`, then the daemon exits |

Events (daemon→client, `"ev"`): `exit` (`id`, `code`), `replayed`. A single connection attaches to at most one session at a time; multiple connections (the plugin and the TUI, or two split panes) may attach to the same session — output fans out to all of them, input is accepted from any of them. **The PTY size is the minimum of cols and minimum of rows across every attached connection** (the same rule tmux uses), recomputed on `resize`, `detach`, and disconnect.

Disconnection: if `select` reports the socket readable but `recv` returns empty, or the connection raises `ECONNRESET`/`EPIPE`, it's treated as disconnected — removed from the session's attached connections, `clients` count decremented, size recomputed. This follows the same cleanup path as an explicit `detach`.

### 4.3 Session lifetime

- `start`: `pty.fork()` → the child does `os.chdir(cwd)` then `os.execvpe(argv[0], argv, env)`; the parent sets the initial size with `TIOCSWINSZ`.
- The child's environment is exactly the request's `env` (the daemon's own environment isn't inherited) plus `TERM=xterm-256color`, `COLORTERM=truecolor`, and `AGENT_SESSIONS_ID=<id>`. The plugin builds `env` from three sources: `PATH`, `LANG`, `HOME`, `USER`, `TMPDIR`, and `CLAUDE_CONFIG_DIR` taken from a login shell (`backend.ts`'s `loginEnv`: `$SHELL -l -c env`, run once and cached, falling back to `defaultLoginShell(isMac)` — `/bin/zsh` on macOS, `/bin/sh` on other platforms, since some minimal Linux/WSL2 setups don't have `bash`), so they match what a real terminal would see (Obsidian launched from the Dock, or an equivalent GUI launcher, otherwise inherits a much sparser environment); `VISUAL` (`main.ts`'s `visualPath()`: `agent-sessions-code` next to the `agent-sessions` in use); and `AGENT_SESSIONS_VAULT` (§3.2). `EDITOR` is left untouched. **`PATH` specifically** also gets whatever an interactive shell adds on top: `loginEnv` additionally runs `$SHELL -i -c 'echo $PATH'` (the same marker-wrapped, 3-second-timeout `execInteractive` probe `locateBinary` uses, §7.7) and merges its `PATH` onto the login shell's with `mergePath` (login entries first, then any new ones from the interactive shell, in order, duplicates dropped) — a login-but-non-interactive shell never sources `.zshrc`/`.bashrc`, so a version manager (mise, nvm, …) wired in there is invisible to a plain login `PATH`, and without this fix not just this plugin's own binary lookups but *the launched session itself* — and anything it shells out to, like another Claude Code plugin's own hook script needing `node` — could fail to find it. If the interactive probe fails or times out, `PATH` is just the login shell's own, unchanged, so this never blocks a session from starting. Cached together with the rest of `loginEnv`; the Agents settings tab's "Find again" button (`resetLoginEnvCache`) re-probes it too, so a session started right after doesn't launch with a stale `PATH`.
- Output buffering: a `deque` of chunks per session, capped at 1 MiB total, oldest chunks dropped first. Replay starts at a chunk boundary and is sent in `R` frames of up to 64 KiB. Each connection's send queue is capped at 4 MiB; a client that falls further behind is disconnected.
- On attach: `resize` is applied, then the buffer replays via `R`. If attaching *changed* the PTY size, the row count is reduced by one right after `replayed` and then restored a moment later — this nudges Claude Code into redrawing the bottom of the screen via `SIGWINCH`; when the size didn't change, the replayed screen is already correct as-is.
- Exit detection: EOF or `EIO` on the master fd triggers `waitpid(pid, WNOHANG)`. `SIGCHLD` is also routed through a self-pipe into the `select` loop, to catch the case where a grandchild process still holds the PTY open and EOF hasn't arrived yet. Once detected, every connection attached to that session receives an `exit` event.
- Suspend (Unix): a session leads its own session (`pty.fork` calls `setsid`) with no shell above it, so nothing can `fg` a suspended agent; the daemon undoes every suspend itself (`_unsuspend`). `waitpid` also passes `WUNTRACED`, and a child seen stopped gets `SIGCONT` on its process group at once. Claude Code and OpenCode don't let the line discipline turn Ctrl+Z into a signal (they run in raw mode); they read the `0x1A` byte, leave raw mode, register a `SIGCONT` handler that takes the terminal back, and send `SIGTSTP` to their own process group — which the kernel discards for an orphaned process group, so they never stop and wait for that `SIGCONT` instead. For 5 seconds after input containing `0x1A`, the daemon therefore checks the terminal every 50 ms and sends `SIGCONT` when it finds it back in cooked mode (`ICANON`, read with `tcgetattr` on the master), again at most every 0.5 s while it stays there. An agent that gives Ctrl+Z its own meaning stays in raw mode and gets no signal. Either way the screen then gets the same one-row `SIGWINCH` nudge as on attach, and `daemon.log` records `continue <id> (stopped|suspended)`.
- An exited session is **kept until `forget`-ten** (its record and buffer). A background tab that later attaches still gets a replay followed by `exit`, landing on the same exited screen. `forget` is sent by the plugin ("Resume"/"Close") and by the TUI.
- `kill` sends `SIGTERM` to the process group, `SIGKILL` after 10 seconds.
- The daemon itself exits once it has had zero running sessions and zero connections for `idle_exit` seconds (default 600; configurable via `--idle-exit`). On any exit (idle timeout, `shutdown`, `SIGTERM`), it writes **only the sessions that had already exited by that point** (`id`, `code`, `exitedAt`) to `exited.json`, which the next daemon instance reads back on startup and keeps until each one is `forget`-ten (buffers aren't carried over — only the fact that it exited and with what code). Sessions still running when the daemon itself is killed by `SIGTERM` (as part of its own shutdown) aren't recorded there, since that's an external stop, not the session's own exit; they resume normally with `--resume` after a restart. A background tab attaching across a daemon restart still gets `exit` and lands on the exited screen. `exited.json` has no size cap — it doesn't grow unbounded because the plugin sends `forget` for any exited `id` with no open terminal tab, on every `onLayoutReady` and `layout-change` (an `id` that still has a tab is left alone). `SIGTERM` kills every running session before the daemon itself exits. A single daemon instance is guaranteed by `daemon.pid` plus `flock`: a second daemon that fails to acquire the lock exits immediately, and the caller (the plugin) waits one second and reconnects.
- On startup, `~/.agents/sessions/` is created with mode 0700, and the socket is bound under `umask 0077`.

`model`/`effort` are additive and non-Claude: `agents/opencode/scan.py` fills `model` only (`<providerID>/<id>`, e.g. `ollama/gpt-oss:20b`; OpenCode has no effort field), and `agents/codex/scan.py` reads both from the rollout's most recent `turn_context` (`payload.model`/`.effort`; an older rollout has no top-level `effort`, only `collaboration_mode.settings.reasoning_effort`, checked as a fallback). Cached in the same `scan-cache.json` entry as `head` (§3.3's `SCAN_SCHEMA_VERSION`). Not added to Claude Code's own rows — Claude's model/effort already come from statusLine (§14), real-time and already surfaced separately; a transcript-derived copy here would risk showing something stale or inconsistent with what statusLine reports for the same session.

Scanning (`sessions/scan.py`): transcripts are `~/.claude/projects/*/<uuid>.jsonl`. Names come from one call over every transcript for `custom-title` lines — `rg` if it's on `$PATH`, else `grep` (found via `$PATH`, never a hard-coded path — some environments don't have it at `/usr/bin/grep`, or at all), else transcripts are read directly in Python, line by line; the last matching line in a file wins in every case. The head of each file (up to 2000 lines) yields `cwd`, the first human prompt, and `child` — true when an `agent-setting` line is present, `sessionKind` is `bg`, or the first `entrypoint` seen isn't `cli`. `last_activity` is the timestamp of the last user message or assistant response, found by reading backward from the end of the file (up to 16 MiB; tool-result, meta, and sidechain lines don't count), falling back to the file's mtime.

Caching: `scan-cache.json` holds `path → {mtime,size,schema_version,head,last_activity}`. A file is skipped when its `mtime` and `size` still match *and* `schema_version` equals `SCAN_SCHEMA_VERSION`, unless its mtime is within `RACY_WINDOW` of now (§19). `SCAN_SCHEMA_VERSION` (bumped whenever the extraction logic that produces `head` changes) protects against an *unchanged transcript* being trusted from a cache entry written by older, now-different extraction logic after an upgrade — mtime/size alone can't detect that, since the transcript itself never changed, only the code reading it did. `agents.codex.scan`'s own `SCAN_SCHEMA_VERSION` (§3.3) works the same way, versioned independently, sharing this same cache file. A second full scan takes well under 0.1 seconds. OpenCode's rows bypass this cache entirely (§3.3).

### 5.1 Starting and reading sessions from the CLI

`new`, `sessions`, `show` and `stats` exist for the agent skills (§20.2) and for scripts; their text output is English and meant to be read by an agent or a person, and `--json` gives the same data as JSON.

**`new`** repeats the plugin's launch without Obsidian. It registers the session in `sessions.json`, starts the daemon detached when nothing answers on its socket, and sends `start` with the argv and env the plugin would use. Where the plugin reads its settings, the program reads a mirror of them: `ui.json`'s `agentLaunch` holds, per agent, the configured executable (empty = first match on `PATH`), the parsed "environment variables", and for OpenCode `launchVia` and `ollamaModel` (`agentsessions/agents/launch.py`; written by `backend/ui-state.ts`'s `agentLaunchFor`). Argv per agent:

| Agent | argv |
|---|---|
| Claude Code | `claude --session-id <uuid> [--name=N] [--remote-control[=N]] [-- PROMPT]` |
| Codex | `codex [-- PROMPT]` |
| OpenCode | `opencode [--prompt PROMPT]`, or `ollama launch opencode --model M -y -- [--prompt PROMPT]` |

The env is the plugin's: from the caller only `PATH`, `LANG`, `HOME`, `USER`, `TMPDIR` and `CLAUDE_CONFIG_DIR` (the login-shell subset the plugin takes), then `VISUAL` (and `EDITOR` for OpenCode) set to the built-in editor's shim, `AGENT_SESSIONS_VAULT`, and the agent's own variables; the binary's directory leads `PATH`. Everything else the caller has (`CLAUDECODE`, `CLAUDE_PID`, `CLAUDE_EFFORT`, `CLAUDE_CODE_*`, `CLAUDE_PLUGIN_*`, `AGENT_SESSIONS_ID`, `CODEX_THREAD_ID`, `OPENCODE_PID`) is left out, so the new session is not taken for a child of the caller. The default agent is the caller's own (the daemon's record of `AGENT_SESSIONS_ID`, else the markers above); it must be enabled.

Confirmation differs by agent. Claude Code takes its id, name and Remote Control as flags, so the transcript confirms them: the latest `custom-title` equals the name, and a `system`/`bridge_status` line carries the Remote Control `url`. With neither a name nor Remote Control there is nothing to read back, and the session counts as started when it is still running after a moment. Codex and OpenCode choose their own ids and record a session only once its first message is sent, so `new` polls `json resolve` (the plugin's method, §3.3) and, when it finds the id, writes the link `sessions[<id>] = {agent, cwd, daemon, name?}` (the name is kept for OpenCode only; Codex cannot be named at launch and the output says so). `--prompt` is optional. Without it there is nothing to resolve yet, so `new` exits `0` once the process is still up after a moment and prints the daemon id with a note that the session appears under its real id after the first message and that Obsidian links it: the plugin resolves and links any running, unlinked Codex/OpenCode daemon session it sees on a live refresh (`sessions/orphans.ts`, `main.ts`'s `adoptOrphanSessions`, §7.7), for as long as it runs. An OpenCode `--name` waits in `pendingRenames[<daemon id>]` (§3.2) for that link. With `--prompt`, `new` itself polls for the id as above and, if it does not appear in time, exits `1`. A session that ends before it is confirmed exits `2`. Exit `1` never retries: the session keeps running and the output says how to attach.

**`sessions`** merges `json scan` and `json live`: `status` is `running` (busy, or running a shell command), `asking` (the agent waits for an answer; `waiting_for` says which), `idle`, or `ended` (no agent process). The plugin's "waiting" (a finished turn not yet looked at) has no counterpart, because nothing looks at a session from the CLI. Child (sub-agent) and archived sessions are left out unless `--all`. **`show`** and the skills identify the caller's own session by `AGENT_SESSIONS_ID` mapped through `sessions.json`'s daemon links, else `CLAUDE_CODE_SESSION_ID` / `CODEX_THREAD_ID`. A query is an exact id, a unique id prefix (4+ characters), an exact name, or a unique name substring; several matches are listed and none is picked.

`AGENT_SESSIONS_RUNTIME_DIR` moves the whole runtime directory (`config.RUNTIME_DIR`: socket, pid, log, `ui.json`, `vault.json`, status files), so a scratch daemon and its clients stay apart from the real one.

## 6. Sending commands (rename, compact)

`/rename NAME` and `/compact` both go through `main.ts`'s `sendCommand(id, text)` to reach the PTY. The row menu and the dialogs call this one function without caring which path below it takes.

Every path sends the same shape of sequence (`terminal/command-chunks.ts`'s `commandChunks`, agent-aware — §7.7): for Claude, Ctrl+S (`\x13`, Claude Code's built-in `chat:stash`) only when the open tab's input box holds a draft — on an empty box Ctrl+S brings a previously stashed draft back instead, and the command would land after it (`terminal/prompt-draft.ts`'s `promptHasDraft` reads the visible rows: the last `❯` line and its continuation lines up to the `─` rule count as a draft when any character after the `❯` is drawn at normal intensity, since the empty box's placeholder is dim — Codex's composer is read the same way from its `›` line down to the first blank line, which `nameNewCodexSession` uses, §6; routes 2 and 3 have no screen to read and send no Ctrl+S) → the command as a **bracketed paste** (`\x1b[200~` + text + `\x1b[201~`; typing it as literal keystrokes would trigger `/` completion and corrupt it; for Claude, a command with no argument, such as `/compact`, is followed by Tab, since its completion list stays open otherwise and swallows a rebound submit key such as meta+Enter — the paste, the Tab and the submit go in three writes 250 ms apart (`COMMAND_CHUNK_GAP_MS`), so the list exists by the time Tab arrives; for Codex, a command with no argument is pasted with a trailing space, which closes its popup, and the submit key follows in a second write (on Windows the submit key is always a second write, §19.1); for OpenCode the paste and the `\r` go in two writes the same distance apart, since `\r` runs the highlighted popup command only once the popup is up — arriving with the paste it's read as Return in the input box, a newline under the managed keybinds — and a trailing space would send `/compact ` to the model as plain text) → the submit sequence (`submitSequence(settings, agent)`, §7.2 — Claude Code's and Codex's configured submit key; plain `\r` for OpenCode). Ctrl+S is skipped for any non-Claude agent (`chat:stash` is Claude Code-specific; an agent that doesn't recognize Ctrl+S could treat it as XOFF and hang, rather than harmlessly no-op). **The stashed draft is never restored explicitly** — Claude Code restores it on its own after the next submission ("Draft restored").

1. **A tab is open and attached**: write to the PTY from that tab. Looked up by `id` directly (`main.ts`'s `findTerminalView`) — an open tab's own `sessionId` (`TerminalView.id`) is already the real id post-relink (the same "one session, one tab" identity used everywhere else — §7.7), never the daemon-tracked placeholder.
2. **No tab, but the daemon has it running**: attach temporarily (120×40) under the daemon-tracked id (`main.ts`'s `daemonIdFor(id)`, which can differ from `id` for a linked Codex or OpenCode session — §7.7), write, detach.
3. **Not on the daemon, or exited** (`forget` first if exited): **start it in the background**, under the session's own real id (never the daemon-tracked placeholder — a since-ended daemon session's placeholder is meaningless to resume by) — `start` (resume argv per agent, 120×40) → attach → `registry.waitFor(id, 'idle', 60s)` (waits for the state itself, not a transition, so it works even for an `id` never observed before) → send the command → `waitFor(id, 'busy', 10s)` (catches commands that never go busy) → `waitFor(id, 'idle', 60s)` → send `/exit` the same way → wait up to 30s for `exit` (falling back to `kill`) → detach → `forget` → `rescan([id])`. Progress shows as a `Notice` ("Renaming…"). A timeout raises, and the caller shows it in a `Notice`; every way out that isn't success (a failed start, a timeout, a thrown error) kills the background process and forgets it, so none is left running. OpenCode reports status only when its plugin sees an event, so a freshly resumed session may show none until a turn has run: for OpenCode the two `idle` waits also accept "no status at all and the terminal quiet for 2.5 seconds after it started drawing" (`backend/headless-ready.ts`); a `busy` or `waiting` status is never taken as ready. The `busy→idle` notification (§12) is suppressed for the duration of this path.

A new, named **Claude** session takes its name on the command line (`--name=NAME`, §7.7's launch argv; `newSession` keeps it in `launchNames` until the first `start`, and in `pendingNames` for the tab title), so a Remote Control session it starts is created under that name. Claude Code writes a `--name` to the transcript only with the first message, so `start` is still followed by `waitFor(id,'idle')` → `sendCommand(id, '/rename NAME')` with the same name, which writes it at once. Both renaming and creating a session fire `SessionIndex.waitForName(id, expected, timeoutMs=5000, intervalMs=300)` right after sending, without waiting for it: it resolves immediately if the name already matches, otherwise rechecks every 300ms (calling `rescan([id])` in between) for up to 5 seconds before giving up silently (worst case, the periodic scan in §10.1 catches up later). `/rename` doesn't invoke the model, so it never goes `busy` and produces no `events.log` entry — without `waitForName`, the tab title would stay stale until the next periodic scan (60 seconds). OpenCode has no `/rename`: renaming an OpenCode session writes `sessions[<id>].name` in `sessions.json` (inside the §3.1 lock) and rescans, sending nothing to the TUI and needing no `waitForName`; the session index overlays that name on the row. Which of the two a rename takes is decided by the agent that runs the session — the open tab's own agent first (a fresh tab has no row and no store entry under its placeholder id), then the index row, then `sessions.json` (`sessions/rename.ts`) — never by the index row alone, so `/rename` is never typed into an OpenCode TUI (it would reach the model as a prompt). A tab still under its placeholder id (§7.7) keeps the name in memory (`pendingNames`, shown in the tab title at once) and `linkAgentSession` writes it into `sessions.json` when the real id is known; a new OpenCode session named at creation takes the same path. A new Codex session named at creation (`sessions/rename.ts`'s `createNameRoute`: `composer`) keeps the name in `pendingNames` too, so the tab title and the side panel's stand-in row (§8) show it at once, and gets `/rename NAME` typed into its composer as soon as that is on screen and empty (`nameNewCodexSession`: the tab is attached and `promptHasDraft(…, 'codex')` is `false` — the last `›` line and the lines under it up to a blank line hold only the dim placeholder, and the `›` itself isn't dim, which would mean input is disabled). Codex names its thread before the first message: the TUI starts its thread at launch, and `/rename` there sets `threads.name` in `state_5.sqlite` and `session_index.jsonl` with no rollout yet (`codex-rs/app-server`'s `thread/setName` → `update_thread_metadata`); a `/rename` typed before the thread has started is held ("Waiting for startup") and applied once it has (`chatwidget/input_flow.rs`'s queue). Checked on codex-cli 0.160.1, sent 0.3 s and 10 s after launch, and the name stays once the first message creates the rollout. When `resolveAgentSession` links the tab, `linkAgentSession` writes the name into `sessions.json` (`sessions[<thread id>].name`), and the session index shows it on the Codex row until Codex's own title has a name (`rowFromScan`, `Row.nameStored`). `confirmCodexName` then rescans that row for up to 15 s; if Codex's own title still lacks the name (the composer never came up empty, or a Codex version dropped the early `/rename`), it waits for the tab's turn to end (`terminalStatuses`: not working, asking or connecting) and the composer to be empty, and sends `/rename NAME` once more. A Rename in the meantime replaces the name given at creation, and nothing checks for the old one any more.

**Remote Control title.** Claude Code titles a Remote Control session once, when it creates it, from the session's name at that moment (`--remote-control NAME`, else the name, else a title it derives from the conversation). After that only `/rename` while connected changes it: a resumed session (`--resume`) reconnects to the Remote Control session recorded in its transcript without sending its name, and a rename made while it was not connected — route 3, Remote Control off or still connecting — never reaches it. Hence the `--name` at creation, and two more steps:

- **After a resume**: when a tab starts a Claude session with `--resume` (`TerminalView.startSession`, which covers opening an ended session and Restart), `main.ts`'s `syncRemoteControlTitle` waits up to 120 s for that process to report Remote Control connected (`bridgeSessionId` in `~/.claude/sessions/<pid>.json`, `RegistryEntry.rc`) and `idle` — `Registry.waitUntil`, with the record's `startedAt` no earlier than the launch, so a previous process's record does not count — and then sends `/rename <current name>` through `sendCommand`. A session without a name, or whose Remote Control never connects, gets nothing. `/rename` with an unchanged name still sends the title, so the transcript gains one "Session renamed" line per resume of a named session connected to Remote Control.
- **Route 3**: when resuming the session connects Remote Control — `remoteControlAtStartup: true` in Claude Code's `settings.json`, or a `bridge-session` line in the transcript, since a resume reconnects to a recorded Remote Control session even with the setting off (`sessions/remote-control.ts`'s `resumeConnectsRemoteControl`) — the headless process waits to be connected and `idle` (`Registry.waitUntil`, up to 30 s) before `/rename` is sent, and after the new name shows up it waits 2 s more (`RC_TITLE_SETTLE_MS`) before `/exit`, so the title request leaves before the process ends. A session that never used Remote Control is renamed without the wait.

`/remote-control NAME` is not a way to rename: on a connected session it opens the status and disconnect dialog.

Whether the session has just been compacted with no instruction since comes from `row.compacted` (§7.5 — the SessionStart(compact) marker or the transcript's `after_compact`, kept through local commands until a prompt the model answers; Claude only, so the action is never disabled for Codex or OpenCode). `isJustCompacted` disables the row menu's/terminal's "Compress session" action while it's set, and `compactSession` checks it again before sending, showing a `Notice` instead. `json detail`'s `last_command` isn't used for this: it's the most recent slash command anywhere in the tail, which stays `/compact` through any number of ordinary prompts afterwards.

## 7. The terminal view (`agent-sessions-terminal`)

State (`getState`): `{id, agent, cwd, fontSize?, fresh?, daemonId?}` (`fresh` is true only for a brand-new, not-yet-started session, and clears on the first `start`; `daemonId` is only present for a linked Codex or OpenCode session, where it differs from `id` — §7.7). Obsidian persists this in the workspace and restores it across restarts.

### 7.1 Connecting, I/O, and sizing

- xterm 5.x: `fontFamily`/`fontSize` from settings (a per-tab `fontSize` takes priority), `lineHeight: 1.0`, `letterSpacing: 0`, `scrollback` from settings (default 5000), `allowProposedApi: true`, `macOptionIsMeta: true`, `cursorBlink: true`. Addons: fit, webgl (falls back to the default canvas renderer on failure), unicode11.
- Padding: the `padding` setting (`comfortable` = 12px / `compact` = 4px / `none` = 0) flows into a CSS variable on the container. `.agent-sessions-terminal-body` is `overflow: hidden`, and `fit()` computes against the area minus padding — `FitAddon` reads the *element's* padding, so the padding lives on the outer wrapper rather than xterm's own parent, keeping the scrollbar out of the padded area.
- Connecting: the first time the `ResizeObserver` reports a non-zero size, `ensureAttached()` runs. If the daemon already has that `id`, it attaches (an exited session replays then immediately shows the exit screen); otherwise it starts one — `argv` depends on the agent (`backend.ts`'s `buildAgentArgv`; §7.7). If the daemon can't be reached, it tries to start it, waits one second and reconnects, and shows an error on the exit screen after three failures.
- Output: `D` frames go to `terminal.write(Uint8Array)`. Writes during replay (`R`) are batched, with `scrollToBottom()` once `replayed` arrives.
- Input: `onData`'s string, and `onBinary`, both go out as UTF-8 `D` frames.
- Sizing: `ResizeObserver` → 50ms debounce → `fit()` → `onResize` → `resize`.
- Exit (`exit` event): a "The session has ended (code)" banner appears over the output, with **Resume** and **Close**. Resume is `forget` followed by `start` with `--resume`; Close is `forget` and closing the tab. When the exit follows a failed resume (the output matches "No conversation found", "Session not found", or "not found"), **Start as new** is offered as well. The same banner area covers the other failure cases: a lost daemon connection offers **Reconnect**; an unreachable daemon, a missing `claude` (with a link to settings), or any other start error offers **Retry**; each also offers **Close**.
- Closing a tab (`onClose`): detaches and closes the connection, disposes xterm. The session itself keeps running. `SessionIndex`, `registry`, `statusline`, and `settings-changed` subscriptions are registered via `this.register(unsubscribe)`, which Obsidian tears down on `onClose`.
- Settings changes: `main.ts` fires `settings-changed` on save, and every open terminal view's `applySettings()` re-applies font, size (a per-tab override if set), padding, and scrollback to xterm and calls `fit()`.
- Header actions (`addAction`): `@` (insert the current note), previous prompt, next prompt, last response. Session-level actions (rename, compress, archive, end, session analysis, copy ID) live in the row menu on the side panel and manager instead. The terminal's own `⋯` (`onPaneMenu`) has Obsidian's standard items (including split right/split down) followed by a separator, then "Rename", "Compress session", "Session analysis", "Copy ID" (archive and end-session stay row-menu-only).

### 7.2 Submit key and Enter

One setting, **submit key** (`enter` default, `shift+enter`, `ctrl+enter`, `alt+enter` (Option), `cmd+enter` — macOS-only, see below for non-macOS). Any other Enter combination becomes a newline. `views/terminal.ts`'s `handleKey` (`attachCustomKeyEventHandler`) intercepts every Enter combination except while composing with an IME (the pure logic lives in `keys.ts`) — **for every agent's tabs**. `classifyEnter`/`resolveEnterAction` have no agent concept; the bytes sent come from `agentSendSequence(agent, action, submitKey)`: for Claude Code and Codex it is `sendSequence` (below — the same bytes for both, only which config file gets written, `keybindings.json` vs. `config.toml`, differs); for OpenCode, with the submit key on Enter (its defaults, nothing written) the submit key sends `\r` and every other Enter combination `\n` (Ctrl+J, a newline in OpenCode); with any other submit key its `tui.json` is set so that `\n` submits and `\r` is a newline (§7.7), so the chosen submit key sends `\n` and every other Enter combination `\r`. Plain Enter is `\r` in both modes, which is what OpenCode's popups and dialogs select on:

- `classifyEnter(ev)`: `passthrough` if it isn't Enter, or during IME composition (`isComposing`/`keyCode 229`). Otherwise classifies the modifier as one of shift/ctrl/alt/cmd (metaKey)/none, in that priority order.
- `resolveEnterAction(cls, submitKey)`: `submit` on a match, otherwise `newline` (or `passthrough` for a non-Enter key or mid-composition).
- `sendSequence(action, submitKey)` (i.e. `submitSequence()`): when `submitKey === 'enter'`, Claude Code's own default applies — submit is `\r`, newline is `\x1b\r`. Any other submit key reverses that (`keybindings.json` for Claude, `config.toml` for Codex — see below), so submit is `\x1b\r` (meta+enter/alt-enter) and newline is `\r`. This is centralized in `sendSubmit()`, which also records the prompt marker (§7.3). Sending a command (§6) and the built-in editor's "Send" (§7.4) use the same function.

Esc stops `keyup` propagation (Obsidian would otherwise steal focus). `Cmd +`/`Cmd -`/`Cmd 0` are the font-size shortcuts; every other Cmd-combination is left to propagate to Obsidian (xterm sends nothing for Cmd-combinations, and blocking them would break Cmd+W/Cmd+P). Ctrl- and Option-combinations, and unmodified keys, go to xterm, with `keydown` propagation stopped so Obsidian's hotkeys don't also see them. Every Enter combination, including Option+Enter, is intercepted by `handleKey`, so it always resolves to either submit or newline per the setting.

`keybindings.json` (under `$CLAUDE_CONFIG_DIR`, not the vault's own `.claude/`) is written by `applySubmitKey`, called the instant the dropdown changes (through a confirm dialog for anything other than `enter` — `confirm.writeKeybindings`) — never only at startup or from a separate "apply" step. When `submitKey !== 'enter'`: `Chat.enter` is set to `chat:newline` and `Chat.meta+enter` to `chat:submit` (`$schema`/`$docs` are added if missing). Reverting to `enter` removes both. Either way, `applySubmitKey` also cleans up `OWNED_KEYS` — `enter`/`meta+enter`/`cmd+enter`/`ctrl+enter`/`shift+enter`/`alt+enter` — the full set of keys this feature could plausibly have put a `chat:submit`/`chat:newline` value on across its history (an earlier version wrote `shift+enter` directly; a hand-edited or Claude-Code-authored file can use any of the literal `SubmitKey` names): switching to a non-`enter` key clears any of the other four holding a stale `chat:submit`, and switching back to `enter` clears every one of the six still holding its canonical value. A key holding some other, unrelated action is always left alone (with a `warning` when it was one of `OWNED_KEYS`, since that specific key not matching what this feature expects needs a manual look). This is a Claude Code-wide setting, so it also affects `claude` started from any other terminal (the settings tab says so — including that whether that terminal can even tell `ctrl+enter`/`cmd+enter` apart from plain Enter depends on the terminal, so only this plugin's own tabs are guaranteed to send the chosen key reliably, since they synthesize the bytes themselves rather than relying on the terminal to report the real modifier). `applySubmitKey` returns `{status: "written" | "unchanged" | "failed", warning?}` — the settings tab shows a `Notice` for all three (`notice.keybindingsWritten`/`notice.keybindingsUnchanged`/the `warning` text on failure), so every change to this setting has a visible, immediate result.

`agentsessions/claude/keybindings.py`'s `remove_enter_keys()` (`agent-sessions setup --remove`/`uninstall.sh`, §5) mirrors this same `OWNED_KEYS` set and `ownedCanonicalValue` rule (its own `OWNED_KEYS` constant), so a stray `cmd+enter`/`ctrl+enter`/`shift+enter`/`alt+enter` entry is cleaned up the same way on uninstall as it would be by the plugin's own `applySubmitKey`.

**Codex's own config**: `terminal/codex-config.ts`'s `applyCodexConfig(path, submitKey)` writes Codex's submit-key keymap and, only when `[tui]`'s `status_line` isn't already set (by the plugin or the user), a default `status_line`, to `$CODEX_HOME/config.toml` (`CODEX_HOME` — this plugin's own "Codex environment variables" setting first, then the system env var, then `~/.codex`; resolved by `AgentSessionsPlugin.codexConfigPath()`, the same priority `agentEnvFor` uses for the Python side — not the vault's own `.claude/`, and not the same file as Claude Code's `keybindings.json`). Called from the same place Claude's `applySubmitKey` is (the settings tab's submit-key dropdown, behind the same confirm dialog when leaving `enter` — its message names both files when Codex is enabled), once more when Codex is switched on, when the program is installed or reinstalled (`installBackend`, which the install dialog and the welcome guide both run), and on load for an enabled Codex the plugin has never set up — first-run detection just enabled it, or it was enabled before the plugin did this (`applyAgentConfigOnce`, `settings.ts`'s `agentConfigDue`; each of these records `codex` in the hidden `agentConfigApplied` setting, so a later load leaves the file alone and a `status_line` the user took out stays out until the next install or switch-on) — so `status_line`'s default gets its chance to apply even if the submit key is still `enter`, which writes nothing keymap-related; and when Codex's "environment variables" field is left with a `CODEX_HOME` that names another existing folder (a new profile gets its own managed lines; `codexProfileNeedsSync` — not on every keystroke, and never for a folder that doesn't exist).

From the Codex source (`codex-rs/config/src/tui_keymap.rs`/`tui/src/keymap.rs`, codex-cli 0.154.0-alpha.6.2): `composer.submit`'s default is plain Enter alone; `editor.insert_newline`'s default is Enter, Shift-Enter, *and* Alt-Enter together (own `deny_unknown_fields` schema — an unrecognized field name breaks the whole file). Codex's key-chord syntax also has no `cmd`/`super`/`meta` modifier at all (only `ctrl`/`alt`/`shift`), so there's no way to write "Cmd+Enter" into it directly. Rather than needing a different Codex binding per `submitKey` choice, this feature always writes the *same fixed pair* whenever `submitKey !== "enter"` — `composer.submit = "alt-enter"` and `editor.insert_newline = ["enter", "shift-enter"]` (the default three, minus `alt-enter`, so nothing conflicts) — regardless of which of the 4 non-`enter` choices is actually configured. This works because the plugin's own key interception (above) is what translates whichever one the user picked into that same alt-enter byte sequence (`\x1b\r`) sent to the PTY — mirroring Claude's own `keybindings.json` approach exactly (one fixed `meta+enter` binding there too, regardless of which literal `SubmitKey` is configured). Reverting to `submitKey === "enter"` removes both managed lines instead of leaving them stale. `status_line`'s default, when it applies, is `["model-with-reasoning", "context-used"]` — the closest match among Codex's own real status-line item names (defined in `codex-rs/tui/src/bottom_pane/status_line_setup.rs`) to Claude Code's own statusLine's "model · effort · ctx%".

Every line this writes ends with a trailing comment, `# managed by Agent Sessions` (`MANAGED_MARKER`, must match `agentsessions/codex/config_toml.py`'s own constant exactly — agreed with lnx-py), and it never overwrites a pre-existing, unmarked line for a key it wants to write (a `warning`, same shape as `applySubmitKey`'s, names the conflicting key instead — `status_line` is the one exception, where "already set by anyone" is the *expected*, silent no-op case, not a conflict). Backs up first (`path.bak-<YYYYMMDDHHmmss>`, matching the Python side's own convention exactly) whenever a write actually changes anything, skipped for a brand-new file. Like the Python side, this is line-based text editing only, never a TOML parse/rewrite (§5's table row above has the reasoning) — a table header is only ever recognized as a single whole line of the exact form `[dotted.path]`; `looksMalformed` (an unclosed triple-quoted string, or unbalanced `[`/`]` across the whole file) is a narrow, deliberately non-exhaustive sanity check, not a real parser, and blocks any write with a `warning` rather than risk editing something it doesn't understand.

`agent-sessions setup --remove` drops every line ending with that marker via the same plain line-based approach (§5's table row above), not a TOML parse/rewrite — nothing else is inferred, unlike the JSON-based `settings.json`/`keybindings.json` cleanup, which does drop an emptied container. That still comes out right for a table the plugin creates purely to hold its own keys (e.g. `[tui.keymap.composer]`, when it didn't already exist): its header line is marked too (`applyCodexConfig`'s own `upsertManagedKey`), so it's simply another line ending with the marker and is removed along with its keys; a table that already existed for any other reason (the user's own, or Codex's own) never has its header marked, so it's always left in place even if every key under it happened to be the plugin's — same "marked or not" rule either way, no special-casing needed (covered by a test). `--config-toml PATH` overrides the default path, matching `--settings`/`--keybindings`.

On startup, `reconcileSubmitKey(chatBindings, current)` compares the file's actual state (is Enter remapped to a newline or not) against the current setting (`enter` or not): if they agree, the setting is kept as-is (`shift+enter`/`ctrl+enter`/`alt+enter`/`cmd+enter` can't always be told apart just from a generic `meta+enter` write); if they disagree, the setting is re-derived with `deriveSubmitKey(chatBindings)` (`enter: chat:newline` plus whichever of `SUBMIT_KEYS`' literal names — `cmd+enter`/`ctrl+enter`/`shift+enter`/`alt+enter`, or `super+enter` as an alias for `cmd+enter` — is present with `chat:submit` wins, in that priority order; with none of those but `meta+enter: chat:submit` present, defaults to `alt+enter`, since Claude Code's own key-naming makes `meta` an alias for Alt/Option, never Cmd — `cmd`/`command`/`super`/`win` is the actual Command-key group, and per Claude Code's own docs most terminals don't even report it; no `enter` remap, or `enter: chat:submit` → `enter`). The settings tab re-reads `keybindings.json` every time it opens and offers to reconcile a mismatch. A missing file is treated as "submit"; malformed JSON shows "unreadable" and blocks changes.

Submit-key symbols (`⏎`/`⇧⏎`/`⌃⏎`/`⌥⏎`/`⌘⏎` on macOS, `keys.ts`'s `SUBMIT_KEY_SYMBOLS`) label the "Send" button (e.g. "Send (⌘⏎)") and the statusLine (§14); see below for non-macOS labels and symbols.

**The full combination table** (`test/terminal/keybindings.test.ts`'s "the submit-key combination table" pins every row below for Claude's `keybindings.json`; `resolveEnterAction × sendSequence` (`test/terminal/key-role.test.ts`) pins all 25 submit-key×keypress combinations for the PTY-bytes columns, which have no agent concept at all — same bytes for Claude and Codex). OpenCode has its own byte mapping (`agentSendSequence`, `test/terminal/key-role.test.ts`), so the PTY-bytes columns below don't apply to it. `submitKey` is a single, agent-global setting. Codex's `config.toml` columns don't vary by `submitKey` choice the way Claude's `keybindings.json` does — it's always the same fixed `alt-enter`/`["enter", "shift-enter"]` pair whenever `submitKey !== "enter"`, which is exactly why the PTY bytes column (driven by the plugin's own key interception, not by Codex's config) still varies per row the same way Claude's does; `test/terminal/codex-config.test.ts`'s "sendSequence × applyCodexConfig" cross-checks that the two stay consistent.

#### 7.2.1 Non-macOS key routing

`Platform.isMacOS` (from Obsidian) branches the whole terminal key-handling path. macOS is unchanged from the above.

On other platforms, Obsidian's own hotkey modifier is Ctrl rather than Cmd, and `claude` itself uses Ctrl+C/D/G/R/O/S/L/T and more (a requirement — every key Claude Code uses must reach the terminal). So Ctrl can't simply pass through to Obsidian the way Cmd does on macOS. `keys.ts`'s `classifyCtrlKeyNonMac(ev)` decides where a Ctrl-combination goes (called from `views/terminal.ts`'s `handleKey` only when `!Platform.isMacOS`). The default is **the terminal** (`claude` wins ties), with these exceptions:

| Key | Destination |
|---|---|
| Ctrl+Shift+C | Copies the terminal's selection (`terminal.getSelection()` → `navigator.clipboard.writeText`; does nothing if nothing is selected) — the convention Linux terminal apps use |
| Ctrl+Shift+V | Pastes the clipboard into the PTY (`navigator.clipboard.readText()` → `sendInput`), wrapped in a bracketed paste if `terminal.modes.bracketedPasteMode` is set (same reason as §6: avoid mis-triggering `/` completion) |
| Ctrl+Shift+=/−/0 | Font size (`TerminalView.zoomFont()`, the non-macOS equivalent of Cmd +/−/0) |
| Ctrl+Shift+W | Runs Obsidian's `workspace:close` (closes the tab) |
| Ctrl+Shift+P | Runs Obsidian's `command-palette:open` |
| Ctrl+Shift+<anything else> | Goes to Obsidian (the key event is passed through, not handled) |
| Ctrl+Tab, Ctrl+, | Goes to Obsidian (tab switching, settings — passing the event through is enough, since Obsidian's own default hotkeys already cover these) |
| Any other Ctrl+<key>, **including plain Ctrl+W and Ctrl+P** | Goes to the terminal |

"Goes to Obsidian" means xterm doesn't see it (the handler returns `false`), but `preventDefault`/`stopPropagation` aren't called — the same approach as macOS's Cmd-combinations, letting the native `keydown` reach Obsidian's own hotkey handling (which only does something for combinations Obsidian already binds by default, such as Ctrl+Tab and Ctrl+,). Copy, paste, font size, close-tab, and command-palette are handled directly, so those call `preventDefault`/`stopPropagation` and reach neither xterm nor Obsidian's native handling.

Ctrl+Shift+W and Ctrl+Shift+P exist specifically because plain Ctrl+W and Ctrl+P are reserved for the terminal: Claude Code's own input line uses Ctrl+W for "delete one word" and readline-style input can use Ctrl+P for history, so routing those to Obsidian's close-tab/command-palette would break them inside a session. `views/terminal.ts`'s `runObsidianCommand()` invokes `app.commands.executeCommandById()` (an internal Obsidian API not in its public types, cast the same way `main.ts` casts for `app.setting`) to run `workspace:close`/`command-palette:open` explicitly, since passing the raw key event through wouldn't trigger them — Obsidian's own default hotkeys for those actions are bound to the plain (non-Shift) combinations.

Right-click copy/paste (xterm.js's own `rightClickHandler`/`copyHandler`/`handlePasteEvent`, listening on the element's native `copy`/`paste`/`contextmenu` DOM events) needs no platform branch — it rides the browser's native clipboard events the same way on every platform.

### 7.2.2 Editor key

One setting, **editor key** (`ctrl+g` default, `ctrl+q`, `alt+g` — Option+G on macOS): the key that opens the agent's external editor, which `$VISUAL` points at the built-in editor pane (§7.4). `keys.ts` holds the mapping (`agentEditorKeyName`, `agentDefaultEditorKey`) and the dropdown labels (`editorKeyLabel`); the key is passed to the terminal unchanged (a plain Ctrl or Alt key event xterm turns into `\x07`, `\x11` or `ESC g`), and every agent is configured to open its editor on it. Each agent's own default for this action, and what the plugin writes when the choice differs:

| Agent | Own default | Written for another key | Key syntax |
|---|---|---|---|
| Claude Code | `chat:externalEditor` on `ctrl+g` and the chord `ctrl+x ctrl+e` | `Chat.<key>: chat:externalEditor` and `Chat.ctrl+g: null` in `keybindings.json` (`applyEditorKey`) | `ctrl+q`, `meta+g` |
| Codex | `tui.keymap.global.open_external_editor` = `ctrl-g` | `[tui.keymap.global] open_external_editor = "<key>"` in `config.toml`, marked as ours (`applyCodexConfig`) | `ctrl-q`, `alt-g` |
| OpenCode | `editor_open` = `<leader>e` (Ctrl+X, then E) | `keybinds.editor_open` in `tui.json`, for every choice including `ctrl+g` (`applyOpencodeTui`) | `ctrl+q`, `alt+g`, `ctrl+g` |

**Why these three keys.** A choice has to be free in all three agents and reach the PTY. Claude Code uses Ctrl+A/B/C/D/E/G/K/L/O/R/S/T/U/V/W/Y and Ctrl+X as a chord prefix; Codex's editor and main keymaps use Ctrl+A/B/C/D/E/F/G/H/J/K/L/M/N/O/P/R/S/T/U/V/W/X/Y and `Ctrl+/`; OpenCode's defaults use Ctrl+A/B/C/D/E/F/K/M/N/P/R/T/U/V/W/X (leader)/Z and Ctrl+G (`messages_first`). Codex refuses to start when `open_external_editor` collides with one of its own bindings (`Ambiguous tui.keymap.main bindings`: `ctrl-e` shadows `editor.move_line_end`), so a key is offered only when Codex accepts it. Ctrl+Q and Alt/Option+G collide with nothing in any of the three, and each opened `$VISUAL` in live runs of Claude Code 2.1.285, Codex 0.159.0 and OpenCode 1.18.33 (`ctrl+q`, `meta+g`/`alt-g`/`alt+g`, and `ctrl+g`). Ctrl+G reaches the terminal on non-macOS because the terminal view claims plain Ctrl keys ahead of Obsidian's hotkeys (`terminalClaimsKey`); Ctrl+Q takes the same path. Alt+G is not claimed; xterm sends `ESC g` for it (`macOptionIsMeta`), which Obsidian has no default hotkey for.

OpenCode's Ctrl+G is also its `messages_first`; with the prompt focused the editor opens and the transcript does not move, so that binding is left as it is.

The setting tab writes on change: a key other than Ctrl+G goes through a confirm dialog (`confirm.writeEditorKey.*`, naming Claude Code, Codex when enabled, and OpenCode when enabled), and returning to Ctrl+G removes the entries of Claude Code and Codex again. `applyEditorKey` follows the rules of `applySubmitKey`: only its own keys are added or removed, a key already holding another action is never overwritten (a `warning`, with Ctrl+G left bound so the editor stays reachable), and a `Chat` block that ends up empty is dropped; it shares the file with the submit key and neither undoes the other. Codex's editor line is removed when Codex is switched off (`applyCodexConfig(…, {statusLine: false})` removes every managed keymap line and writes no `status_line`); OpenCode's `tui.json` follows the same switch, and the sync also runs at startup, since the editor key is managed whenever OpenCode is enabled. `setup --remove` restores all three: `keybindings.py` removes the editor entries, `config_toml.py` drops every marked line, and `tui_config.py` puts back each key in the backup's `managed`.

### 7.3 Links, `@`, and jumping

- Links (`links.ts`): via `registerLinkProvider`. A line is scanned for `[\w./~\-]+(?:\.[A-Za-z0-9]+)(?::\d+(?::\d+)?)?` candidates (URLs are skipped); an absolute path inside the vault is made relative, a relative path is resolved against the session's `cwd` and then made vault-relative, and only paths that resolve to a real file (`vault.getAbstractFileByPath`) become links. Clicking opens the file (`openLinkText`) in the main area; a line number moves the cursor there.
- `@` insertion: the command "Agent Sessions: Insert current note as @" and the header's `@` button. `workspace.activeEditor` is `null` while the terminal has focus, so `main.ts` tracks the last `MarkdownView` that was in front via `active-leaf-change`, exposed as `lastMarkdownView()`. The path is relative to the session's `cwd` (absolute if outside it). A multi-line selection appends `#L{from}-{to}`. A path containing spaces is quoted. `@path ` is written to the PTY, and focus moves to the terminal.
- Jumping (`marks.ts`): every time `handleKey` intercepts an Enter that resolves to submit (including the unmodified case) and calls `sendSubmit()`, a prompt marker is recorded (`onData`'s own `\r` doesn't record one, to avoid double-counting a newline that includes `\x1b\r`). A response marker is recorded on the `idle → busy` transition from `registry` (including the case where the very first observation of a session's status is already `busy`), keeping only the most recent one. "Previous prompt" is the nearest marker above the current top of the visible screen; "next prompt" the nearest one below it; "last response" is the response marker. `scrollToLine(marker.line)` does the scrolling. Discarded markers are dropped.
- When `~/.claude/settings.json`'s `"tui"` is `"fullscreen"`, Claude Code redraws the whole screen itself and keeps its own scroll state — nothing accumulates in xterm's scrollback (`buffer.length === rows`). Marker-based jumping doesn't work in that mode, so the three jump buttons send Claude's own scroll keys (PageUp, PageDown, End) instead.

### 7.4 The built-in editor

Claude Code's editor key (Ctrl+G by default, §7.2.2) calls `$VISUAL` via `spawnSync(cmd, [...args, tmpfile], {stdio:'inherit'})`, waiting for it to exit and re-reading the file on exit code 0 (a non-zero exit or a signal shows "quit unexpectedly" and keeps the original content). An executable whose basename contains `code`, `cursor`, `windsurf`, `codium`, `subl`, `atom`, `gedit`, or `notepad` is treated as a GUI editor and Claude Code skips switching to the terminal's alternate screen buffer (`prepareTerminalForHandoff`). `/memory` uses the same path.

- `bin/agent-sessions-code` (`sh`; `exec "$(dirname "$0")/agent-sessions" edit "$@"`). `install.sh` symlinks it to `~/bin/agent-sessions-code`; its name contains `code` specifically to match the GUI-editor heuristic above. The plugin puts `VISUAL=<its absolute path>` into a session's `start` env (§4.3 — the path must contain no spaces).
- `agent-sessions edit FILE` (`agentsessions/cli/edit.py`) connects to `~/.agents/sessions/plugin.sock` and sends `{"op":"edit","file":FILE,"session":$AGENT_SESSIONS_ID,"cwd":…}`. `{"ok":true}` returns exit code 0; `{"ok":false,"error":"cancel"}` returns 1 (no editor opens; Claude keeps the original content). Any other outcome — `error` of `no-tab` or `busy`, a connection failure, or an unexpected EOF/`ECONNRESET` (including Obsidian crashing) — **falls back to a terminal editor**: `$AGENT_SESSIONS_FALLBACK_EDITOR`, or `vi` if unset, `execvp`'d in the same terminal. It waits indefinitely for a response (Ctrl+C/`SIGTERM` sends `{"op":"cancel"}` and exits 1).
- `edit-server.ts` listens on `~/.agents/sessions/plugin.sock` (unlinking a stale socket on `onload`, closing and unlinking on `onunload`, `chmod 0600` after creation). Frames reuse `daemon-client.ts`'s `encodeFrame`/`FrameDecoder` (`J` only). An `edit` request looks up the terminal view for `session`; none found returns `{"ok":false,"error":"no-tab"}`; otherwise `view.openEditor(file, cwd)` runs and the response reflects send/cancel, then the connection closes. A second `edit` request for a tab already mid-edit gets `{"ok":false,"error":"busy"}`. If the client disconnects first (Claude Code was interrupted), the edit pane closes. If **the tab** closes first (`onClose`, plugin `onunload`, or the socket closing), the original content is written back to the temp file and `cancel` is returned before closing — a single `pendingEdit` field on the view is the source of truth, and every closing path resolves it.
- `views/editor-pane.ts` splits the terminal view's body vertically (top: the rest of xterm; bottom: the edit area). Height is the `editorHeight` setting (default 40%, clamped 10–90%), yielding to the terminal's 8-line minimum; the edit area's own minimum is 4 lines plus its toolbar. Opening/closing re-runs `fit()`. The edit area is a `<textarea>` (native paste, IME, undo; minimal Markdown awareness). Font settings flow in the same way as the terminal (`applySettings(fontFamily, fontSize)`, called on every `settings-changed`), so changes apply live even with the editor open. `.agent-sessions-editor-text` defaults to a slightly looser `letter-spacing: var(--as-editor-letter-spacing, 0.03em)` and `line-height: var(--as-editor-line-height, 1.7)` than the terminal, for readability. Opening it loads the temp file's content, focuses it, and places the cursor at the end. A one-line toolbar shows the filename (basename), "Send (<submit-key symbol>)", and "Back to input (Esc)". Autosave is `autosave.ts`'s `SaveDebouncer` (`schedule`/`flush`/`cancel`, a plain class with no DOM or Obsidian dependency): after 800ms of no typing, it writes to a temp file and renames it into place (an `input` event mid-IME-composition doesn't call `onChanged()`; `compositionend` does, so a save never lands mid-conversion). "Send" and "Back to input" both `flush()` any pending timer and write immediately (a no-op if `text === lastSaved`). "Cancel" (the discard path) only `cancel()`s the timer — `original` is written back separately. A failed autosave write logs to `console.warn` rather than a `Notice`, since it can fire as often as every 800ms.
  - **Send**: in a Codex or OpenCode tab (whose editor key only opens the prompt), or when the temp file starts with `claude-prompt-` (a Claude prompt edit) (`submitsAfterEdit(file, agent)`), the final content is written and `ok` is returned, then (after a 300ms pause for Claude to read it back) `submitSequence()` is sent to the PTY. Other files (e.g. `/keybindings`) are written but not submitted.
  - **Back to input** (also Esc): writes the current content and returns `ok` without sending — Claude returns to the (non-empty, non-zero-exit) input line as usual.
  - Keys: the submit-key setting sends, any other Enter combination inserts a newline, `Esc` returns to input (or closes an open completion list first), and Tab / Shift+Tab indent / outdent by two spaces (`indent.ts`: with no selection Tab inserts two spaces at the cursor; otherwise every line the selection touches gains or loses up to two leading spaces, applied through `insertText` as one undo step). Mod+W (Obsidian's "Close current tab" — Cmd+W on macOS, Ctrl+W elsewhere) does nothing while the editor pane is open: the tab view's own `Scope` (active only while this tab is the active one) claims it with `isCloseTabKey` before Obsidian's hotkeys see it, so other tabs still close with it. IME composition (`isComposing`/`keyCode 229`) is ignored. Everything else is the textarea's normal behavior. `keydown` propagation is stopped (kept away from Obsidian's hotkeys; Cmd+V/C/X/Z/A stay native). While `pendingEdit` is set, the terminal's own `attachCustomKeyEventHandler` returns `false` for everything and `onData` is discarded (no keys reach the PTY).
  - `@` completion (`at-complete.ts`): the search term updates on non-composing `input` events and on `compositionend`. Typing `@` starts a search term that runs to the next space; a dropdown (up to 8 results) appears below the textarea. Candidates come from `app.vault.getFiles()` filtered with `prepareFuzzySearch`, shown as vault-relative paths. ↑↓ moves the selection, Enter/Tab confirms (replacing `@` through the search term with the vault-relative path from `cwd`, quoted if it contains spaces, plus a trailing space). Esc closes the list without ending the edit. Enter while the list is open confirms rather than submitting.
  - Bracketed paste doesn't apply here (pasting into a plain `<textarea>`).

### 7.5 Tab state and icons

View icons: `layout-dashboard` for the Session Manager, `list-tree` for the side panel (ribbon and sidebar tab). The terminal's icon (base form `square-terminal`) changes with state.

A pure function, `terminalStatus(input)` (`terminal-status.ts`), decides a single `TerminalStatus`:

| State | Condition | Icon | Group | Color / motion |
|---|---|---|---|---|
| connecting | Mid attach/start | `loader` | running | Muted, spinning |
| working | `registry` status is `busy` | `loader-circle` | running | Accent color, spinning |
| running-shell | `registry` status is `shell` (a tool is running a command) | `terminal` | running | Accent color, blinking (opacity) |
| asking | `registry` status is `waiting` (Claude Code's own value in `~/.claude/sessions/<pid>.json` — AskUserQuestion, a permission prompt, elicitation, a model-switch confirmation, or similar, waiting on a dialog) | `hand` | needs-input | Pink, pulsing (scale) |
| waiting | After `busy→idle`, before that tab has been brought to front (unrelated to Claude's own `waiting` status — the names just happen to collide) | `eye` | needs-review | Orange, pulsing (scale) |
| editing | The built-in editor is open | `pencil-line` | done | Blue |
| idle | Connected and idle (already seen) | `circle-check` | done | Normal |
| detached | The tab exists but isn't connected (after restore, before it's been brought to front) | `circle-dashed` | done | Muted |
| compacted | Just after `/compact` completes (manual or automatic), until a prompt the model answers — local commands in between (`/rename`, `/model`, `/effort`, `/reload-plugins`, `!` shell commands), an exit or a resume leave it set (below) | `archive-restore` | needs-review | Orange, static |
| exited | `claude` exited | `circle-stop` | done | Muted |
| error | Can't reach the daemon, `claude` missing, or start failed | `triangle-alert` | error | Red |

Priority order: error > exited > asking > editing > connecting > running-shell > working > waiting > compacted > detached > idle. Animated states (connecting, working, running-shell, asking, waiting) respect `prefers-reduced-motion`. The spin (connecting, working) is applied to the lucide `<svg>` itself, with `transform-box: fill-box; transform-origin: center` — not to the wrapping element the `agent-sessions-status-<status>` class is toggled on — so it rotates around the icon's own rendered center rather than a point the browser derives from the svg's viewBox coordinate space, which is visibly off-center otherwise.

**Groups** (`statusGroup(status, archived)`, `terminal-status.ts`): a coarser classification laid over the 11 fine statuses above, matching the buckets Claude's own app filters sessions by — `needs-input` (asking), `needs-review` (waiting, compacted), `running` (connecting, working, running-shell), `done` (idle, editing, detached, exited), and `error` (its own bucket — no filter of its own, see below). A `Row`'s `archived` flag overrides all of that: an archived session is always the `archived` group, regardless of its last-known status, shown with the `archive` icon in place of the status icon. The icon for each of the first four groups — a hand, an eye, a spinning arc, a checkmark — is literally that group's first-listed fine status's icon, since Claude's own app uses the same one. This grouping backs two things: the side panel's badge ("Needs input N · Needs review M", counting `needs-input`/`needs-review` — `attention.ts`'s `attentionCounts`/`urgencyByGroupKey`) and the manager's status-filter menu (below).

A tab's state lives in `plugin.terminalStatuses` (id → state); if several views share an id, the higher-priority one wins. Side-panel and manager rows use this same value when a tab exists, and otherwise the subset derivable from `Row` and `registry` (working/running-shell/asking/compacted/exited/idle/detached). A row's mark is the same icon (`TERMINAL_STATUS_ICON[status]`, `rowStatusMark`), the same shape, color, and motion as the tab (sharing the `agent-sessions-status-<status>` class), with a tooltip combining the group and fine status names (`statusTooltip`, e.g. "Done — Not connected"; `error` has no group label of its own, so its tooltip is just "Error"; an archived row's tooltip is just "Archived", since the icon already changed and the underlying status no longer matters). `asking`/`waiting` rows are additionally highlighted with a background (§8, §10.1).

`asking` is detected without a hook: Claude Code itself writes `status: "waiting"` plus a reason, `waitingFor` (e.g. `"input needed"`, `"permission prompt"`, `"dialog open"`), to `~/.claude/sessions/<pid>.json`. `registry.ts` watches this file and passes the raw value through untouched (`RegistryEntry.waitingFor`, `Row.waitingFor`; `waiting_for` in `json live`). The `Notification` hook (`notification_type` values like `permission_prompt`, `idle_prompt`, `elicitation_dialog`, `agent_needs_input`) is a one-shot event that would require reconstructing persistent state and risks being missed entirely, so it isn't used; `status: "waiting"` is itself persistent, so reading it is enough.

**Codex `working`/`asking`: read live from its own terminal title, not just the daemon's rollout-tail poll**. Codex has no per-process status file like Claude's; the daemon's own Codex adapter derives `registryStatus` by tailing the session's rollout file, which lags slightly behind whatever Codex is actually doing right now. Codex also writes its own live status directly into the terminal's OSC-0 title (`codex-rs/tui/src/terminal_title.rs`/`chatwidget/status_surfaces.rs`) — a braille spinner (`⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏`) while a turn is running, and a blinking `"[ ! ] Action Required"`/`"[ . ] Action Required"` prefix while blocked on user input (an approval prompt, elicitation, etc) — and `TerminalView` reads this back live via xterm's own `onTitleChange`, `classifyCodexTitleStatus` (`sessions/codex-title-status.ts`, a pure function: `"working"`/`"asking"`/`null`) feeding a `titleStatus` field into `terminalStatus()`'s `working`/`asking` checks (OR'd alongside the `registryStatus` ones — Claude never sets this field, so its own behavior is unaffected). This only works while the user's own `tui.terminal_title` config still includes Codex's `"activity"` item (its own built-in default does — unlike `composer.submit`/`editor.insert_newline`/`status_line` (below), this plugin deliberately never writes to `tui.terminal_title` itself: if a user has customized it away from the default, title-based detection just has nothing to work with and silently falls back to `registryStatus` alone, rather than the plugin reaching further into a setting it wasn't asked to manage); `classifyCodexTitleStatus` returns `null` (not `"idle"`) when neither marker is present, so `registryStatus` alone decides in that case. Both markers are Codex's own hardcoded English text/glyphs, not something this plugin controls, localizes, or can rely on staying the same forever — if a future Codex release changes them, classification just stops matching and title-based detection silently falls back to the rollout-based one, without breaking anything.

**OpenCode `working`/`asking`** come from the registry alone: `Registry` reads the status plugin's files (`~/.agents/sessions/opencode/<ses_id>.json`, §3.3) next to Claude's `~/.claude/sessions` ledger, watches both folders with `fs.watch`, and keys OpenCode's entries by `ses_…` — which is the tab's id once it is linked (§7.7). Tab icon, row marks, the attention badge, `waitFor`, and the `onIdle`/`onBusy` notifications therefore work for OpenCode exactly as for Claude, and `waiting` maps to `asking` the same way Claude's does. There is no terminal-title signal for OpenCode, and Codex keeps its title-based status.

**`/goal` mark (Claude Code only), beside the state mark, never instead of it.** Claude Code records a goal only in the transcript, as `attachment` lines of type `goal_status` (neither `~/.claude/sessions/<pid>.json` nor the statusLine JSON carries it): `/goal <condition>` appends `{met: false, sentinel: true, condition}` (re-sent unchanged on resume and after compaction); after each turn the goal's Stop-hook evaluator appends `{met: false, condition, reason}` (not yet) or `{met: true, condition, reason, iterations, durationMs, tokens}` (met — Claude Code then drops the goal), or `{met: false, failed: true, …}` when it judges the condition impossible; `/goal clear` (or `stop`/`off`/`reset`/`none`/`cancel`) appends `{met: true, sentinel: true, condition}`. The latest line decides, as in Claude Code itself; a new `/goal` simply comes after the old one. `json scan` folds these lines (`scan.py`'s `apply_goal_status`) into each session's `goal: {condition, met, reason, since, updated}` (+ `failed`), or `null` — read in the same `rg`/`grep` pass that already collects every transcript's `custom-title` lines (`scan_names_and_goals`; pattern `"attachment":{"type":"goal_status"`, which a quoted copy inside a tool result never matches since its quotes are escaped), so it costs no extra file reads and needs no cache of its own; the reason is cut to 1000 characters. Codex has its own `/goal` (in `~/.codex/goals_1.sqlite`'s `thread_goals`: `active`/`paused`/`blocked`/`usage_limited`/`budget_limited`/`complete`), not read yet; OpenCode has none. `sessions/goal.ts` (pure) gives the state (`active`/`met`/`failed`), icon (`target`/`trophy`/`flag-off`), class and tooltip (state, condition cut to 200 characters, the evaluator's reason to 280); `views/goal-render.ts` draws it after the name in side-panel rows (`renderRow`) and manager rows, and after the title in the terminal tab's header (`syncTabGoalMark`, from `TerminalView.updateIcon` and `refreshDeferredTerminalTabs` — an element of its own that Obsidian's header redraws leave alone). Colours: purple while active (no state uses it), green once met, faint once failed; only an active goal on a running session (`connecting`/`working`/`running-shell`) moves — a slow opacity breathe (`is-live`), off under `prefers-reduced-motion`. To show a change sooner than the 60-second scan, `SessionIndex` rescans a Claude session on `busy` while it has no active goal (the sentinel is written before the turn it starts) and on `idle` while it has one (the verdict is written before the turn ends) — `goalNeedsRescan`; `/goal clear` starts no turn, so it waits for the periodic scan.

`compacted` has no equivalent field in `~/.claude/sessions/<pid>.json`, so it's detected via a hook instead. `SessionStart` carries a `source` (`startup`/`resume`/`clear`/`compact`/`fork`); `compact` covers both a manual `/compact` and automatic context compaction. `PreCompact`, which fires before compaction starts, is one-shot and can't mark "done", so `SessionStart` with `source=compact` (fired once compaction has finished and the session has effectively resumed) is the "enter" signal instead. `agentsessions/claude/hooks.py`'s `_update_compacted(data)`, called from `record_hook`, creates `~/.agents/sessions/compacted/<session_id>.json` (temp file + rename) on `SessionStart`+`source=compact`, and deletes it on `UserPromptSubmit` (the next prompt) or `SessionEnd`. `setup` registers the `SessionStart` hook with matcher `compact` specifically so it doesn't fire on every unrelated startup. The plugin's `CompactedTracker` (`compacted.ts`, the same `fs.watch` + 200ms-debounce shape as `registry.ts`/`statusline.ts`) watches this directory and tracks only file existence, exposed as `has(id)`.

The marker alone loses the state whenever the process ends: a `/compact` sent to a session with no tab runs headless and finishes with `/exit` (§6), and a restart, an Obsidian restart or a resume all fire `SessionEnd`. So the transcript is the lasting record. `json scan` reports `after_compact` for a Claude session (`sessions/scan.py`'s `read_after_compact`, cached with the rest of a scan entry), walking back from the end of the transcript to its last `compact_boundary`: `"clean"` when only local commands and machine lines follow it — `system`/`local_command` lines, user lines opening with `<command-name>`, `<local-command-…>` or `<bash-…>`, `isMeta` lines, the compaction summary, titles and other bookkeeping; `"input"` when a user line reads as a prompt but the model hasn't answered; absent once an assistant line or a tool result follows (a reply, a slash command that runs a model turn such as a skill or `/review`, or automatic compaction in the middle of a turn), or with no compaction in the tail. The rule keys off Claude Code's own markers rather than a list of command names; `/btw` writes nothing to the transcript and so doesn't count either way. `Row.compacted` is `isCompacted(marker, after_compact, ctx)` (`compacted.ts`): the marker, or `"clean"`, or `"input"` while the statusLine's `context_window.used_percentage` reads 0 — no turn has filled the context since. A 0% reading on its own doesn't count: a resumed session reads 0% before its first turn whether or not it was ever compacted. `SessionIndex.isCompacted(id)` is what a tab reads (the row's value, or just the marker for a tab whose session has no row yet). The scan state refreshes on every `events.log` append for that session (the `SessionStart(compact)` and `UserPromptSubmit` hooks included) and on the 60-second rescan. Codex and OpenCode have no compacted state.

Since Obsidian 1.7, a tab never brought to front is a deferred view, so its icon and title come from whatever was last saved rather than being computed live. `refreshDeferredTerminalTabs()` (`main.ts`), run on `onLayoutReady`, `layout-change`, and any `index`/`registry` change, writes both `leaf.view.title` (a field `DeferredView` exposes) and the tab-header DOM (`.workspace-tab-header-inner-icon`, `.workspace-tab-header-inner-title`) directly. The icon is `rowTerminalStatus(row)`'s state icon (`detached` if there's no row), with the matching `agent-sessions-status-<status>` class and tooltip. The title is `sessionDisplayName` (`name.ts`, §11 — the same pure function `views/terminal.ts`'s `getDisplayText()` uses, so both agree on the rule), fed from the `Row` if there is one (name, label, and agent), or else the leaf's own persisted state for the agent (a deferred tab can exist with no `Row` at all yet).

### 7.6 One session, one tab, and splitting

`openSession(id)` (`open-session.ts`): looks through `workspace.getLeavesOfType('agent-sessions-terminal')` for a leaf whose `view.state.id === id`; if found, `revealLeaf`s it and stops. Otherwise it creates a leaf in the main area (`workspace.getLeaf('tab')`) and calls `setViewState`. A new Claude session follows the same path (writing `sessions.json`'s `sessions[id]` first, `id` the session's own persistent id from the very first scan) — a new session for any other agent opens the same way but under a daemon-only placeholder `id` (§7.7), since there's no flag letting the caller assign the real one up front. Concurrent calls for the same `id` are de-duplicated via `opening: Map<id, Promise<WorkspaceLeaf>>` — a call already in flight for that `id` returns the same promise.

"Split right"/"split down" (the `⋯` menu, `app.workspace.duplicateLeaf(leaf, 'vertical' | 'horizontal')`) and Obsidian's own "Duplicate tab"/"Open in new window" are allowed to create multiple views sharing an `id` — they bypass `openSession` (`TerminalView.setState` doesn't self-close in this case). Each view attaches independently (the daemon's minimum-size rule still applies across them) and detaches independently when closed. A normal open via `openSession` always moves to the existing tab instead, so it never creates a duplicate on its own.

### 7.7 Multi-agent: Claude Code, Codex, and OpenCode

The plugin can launch any of three CLI agents as a tab's PTY — `settings.ts`'s `AgentId` (`"claude" | "codex" | "opencode"`), the plugin-side half of §3.3's Python adapter split. `AgentSessionsSettings.agents: Record<AgentId, {enabled, path, env}>` — per agent, whether it's offered at all, its executable path (empty = auto-detect), and `KEY=VALUE` environment variables (one per line, `settings.ts`'s `parseEnvLines`) merged into the launched process's env. OpenCode's entry also has `launchVia` (`"opencode"`, the default, or `"ollama"`) and `ollamaModel`. At least one agent is always enabled — the settings tab's toggle refuses to turn off the last one (`notice.needsOneAgentEnabled`).

**Auto-detection** (`backend.ts`'s `detectAgent`/`locateBinary`), per agent, in order (on Windows `locateWindowsProgram` instead, §19.1): (1) the login shell's `command -v <bin>` (`$SHELL -l -c`); (2) the same probe in an *interactive* shell (`$SHELL -i -c`, `execInteractive`) — a version manager (mise, etc.) whose shell integration is wired into `.zshrc`/`.bashrc` rather than a profile file only shows up on `PATH` there, since a login-but-non-interactive invocation never sources it; the probe's own output is wrapped between two unique markers (an interactive shell can print prompts/banners ahead of it) and only the text between them is trusted, with a 3-second timeout guarding against a hung rc file; (3) `commonBinDirs`' fixed locations, first executable match wins — mise's shims, its per-version node installs newest-first (`sortVersionsDesc`; a node-managed tool like Codex's `codex.js` lives under `installs/node/<version>/bin/`), asdf's shims, volta, nvm's per-version installs newest-first, `~/.local/bin`, OpenCode's own `~/.opencode/bin`, `/opt/homebrew/bin` on macOS, `/usr/local/bin`, and npm's own `npm config get prefix`/bin. `commonBinDirs` itself is pure (the caller gathers the version-directory listings and `npm config get prefix`'s output first). `detectAgents` (plural) just runs `detectAgent` for every `AgentId` in turn — used only for the very first run, when saved settings have no `agents` object at all (`main.ts`'s `needsAgentDetection`, checked against the *raw* loaded data before `mergeSettings` fills in defaults); it enables whichever it finds, and none found leaves Claude enabled. Each agent's settings block (see §15) has its own "Find again" button, which only calls `detectAgent` for that one agent (not both — a click on Codex's button has no reason to also re-probe Claude's binary) and shows the result inline, along with `<bin> --version` (`agentVersion`, best-effort, `null` shown as nothing); unlike the first-run case it never flips a toggle on its own, but if it finds a still-disabled agent, it shows an inline "Enable" button next to the result — a user with settings already saved (so the first-run auto-enable in `autoDetectAgentsOnFirstRun` never runs for them) needs some way to turn on an agent installed after the fact without hunting for the toggle above.

**`withBinDirOnPath`** (`backend.ts`): prepends the resolved binary's own directory onto the launched process's `PATH`, applied at every launch site (`terminal.ts`'s `startSession`, `main.ts`'s `sendHeadless`) regardless of how the binary was found. A version-manager-resolved binary is often a `#!/usr/bin/env node` script (Codex's `codex.js`) rather than a real executable — without its own directory on `PATH`, the spawned process's `env node` lookup can fail if node isn't already reachable through whatever `PATH` it inherits (mise's shims resolve the right node version internally, but still need their own directory reachable at all to run in the first place). Harmless for a real binary too.

**Env passed to Python**: `backend.ts`'s `agentEnvFor(settings)` computes `AGENT_SESSIONS_AGENTS` (every enabled agent, comma-separated — §3.3's `enabled_agents()` reads this) and, if Codex's own env setting has `CODEX_HOME` / `CODEX_SQLITE_HOME` lines, those too (`agentsessions/agents/codex/rollout.py`'s `codex_home()` reads it straight from the process env on every call, no caching). It also carries OpenCode's `XDG_DATA_HOME`/`XDG_CONFIG_HOME`/`OPENCODE_DB`/`OPENCODE_DISABLE_CHANNEL_DB` — from OpenCode's own env setting, else from the login shell's environment (`loginEnv`, the environment a session launches with; read once, asynchronously, so the first calls after startup go without it) — because OpenCode locates its database and plugin folder by them and the Python side (`agents/opencode/db.py`, `setup.py`) must look in the same places. `installOpencodePlugin` passes the same variables to `setup`. `setAgentEnv(vars)` stores this at module level, read implicitly by `envWithVault` (the same pattern `i18n.ts`'s `setLang`/`t()` uses) — called once from `onload` and again from `syncUiState` (so it's always current after a settings change), rather than threading a parameter through every `scan`/`live`/`detail`/`usage`/`stats`/`resolve` call site.

**`ui.json`**: `writeUiState` (`backend/ui-state.ts`) now also takes the enabled agent list and writes it as `agents: string[]` — the fallback `enabled_agents()` (§3.3) uses outside a plugin-launched terminal (the TUI, a bare CLI invocation), where `AGENT_SESSIONS_AGENTS` isn't set.

**New-session dialog**: `NewSessionModal` shows an agent picker only when more than one agent is enabled (with exactly one, that one is used without asking); it defaults to `settings.lastNewSessionAgent`, which is overwritten with whatever was actually chosen. `main.ts`'s `newSession(name?, agent = settings.lastNewSessionAgent)` threads the choice through to `sessions.json` and `openSession`. The picker is icon+label buttons, not a native `<select>` — an `<option>` can't hold an icon, and the picker's whole point is to show each agent's own mark (§7.7's "Display").

**Launch argv** (`backend.ts`'s `buildAgentArgv(agent, bin, id, fresh, opencodeLaunch?, codexNoDaemon?, name?)`): Claude's is `--session-id id` fresh, plus `--name=NAME` for a session named at creation (one argument, so a name starting with `-` stays a value), and `--resume id` otherwise. Codex has no flag letting the caller assign a *new* session's own id (`codex` takes none; `codex resume [SESSION_ID]`/`codex fork [SESSION_ID]` both only accept an *existing* one) — so a fresh Codex launch is just `[bin]`, and Codex decides its own new thread id once it starts; resuming an existing (already-known, e.g. from a scanned row) id is `[bin, "resume", id]`. OpenCode is the same: a fresh launch is `[bin]`, a resume is `[bin, "--session", id]`. Codex gets `--no-daemon` right after the binary whenever its `--help` lists that flag (`codexNoDaemon`, asked once per binary and cached; `launch.codex_no_daemon` for `agent-sessions new`; an older Codex without the flag starts without it). Without it Codex's TUI attaches to a shared background app-server that the first Codex tab starts as its own child, with that tab's environment: a later tab's TUI still has its own `VISUAL` (the editor runs in the TUI), but the commands its model runs see the first tab's `AGENT_SESSIONS_ID`. With the flag each tab's Codex runs its own server in its own PTY. With OpenCode's `launchVia` set to `"ollama"`, `main.ts`'s `launchArgv` builds `[ollama, "launch", "opencode", "--model", M, "-y", "--", …]` followed by the same tail (`--session id` when resuming), with `ollama` found like any other binary (`locateProgram("ollama")`). An empty `ollamaModel` is refused with a `Notice` and an error in the tab, since `ollama launch` would otherwise open its own model picker inside the terminal. The settings tab fills the model dropdown from `ollama list` (`listOllamaModels`) and also accepts free text.

**New-Codex/OpenCode-session id resolution — the two-id architecture** (`views/terminal.ts`'s `TerminalView.daemonId`/`relinkId`, `main.ts`'s `resolveAgentSession`/`linkAgentSession`, `backend.ts`'s `resolve`): since a Codex or OpenCode session's real id isn't known until it exists, a `TerminalView` tracks two ids — `id` (row matching, `sendCommand` route 1, the saved workspace layout — the tab's *display* identity) and `daemonId` (every daemon-protocol call: `start`/`attach`/`resize`/`forget`, and matching the daemon's own `list`/`exit` data — the PTY's *tracking* identity). The two coincide always for Claude, and for a not-yet-linked Codex or OpenCode session; they diverge once such a session resolves.

`newSession` for Codex or OpenCode opens the tab under a plugin-generated placeholder id — both `id` and `daemonId` start out equal to it — and kicks off `resolveAgentSession(agent, placeholderId, cwd)` in the background: finds the placeholder daemon session's own pid (polling `client.list()`, since `start`'s own promise doesn't guarantee the daemon call has completed; up to `RESOLVE_PID_ATTEMPTS`), then polls `agent-sessions json resolve <agent> --pid PID --since EPOCH --cwd CWD` (§3.3 documents the strategies Python tries for each agent) until it returns a real thread id — `{thread: null, transcript: null}`, not an error, means "not yet" and the caller retries. Codex doesn't create its rollout file until the first turn completes, which can be well after the tab opens (OpenCode's session row appears at TUI launch, so its resolve normally succeeds at once), so this second stage isn't bounded by an attempt count — it keeps retrying (`RESOLVE_POLL_MS` apart) for as long as the session is wanted: its tab is open (`findTerminalView(placeholderId)`) or its daemon session is still running (`client.list()`, checked each iteration); a session left idle for a while before its first message still gets linked once one is sent, and once the tab is closed and the daemon session has ended nothing is left to link.

The same flow serves sessions without a tab. After every live refresh `SessionIndex` hands the daemon's session list to `adoptOrphanSessions`, which starts `trackNewAgentSession` (at most one resolver per daemon id, `unresolvedIds`; `since` = the daemon session's `startedAt`) for each running Codex/OpenCode session that `sessions.json` does not link (no entry with that `daemon`), that is not itself a known session id (a session resumed under its real id), and that no resolver has yet (`sessions/orphans.ts`'s `orphanDaemonSessions`). This is how a session started by `agent-sessions new` without `--prompt` (§5.1) gets its real id after its first message. `linkAgentSession` takes the name from `pendingNames`, else `pendingRenames[daemonId]` (§3.2), else the entry's own.

Once resolved: `linkAgentSession(agent, thread, cwd, placeholderId)` writes `sessions.json`'s `sessions[thread] = {agent, cwd, daemon: placeholderId}` (keeping any `name` the entry already has) (`types.ts`'s `StoreSessionEntry.daemon`) and rescans — Python's `json live`/`json scan` do the id-relabeling from there (§3.3's `_daemon_list`), so the row appears under `thread` like any other session. Then every open tab still at `placeholderId` (normally one, but a split can make several) has `relinkId(thread)` called on it: `id` becomes `thread` (`daemonId` is untouched — the daemon has no rename op, so the PTY keeps answering to the placeholder for its whole life), the tab's name/icon refresh, `requestSaveLayout()` persists it, and `main.ts`'s `refreshTerminalStatus` runs for both the old and new id (moving the `terminalStatuses` entry across). From this point on `id` is the real id everywhere, including `findTerminalView`'s "one session, one tab" matching (§6, §7.6).

A brand-new Codex session named at creation gets `/rename` typed into its composer as soon as that is on screen and empty, and the name is checked again once the tab is linked; a brand-new OpenCode session keeps the name in memory until the id is known (§6). Either way the tab title and the side panel's stand-in row show it from the start. "Start fresh" on the exit screen of a Codex or OpenCode tab gives the tab a new placeholder id and starts `resolveAgentSession` for it (before `start`, so the "created since" time precedes the launch); the old `ses_…` stays linked to nothing. `main.ts`'s `daemonIdFor(id)` is the reverse lookup `sendCommand`'s routes 2/3 use (§6) — `sessions.json`'s `daemon` field on `id`'s own entry, falling back to `id` unchanged for everything else (Claude, or a Codex or OpenCode session not yet linked).

**A Claude tab whose session id changes** (`sessions/successor.ts`, `main.ts`'s `linkSuccessors`): the tab starts Claude Code with `--session-id <id>`, and two things move the running session to another id. (1) Claude Code re-executes itself right after launch (the one-time auto mode acknowledgement, the first run after a login): a child process writes its ledger record under an id of its own. `planSuccessors` pairs that record with the tab, by its parent pid being the tab's daemon child, or by folder and start time within two minutes when only one tab could be its origin. (2) `/clear`, and `/resume` typed in the tab, keep the process and switch it to another id: the ledger record of the tab's own pid (`DaemonSession.pid`) names an id the tab doesn't have (`planInPlace`, which skips an id another tab or daemon session holds). Either way `linkAgentSession("claude", newId, cwd, daemonId)` writes the link and the tab is swapped over (`relinkTerminalViews`). A re-exec also gets `registry.setAlias(old, new)` for callers still holding the old id; an in-place switch does not, since the old id remains a session of its own with its row and transcript. `linkSuccessors` runs on every ledger change and every live refresh, and finds a linked tab's daemon session under either of its ids (`json live` lists it under the linked id).

**`/clear` in a Claude tab**: Claude Code ends the session (`SessionEnd`, `reason: "clear"`) and starts a new one in the same process (`SessionStart`, `source: "clear"`). The new session gets the old one's name (its transcript starts with the same `custom-title`), and the ledger record keeps the process's start time. `agent-sessions hook` writes the `reason` into `events.log`; `SessionIndex.checkEventsLog` reports such an id (`onCleared`). `matchClear` pairs that report with the tab that moved from the same id in place, whichever comes first, and drops either half left unpaired for a minute (a `/clear` outside the plugin's tabs, a `/resume`). For a pair, `finishClear` archives the old session (the same entry the row menu's Archive writes) and, when it had a name, renames the new one with `/rename` (`renameSession`, so Claude Code and Remote Control get it too) once it is idle: `clearedName` gives `<name> 2`, or the number after the counter the name already ends in, ` 2` to ` 99` (`Cat: Foo 2` → `Cat: Foo 3`; `Plan 2026` → `Plan 2026 2`, a year or a version being part of the name), skipping numbers other sessions already have. An unnamed session stays unnamed and its old part is archived the same way. Codex and OpenCode start a new session in a running process with `/new`; the plugin does not follow that: their tab stays on the session it was linked to.

**Resuming after the daemon itself restarts** (`TerminalView.startSession`): if a linked Codex or OpenCode tab's `daemonId` is no longer in the daemon's `list` (the daemon process restarted — a plugin-only reload doesn't lose it, since the external daemon process and its PTYs outlive that), `ensureAttached` calls `startSession(client, fresh=false)`, which resumes by `id` (the permanent thread / session id — `buildAgentArgv`'s `codex resume <id>` or `opencode --session <id>`) but mints a *fresh* `daemonId` (`crypto.randomUUID()`) for the new `start` call, since the daemon has no rename op and the old `daemonId` no longer names anything. `linkAgentSession(agent, id, cwd, newDaemonId)` overwrites the link so out-of-tab lookups (`daemonIdFor`) keep finding it. Claude never takes this branch — its `id` *is* the daemon id, permanently, by construction.

**Submit key and command sending per agent** (§6, §7.2): Enter interception applies to every agent's tabs. `keybindings.json` and Ctrl+S (`chat:stash`) are Claude Code mechanics; Codex has its own `config.toml` keymap; OpenCode's `tui.json` is managed while OpenCode is enabled (below). `commandChunks` sends `submitSequence(settings, agent)` after the command for Claude and Codex, and Ctrl+S only for Claude; OpenCode's commands always end in `\r`, because the slash popup runs the highlighted command on `\r` in both modes (`\n` leaves the popup open). Bracketed paste is kept for every agent (a standard terminal convention, not Claude-specific). OpenCode's `/compact` and `/exit` are sent the same way, except that a bare command gets no trailing space (Claude's completion-list workaround, §6): `/compact ` with the space is sent to the model as plain text.

**OpenCode's submit and editor keys** (`terminal/opencode-tui.ts`, `syncOpencodeTui`): `keybinds.editor_open` carries the editor key (§7.2.2) whenever OpenCode is enabled. With the submit key on Enter the submit keys are not managed. With any other key, `keybinds.input_submit` is `linefeed,ctrl+j` (`linefeed` is the name OpenTUI gives 0x0a; `ctrl+j` alone does not submit) and `keybinds.input_newline` is `return,shift+return,ctrl+return,alt+return` minus the submit key's own name, in `$XDG_CONFIG_HOME/opencode/tui.json` (the XDG_CONFIG_HOME OpenCode runs with, as for its status plugin). Popup and dialog selection is not governed by these two keys, so `\r` still selects there. Only those keys and the status line's `plugin` entry (§14.1) are touched; the file is parsed and re-serialized as plain JSON with its indentation kept, and a file that isn't plain JSON (comments, trailing commas) is never written — a notice asks the user to set the keys by hand. The user's previous values go to `~/.agents/sessions/opencode-tui-backup.json`, per key (`managed` lists the keys held now); going back to Enter releases the submit pair, and switching OpenCode off or Remove releases everything, putting the previous values back (deleting a key that didn't exist, the `plugin` entry and, when it is left empty, the `plugin` array, and the `keybinds` object or file when the plugin created it) and leaving any key the user has changed since. The sync runs at startup, when OpenCode is switched on or off, when the submit key or the editor key changes (the confirmation dialogs name OpenCode when it is enabled), and after an install or program update.

**The built-in editor** (§7.4) needs no agent branch: `VISUAL` is set the same way in every agent's launch env (`main.ts`'s `editorEnv`; OpenCode gets the same shim in `EDITOR` too — it reads `$VISUAL` first, then `$EDITOR`; its editor key is set in its `tui.json`, §7.2.2, so an OpenCode tab sends the same key as any other), and `bin/agent-sessions-code`/`edit-server.ts`/`editor-pane.ts` have no Claude-specific logic — the `edit` request carries `AGENT_SESSIONS_ID`, which is the daemon's id for the session — for a linked Codex or OpenCode tab that is the placeholder, not the tab's own `ses_…` id, so `handleEdit` matches a tab by either (`tabOwnsEditSession`). Each agent's editor key invokes `$VISUAL`: Claude Code 2.1.285, Codex 0.159.0 and OpenCode 1.18.33 each ran the shim on the editor key in a live run. Codex hands the shim a file `.codex/editor/.tmp*.md` under its working directory (on Windows under `CODEX_HOME`, `%USERPROFILE%\.codex\editor\`), so `submitsAfterEdit` (`claude-prompt-*` files, and OpenCode's always) does not submit after "Send" for it.

**Display**: an agent mark (§8, §10.1; `rows.ts`'s `AGENT_ICON`/`AGENT_NAME_KEY`/`renderAgentMark`) sits next to the state mark on every row, and the detail pane's badge row (§9) leads with the same icon and name. The icon is each agent's own mark (`ui/icons.ts`'s `registerAgentIcons`/`AGENT_ICON_ID` — Claude's, Codex's, and OpenCode's SVGs from [lobehub/lobe-icons](https://github.com/lobehub/lobe-icons), MIT, see `THIRD_PARTY_NOTICES.md`) — single-color (`fill="currentColor"`), matching every other icon in the plugin, rather than the brand-colored variant lobehub also offers; both source SVGs already share a `0 0 24 24` viewBox, so no size/position normalization is needed. `registerAgentIcons()` is called once from `onload()` (idempotent) before anything renders. Sessions from every enabled agent are listed, sorted, grouped, and filtered together, with no agent-specific split — the manager's status-filter menu (§10.1) is deliberately agent-blind for the same reason.

**Not applied to the terminal tab's own icon** (no agent icon on the tab): the tab header has exactly one icon slot, showing the session's live status (§7.5's `TERMINAL_STATUS_ICON`, driven by `updateIcon()`/`headerIconEl()`).

**Model/effort without Claude's statusLine data**: the plugin reads model and effort only from Claude Code's statusLine (§14; Codex's own `status_line` and OpenCode's status line row (§14.1) are drawn inside those TUIs and report nothing back), so the detail pane's model/effort badges (§9) and the manager's model/effort columns (§10.1) fall back once `statusInfo` (Claude's live statusLine data) has nothing. Two fallback sources, both additive, non-Claude fields — present only for an adapter that populates them, absent (not `null`) otherwise (OpenCode fills `model` only) — read in this order: the session's own `row.model`/`.effort` first (`json scan`'s fields, from the rollout's most recent `turn_context` — already loaded with the rest of the row, no extra fetch, so it's there the instant the detail pane or manager table renders), then `json detail`'s own `model`/`effort` (§9's `Detail` type, a separate per-session fetch that may not have resolved yet) as a last resort. The manager's per-row columns only have the first of these available (there's no per-row `json detail` fetch in a list of many rows), so `row.model`/`.effort` is what actually closes the gap there.

**What isn't implemented yet**: Codex's `/compact` wording (OpenCode has `/compact` and `/exit` but no `/rename`, §6), and whether Codex accepts it via the same bracketed-paste-plus-submit send path Claude uses, haven't been confirmed hands-on (it's sent the same way regardless, on the working assumption that it is a standard slash command and bracketed paste is a terminal-level convention, not Claude-specific). `/rename` is confirmed on codex-cli 0.160.1 through that path, before the first message included (§6). `codex-rs`'s rollout JSONL schema has changed before (§3.3) and could again. A manager-toolbar agent filter (one entry per agent) was considered and deliberately not added — see "Display" above.

## 8. The side panel (`agent-sessions-side`)

The right sidebar, always present. Four areas laid out as a CSS grid (`auto 1fr <detailHeight> auto`), top to bottom:

1. **Nav row**: `+` (new-session dialog), `layout-grid` (opens the Session Manager in the main area, or reveals it if already open), `⋯` (rescan, open settings). No session-level actions live here.
2. **List** (`views/side-list.ts`; sections have headings, empty sections are omitted):
   - **Open tabs**: sessions with a terminal tab, in tab order. A tab whose session has no row yet — a new session before its first message, or a Codex/OpenCode tab still under its placeholder id (§7.7) — is listed too, once the first scan is in, with a stand-in row (`side-list.ts`'s `tabOnlyRow`: the tab's id, agent and folder, the name it was given (`plugin.pendingName`), no time, `Row.tabOnly`); its menu has Rename and End session only (`row-menu.ts`). The real row takes over under the same id once the scan has it (the tab's own id is the real one after `relinkId`), so the row keeps its place and never shows twice. A tab of a disabled agent gets none. The frontmost tab's row is highlighted (a bold name, a background — `--background-modifier-active-hover`, a 10%-`--interactive-accent` tint that reads on both themes — and a left accent bar; bold alone is too easy to miss). When that row is also asking/waiting (§7.5), the asking/waiting background and left border (a stronger, urgency-colored signal) take priority over the frontmost styling's own — declared later in `styles.css`, so the cascade picks them — and frontness instead shows as a thin accent ring around the whole row (`box-shadow: inset`, which doesn't compete with either state's own left border), so neither is lost when both apply at once. The manager's own "selected" row (§10.1) gets the same background/ring treatment, on its `<td>`s rather than the `<tr>` (a `<tr>`'s own background/border don't reliably paint under `border-collapse: collapse`, the same reason its asking/waiting rows are `<td>`-scoped).

**`frontId` is re-derived live, never a cached snapshot.** Reading `activeLeaf.getViewState().state.id` once, at the moment a tab becomes the active leaf, and caching it as `frontId` would be correct for Claude, whose session id is fixed from the moment the tab opens, but wrong for Codex: `relinkId` (§7.7) swaps a Codex tab's id from its daemon-tracked placeholder to the real, resolved thread id *while that tab is already in front*, and no new `active-leaf-change` event fires to catch it — a cached snapshot would keep pointing at an id no row is ever filed under again, so the row would never get `is-front`. `refreshFrontId()` reads a live `TerminalView.sessionId` getter instead (a plain getter over the view's current `id` field, so it's always correct regardless of whether `relinkId` has run since) — called from `active-leaf-change`, at the top of every `render()` (covers "relinked while already front", since `relinkId` triggers a `render()` via `refreshTerminalStatus`'s `terminal-status` event), and once more from `onLayoutReady` (covers the case where, right after a reload, the workspace layout may not have settled yet by the time `onOpen()` itself runs).

**Reads `getMostRecentLeaf(rootSplit)`, not `workspace.activeLeaf`**: `activeLeaf` is deprecated in Obsidian's own API ("especially without checking whether `activeLeaf` is null"), and right after a reload, or whenever focus is genuinely in the side panel itself (e.g. clicking a row), it can be the side panel's own leaf or `null` — neither a `TerminalView`, so `frontId` would not be set at all in that case. `getMostRecentLeaf(root)` — Obsidian's own doc comment: "the most recently active leaf in a given workspace root ... useful for interacting with the leaf in the root split while a sidebar leaf might be active" — tracks the last real content-area tab regardless of where focus currently is; passing `rootSplit` excludes both the side panel and any pop-out window, matching "the frontmost *tab*" as this feature actually means it. The fallback rule itself (`nextFrontId(previousFrontId, activeSessionId)`, `views/rows.ts`, pure and tested — `side.ts` itself imports `obsidian` eagerly and can't be): the most-recently-active root-split leaf's session id wins when it's one of this plugin's terminal tabs, otherwise `frontId` is left as whatever it last was (e.g. every terminal tab has been closed — the side panel keeps highlighting the last real frontmost terminal tab rather than losing track of it).

Clicking brings that tab to front. The heading carries a badge with "Needs input N" and "Needs review M" items (`attentionCounts`; "needs input" = the `needs-input` group (asking), "needs review" = the `needs-review` group (waiting or compacted) — §7.5; each omitted at zero), and clicking either item opens nothing: it flashes that group's rows in the list twice in the item's color (`is-highlight-asking`/`is-highlight-waiting`, an inset shadow over the row's own background; rows carry `data-session-id`) and scrolls the first of them into view. The counts are computed across all three sections together (`attentionCounts(source, [...openTabs, ...running, ...recent])`).
   - **Running**: sessions the daemon holds with no open tab. Clicking opens an attached tab.
   - **Recent**: everything else, most-recently-updated first, up to a setting (default 10). Archived sessions and nameless child sessions are excluded. Clicking opens a `--resume` tab.
   - Row layout: state mark (§7.5's icon/color/motion) + agent mark (§7.7 — which CLI agent, no brand logos) + category chip (if any, §11) + name without the category + last-updated + `▣` if a tab exists + `⋯` (always shown). All three sections share this layout. An asking row gets a pale pink background, a 3px left color bar, and a bold name; a waiting row gets a weaker orange background (no bar, not bold). Last-updated is relative — "just now" / "N min ago" / "N h ago" / "yesterday" / "N d ago", and a locale-formatted short date (no time of day, year included once it's not the current one — `formatDateShort`) from a week on — with the absolute date and time (`formatDateTimeShort`, also locale-formatted — dateStyle/timeStyle "short", year dropped for the current year) in a tooltip; it re-renders once a minute in place (without rebuilding the row). The name column has a `min-width` and never shrinks past it — since it's the only thing on the row that identifies the session, everything else yields first: last-updated hides via a container query once the side panel itself gets narrow, and the other elements (state mark, chip, `⋯`) are already fixed/minimal width.
   - `⋯` opens the row menu: Rename, Move to category (§11, disabled without a name or an auto-derived label to attach one to), Suggest name and category… (§11, Organize for this one session), Compress (disabled right after a compaction, until the next instruction), Archive ⇄ Unarchive, Restart session (running sessions with a real conversation id only — a Codex/OpenCode placeholder is disabled; asks first when the status is working or running-shell — `sessions/restart.ts`'s `restartDecision`; `kill` as for End session, wait until the daemon lists it as exited, then an open tab resumes in place through its own Resume path (`TerminalView.resumeAfterEnd` → `restart(false)`, which also re-links a Codex/OpenCode tab to the new daemon id), or, with no tab, `forget` and open it like a recent session — the same real conversation id either way; picks up changed settings, hooks, skills or environment), End session (running sessions only; `kill` goes to the daemon's own id for the session — the id itself when the daemon lists it, else the `sessions.json` link — and the daemon's list is re-read every second, up to 12 s, until the session shows as exited, so the row leaves Running without a rescan; a tab whose process exits re-reads it too), Session analysis, Copy ID (`views/rows.ts`'s `showRowMenu`). Right-click opens the same menu. Clicking, `⋯`, or right-clicking also selects that row (highlight only).
3. **Detail pane** (`views/detail.ts`, §9): a 4px drag handle sits between it and the list above (`mousedown`→`mousemove` updates `sideDetailHeight`, `mouseup` saves it; default 220px, minimum 80px).
4. **Rate limits** (`views/limits.ts`): a group of rows per enabled agent, each with a small agent icon at its head (`AGENT_ICON_ID`), a usage-percentage bar, and the countdown to reset — `h:mm:ss`, or "N days h:mm" past 24 hours, with no "resets in" label — refreshed every second. `resetsAt` missing shows "—". **Every row shares one set of columns** (agent icon, label, bar, %, countdown), via CSS subgrid: the whole area (`.agent-sessions-limits`) is the actual grid (`grid-template-columns: auto auto 1fr 3em 6.5em`); the per-agent wrapper (`agentWrapEls`, existing purely for `LimitsView`'s own bookkeeping) is `display: contents` so it contributes nothing to layout, and every row (`.agent-sessions-limits-row`) is itself `grid-template-columns: subgrid; grid-column: 1 / -1`, so its children lay out against the *host's* column tracks rather than a fresh set sized to that one row alone. If each row were its own independent grid, a row with a wider label (e.g. "30-day window") would start its bar further right than a shorter-labeled row above or below it. With the subgrid, every row's bar starts and ends at the same x position regardless of how many rows there are, which agent they belong to, or how wide any one row's own label happens to be — the label column is sized once, across the whole area. A little top margin marks the first row of a second-or-later agent group (`isGroupStartRow(agentIndex, rowIndexWithinAgent)`, applied to that row itself, since the `display: contents` agent wrapper has no box of its own for a margin). **The label is always the compact form** ("5h"/"7d"/"30d" — `windowShortLabel`, `manager-model.ts`, same length-based derivation as `windowLabel`, `.short`-suffixed i18n keys): the side panel is narrow enough that the long form ("5-hour window") is never worth showing there, unlike the manager's own wider stat cards, which use it. The long form is in each row's own tooltip (`setTooltip`). **Two different sources, both converted to the same internal `RateLimitWindow` shape** (`{usedPercentage, resetsAt}`) so every row renders through the identical `renderAgentWindow`: Claude always gets exactly two rows (5h/7d), reading the most recently modified `status/*.json` file that carries `rate_limits` (account-wide, written in real time by its own statusLine hook; this assumes one account isn't used concurrently from two places). Every other enabled agent that has usage windows (Codex; OpenCode has none, so it contributes no rows, no group, and with OpenCode as the only enabled agent the whole area is hidden — `agentsWithLimits`) instead polls `agent-sessions json stats`'s `agents.<agent>.windows` (§10.2's same per-agent, not-just-5h/7d shape) every 60 seconds, converted via `fromStatsWindow` (`w.end` doubles as `resetsAt` — the Python side computes it as that exact value, including the same roll-forward rule the client-side `rollForwardWindow` below also applies, so no separate field or conversion is needed). **Row count is dynamic for a non-Claude agent**: one row per window it actually has a tracked percentage for (`realWindows(windows)` — `orderedWindows(...).filter(w => w.used_percentage !== null)`, a pure function, tested against a free-plan Codex account's fixture — `five_hour`/`seven_day` both present but `used_percentage: null`, plus a real `window_43200m`), labeled via `windowLabel(minutes)` — the usual 5h/7d pair, a single non-standard window (a 30-day-only plan is a confirmed real case), more than two, or none at all for that agent (nothing shown, rather than a permanently dashed-out placeholder row; there is no separate "cost only, no bar" row layout for this rare case). Either way, if the window's reset time has passed but a fresh value hasn't arrived yet, `rollForwardWindow` (the same rule as §10.2's pure function) advances it so "the current window" is what's shown; since the redraw happens every second and re-evaluates `Date.now()` each time, the display flips over naturally the instant the reset time passes. Clicking the area re-reads/re-fetches every shown agent's source immediately rather than waiting for the next automatic refresh (rapid clicks collapse into one, with a brief dimmed/`cursor: progress` state) — for Claude this doesn't make fresher `rate_limits` values appear, since those are only ever as current as the last time its own statusLine hook wrote them (it just re-reads whatever is already on disk), but for a `json stats`-sourced agent it's a real re-fetch. **A used-up window reads 100%** with a red bar, and the percentage's tooltip says when it ran out (`exhaustedText`, §10.2). A `json stats`-sourced row gets this straight from `fromStatsWindow`. Claude's status file can't say it (its reading stays just below 100% once the limit is hit, §13.2), so while either Claude reading is at 90% or more (`claudeNearLimit`, `CLAUDE_NEAR_LIMIT_PCT`) Claude joins the 60-second `json stats` poll, and `withExhaustion` lifts a live window to 100% when the matching `json stats` window (its `end` within a minute of the live `resetsAt`) is `exhausted`; below that threshold no extra fetch runs. The shown agent set (`refreshAgents`, called from `SideView`'s existing `settings-changed` handler) is rebuilt whenever the enabled-agent set changes, without needing a full side-panel reload.

The side panel subscribes to `workspace`'s `layout-change`/`active-leaf-change`, and to `registry`/`SessionIndex` changes, to re-render.

**Empty state**: when the list has nothing in any of the three sections, `renderEmptyState` shows a centered wordmark ("Agent Sessions", not localized — a product name), a one-line description (`empty.desc`), and a "New session" button (`mod-cta`, the same action as the nav's `+`) in place of the (otherwise blank) list. `empty.desc` and the two settings-fallback messages below are action-oriented rather than just descriptive, and name the agent(s) the reader can actually act on via a shared `{agents}` placeholder — filled in by `rows.ts`'s `enabledAgentsText(ids)` (one name as is, two as "A or B" via `common.agentsEither`, three as "A, B, or C" via `common.agentsSeparator`/`common.agentsEitherLast`). If no agent is enabled, the button is a "Open settings" one instead (`empty.noAgentEnabled`, naming every agent since none are enabled yet to narrow it down) — there's nothing to launch. If at least one is enabled, the "New session" button shows first and a background check (`resolveAgentBinary` against every enabled agent, via `Promise.allSettled`) swaps it for the same settings fallback (`empty.noAgentFound`, naming the enabled-but-not-found agent(s) specifically) if none of them can actually be found — never awaited inline, so it never delays the rest of `render()`. The rate-limit bars (item 4 above) are a separate, independent DOM area (`limitsHostEl`, built once in `buildSkeleton`) and are shown regardless of whether the list is empty, as long as there's `rate_limits` data on disk to show.

**Hover-to-detail, and reverting without a flash**: hovering a row for 300ms (`rows.ts`'s `HOVER_DELAY_MS`) swaps the detail pane to that session (`onHoverShow`); leaving it schedules a revert back to the default (the frontmost tab, or the top of the list — `showDefaultDetail`) rather than reverting immediately. The revert is wired to `listEl`'s own `pointerleave`, not any individual row's — a `pointerleave` on the list container only fires when the pointer actually leaves the whole list's rendered bounds, never when moving between its children (row to row, into a group heading, through the gap between sections), so moving the pointer directly from one row to another never triggers a revert at all; the previously-hovered row's detail simply stays shown until the new one's own 300ms confirms and replaces it. On top of that structural guarantee, the revert itself is also delayed (`HOVER_HIDE_DELAY_MS`, 200ms, via a small reusable `DelayedRevert` class — `schedule()`/`cancel()`/`pending`, no DOM or `obsidian` dependency, so it's directly testable with fake timers, unlike `SideView` itself) and canceled by `RowActions.cancelHideDetail`, called from every row's own `pointerenter` before its confirm timer starts — insurance against a leave/enter landing right on the boundary between the list and a row just inside it. (A per-row `pointerleave` that reverted immediately would flash back to the default detail for the ~300ms gap until the next row's hover confirmed, on every row-to-row transition.) `renderDetailFor`'s own async `json detail` fetch is guarded against a stale result landing after a newer request (`this.detailId` reassigned before awaiting; the result is discarded if it no longer matches by the time the fetch resolves). The manager has no equivalent: hovering there calls `selectById` directly (`createRowActions`'s `onShowDetail`, with no `onHideDetail` at all), which changes the table's own selection/detail permanently rather than reverting on leave, so there's nothing to flash back to in the first place.

## 9. The detail view (shared component)

`views/detail.ts` is used by both the side panel and the Session Manager. For a given `Row` (or the frontmost tab's session if none is given):

- A small category chip above the name (if any, §11's colors); the `<h4>` shows only the name, without the category (`categoryAndLabel(row)`, a pure function that splits `row.name` via `splitName`).
- Badges: agent (§7.7's display name — "Claude Code"/"Codex"/"OpenCode"), model, effort (from `statusInfo` — Claude's own live statusLine data — falling back to `row.model`/`.effort` then `json detail`'s `model`/`effort` for an agent whose status line the plugin doesn't read, "Default" if none has a value; see §7.7's fallback-order paragraph), and rc (a green ● when connected, ○ otherwise or unknown — the same look as §10.1's rc chip). The model badge shows Claude's `statusInfo.model` as-is, but a Codex fallback value (a raw model id, e.g. `"gpt-5.6-luna"`) through `shortModelName`/`codexShortModelName` (§10.1) instead, with the raw id in a tooltip — otherwise it would read as an id, not a name. OpenCode's `provider/model` value (e.g. `ollama/gpt-oss:20b`) is shown as is.
- A context-usage donut (SVG, `ctxPercent`). If `row.compacted` (§7.5) is true, a small "Compacted" label appears next to it (`.agent-sessions-detail-compacted`), indicating the context was just reset.
- The `/goal` card when the session has one (`renderGoal`, §7.5): the goal mark and state, when it was set, the condition, and the evaluator's latest reason (clamped to 6 and 3 lines; click to expand), with a left edge in the state's colour.
- Total tokens and cost: from `json usage`, cached for 60 seconds (`totalTokens` = input + output + cache-read + cache-create; `formatCost` = `$x.xx`).
- The most recent prompt and response (cards, `-webkit-line-clamp: 6`, click to expand), plus recent tools, folder, and ID.

Hovering a row for 300ms also fetches `json detail` (cached) and shows the same content.

## 10. The Session Manager (`agent-sessions-manager`)

The main-area tab, and the default view for a new tab. Opening it never starts a session — **only choosing "New" or clicking a row does.** The manager is the **usage-analysis** view; the side panel is the **current-work** view — a deliberate split of roles.

`buildSkeleton()` builds two stacked sections: **top** (toolbar + body — `.agent-sessions-manager-body`, the table plus the right-hand detail pane, filling the remaining height), **bottom** (analysis — `.agent-sessions-manager-analysis`, §10.3).

### 10.1 The tree, listing, Other, and Archive

The tree order is "groups (headings, foldable) → Other (heading, foldable) → Archive (heading, shown only when the toolbar's "Show archive" is on, always expanded)". Groups are ordered by their most-recently-updated session. Folded state persists in `sessions.json`'s `folded` (expanded by default) (`tree.ts`/`views/manager-model.ts`'s `flattenTree`). Within each section, rows are ordered by last-updated.

- Groups correspond to category names (the part of `splitName` before the colon in `Category: Name`). A group heading is a caret + category chip (§11) + count + that section's combined 5h/7d cost (`categoryTotals`, column-aligned). A real category's heading shows only its chip — never the category name a second time as plain text, since the chip already carries it.
- Named sessions with no category, and sessions with neither a name nor (per `json scan`'s) `child` set, are combined into one "Other" section (`OTHER_GROUP`, the literal persisted string `"その他のセッション"`, shown to users as `t("group.other")`), interleaved by last-updated. Nameless child sessions never appear here either. Every section heading row gets a 4px (`--size-4-1`) top border in the background color, so it never runs into the previous section's last row visually. The fold identifier is `OTHER_GROUP`; a `folded` entry of `__no_category__` (`tree.ts`'s `LEGACY_NO_CATEGORY_GROUP`) also counts as folded.
- Rows inside a group or Other have no chip of their own — the heading already carries the color.
- Sorting by clicking the 5h/7d column headers flattens the tree (no more grouping), and only then does each row carry its own chip, since it's the only remaining color cue.

A group or Other heading gets an urgency mark — the higher-priority of needs-input/needs-review (asking; waiting or compacted — see §7.5's groups), if either is present anywhere inside it (even folded) — via `urgencyByGroupKey` (`attention.ts`) → `renderGroupUrgencyMark`. The Archive section isn't counted.

Row columns: state mark (§7.5, same icon/color/motion as the tab) · name (agent mark, §7.7, then chip + name, per the rules above) · last-updated · model · effort · 5h cost · 7d cost · folder · `⋯`. Last-updated is the same relative text as the side panel's row (§8 — "just now" / "N min ago" / "N h ago" / "yesterday" / "N d ago", a locale-formatted short date from a week on; `views/rows.ts`'s `formatRelativeTime`), with the absolute date and time in a tooltip (`formatTime`, also `views/rows.ts` — delegates to `i18n/datetime.ts`'s `formatDateTimeShort`) and re-rendered in place once a minute, via the same `RelativeTimeTicker` (`rows.ts`) the side panel uses — one shared timer/tracking mechanism, not two. Sorting by last-updated still orders by the underlying epoch (`row.last_activity`), unaffected by how it's displayed. Model and effort come from `statusInfo` (Claude's live statusLine), falling back to `row.model`/`.effort` (Codex — see §7.7's fallback-order paragraph) when there's no statusLine at all; both show a short form with the full value in a tooltip — `shortModelName(model, agent)` dispatches to `codexShortModelName` for a Codex row (a raw model id like `"gpt-5.6-luna"` needs an actual transform to read as a name, e.g. `"GPT-5.6 Luna"` — splits on `-`, uppercases a short (≤3 char) first segment as a brand-style prefix, keeps a digit-leading segment hyphen-joined as a version number, and Title Cases anything else, space-joined) or just drops a trailing `(...)` for Claude's own display name; unknown values are blank. Row height is at least 32px. Columns are `table-layout: fixed` (mark 24px, last-updated 120px, model 100px, effort 88px, 5h/7d 72px each, folder 160px, `⋯` 28px, name takes the rest) — model/effort/folder are sized so their header text and typical values ("Opus 5.5"/"Sonnet 5", "medium"/"xhigh", a folder name like "project-notes-2026") never clip, so nothing overlaps regardless of the table's overall width; last-updated's 120px is generous enough for the relative text's longest values ("59 min ago", "23 時間前") and the "Last updated"/"最終更新" header in a proportional font (its font size stays the table's own, rather than the side panel's smaller row font, so it doesn't look out of place next to model/effort/folder). At narrower widths, container queries hide folder (<673px) → effort (<623px) → model (<573px) → 5h (<533px), in that order. Clicking a column header sorts (last-updated = the default grouped tree; 5h/7d cost = a flattened list sorted by that cost, descending). Asking/waiting rows get the same background/bar treatment as §8.

Toolbar: `+`, "Rescan" (`rotate-cw`), a name filter, a status-filter button (`filter`, accented while a specific filter — anything but "all" — is active), `⋯` ("Show archive" checkbox). Clicking a row opens it (`openSession(id)`, jumping to an existing tab if one exists). ↑↓ moves the row selection, Enter opens, `/` focuses the filter. A row's `⋯` and right-click open the same row menu as the side panel (`showRowMenu`, §8). The right-hand detail pane is `views/detail.ts` (§9) itself.

The status-filter button opens a menu of `MANAGER_STATUS_FILTERS` — "all" plus every group except `error` (`needs-input`, `needs-review`, `running`, `done`, `archived`), each with that group's icon (§7.5), checked on the current selection (`AgentSessionsSettings.managerStatusFilter`, persisted, default `all`). `matchesStatusFilter(row, status, filter, showArchived)` (`views/manager-model.ts`) decides what shows: `archived` matches only archived rows (regardless of status); every other specific filter matches a non-archived row whose `statusGroup` is that filter (so an `error` row never shows under any specific filter, only under "all"); `all` matches every non-archived row, plus archived ones too when the `⋯` menu's "Show archive" is on — the same toggle `flattenTree`'s `showArchived` already used, now folded into this one function instead of a second, separate rule. The filter narrows the row list before `buildManagerTree` runs, so group headings, their 5h/7d totals, and their urgency marks all reflect only what's currently shown. There's deliberately no separate agent filter alongside this one — sorting, grouping, and this status filter are all agent-blind by design (§7.7), and the row's agent mark already makes an agent's sessions identifiable at a glance without needing to hide the others.

Rescan triggers: opening the view, the Rescan button, an `events.log` append (rescanning just that ID via `--only`), a change under `~/.claude/sessions/` (status updates only, no scan), and every 60 seconds while the view is visible. The side panel shares the same scan results (`main.ts` holds one `SessionIndex`, and both views subscribe to it).

### 10.2 Analysis: stat cards and the category bars

**Independent sibling panels, not sub-sections of one "Analysis"**: the analysis area is built as one panel per enabled agent that has usage windows (`buildAnalysisSections`, `agentsWithLimits` — OpenCode has none, so it gets no panel, and with OpenCode as the only enabled agent the area is hidden) — each with its own row of stat cards on top and its own per-category horizontal bars below. With 0 or 1 agent enabled, it's a single, headingless panel inside the whole-area "Analysis" header/fold (`buildAnalysisHeader`, §10.3). **With more than one agent enabled, there's no single "Analysis" wrapper at all** — the whole-area header is hidden (`.agent-sessions-manager-analysis.is-split`, toggled by `buildAnalysisSections` itself) and each agent instead gets its own independent, top-level heading — "Claude Code analysis"/"Codex analysis"/"OpenCode analysis" (`manager.analysis.titleFor`, icon + §7.7's `AGENT_ICON_ID`) — arranged as CSS grid siblings (`.agent-sessions-manager-analysis-panels`), **always stacked, one column, regardless of width** (only the top-level agent panels stack unconditionally like this — the per-category bars and stat cards *inside* each panel still go side by side when there's room), a plain horizontal border between panels. The panels pack at the top of the area (`align-content: start`): when they're shorter than the area — every panel folded down to its heading, say — the leftover height stays below the last panel instead of being shared out between the grid rows, which would open a gap under each heading. The resize handle and click-to-refresh (below) still apply to the *whole* area regardless of split, since per-panel folding and the whole-area height/refresh are orthogonal concerns.

**Each panel folds independently**: clicking a heading toggles just that panel (`toggleAgentFolded`/`applyAgentFolded`, `▾`/`▸`, `stopPropagation`'d so it doesn't also trigger the analysis body's click-to-refresh), saved per-agent to `managerAnalysisFolded: Record<AgentId, boolean>` (defensively merged like `agents`, so a malformed or missing entry falls back to unfolded rather than discarding the whole saved object) — independent of `managerAnalysisCollapsed`, which only applies to the single-panel (0/1-agent) case, forced `false` while split (so a `true` saved while only one agent was enabled can't hide the panels). Only built at all when there's more than one panel (a single panel has no heading of its own to fold — it uses the whole-area header instead). A folded panel shows only its heading, plus a small usage percentage to its right (`updateAgentSummary`) — that agent's shortest real window (`realWindows(windowsForAgent(stats, agent))[0]`, `views/limits.ts`; e.g. 5-hour for Claude, or whichever non-standard window an account with no 5h/7d quota does track), blank if nothing is tracked yet for that agent. `windowsForAgent(stats, agent)` (`views/manager-model.ts`) resolves each panel's data: `stats.agents[agent].windows` (the identical `StatsWindows` shape as the legacy top-level `windows`, but scoped to that one agent) if present, falling back to the top-level `windows` only for Claude (for a Python build that has no `agents` key). A panel's category bars count only that agent's own sessions (`row.agent === agent`); the table above the analysis area stays one combined, agent-mixed list either way (§10.1's tree isn't split — only the analysis is). Every row's own 5h/7d cost cells, and the sort-by-cost table order, resolve through `sessionCostForRow(stats, row, window)`, so a mixed-agent table still attributes each row's cost to the right agent's data rather than assuming everything is Claude's.

**Not just a fixed 5-hour/7-day pair**: `StatsWindows` (`types.ts`) is a plain string-keyed map — always has `five_hour`/`seven_day` (present even when `used_percentage` is `null`, i.e. not tracked for that agent), plus zero or more additional real windows an agent reports, each keyed `window_<minutes>m` (Codex's confirmed real case: a 30-day-only plan with no 5h/7d tracking at all). Every entry — including the two fixed ones — carries its own length (`minutes`). `windowLabel(minutes)` derives a card's heading purely from the length (`300`/`10080` read "5-hour window"/"7-day window"; another day-aligned or hour-aligned length becomes "N-day window"/"N-hour window"; anything else falls back to "N-minute window" — computed on the plugin side rather than trusting Python's `label_key` hint to match a pre-registered i18n key for a length neither side anticipated). The pace line (`weeklyPace`) renders for every card, not just a fixed 7-day one — the projection starts as soon as usage reaches 1% (`MIN_PACE_USED_PCT`), independent of the window's length and elapsed time, so every window kind is treated alike.

**Claude vs. everyone else, which windows actually get a card**: Claude's panel always draws its 5-hour/7-day pair, one stat card and one category bar per entry actually present in `windowsForAgent`'s result (`orderedWindows(windows)`, sorted by `minutes` ascending) — before `stats` has resolved at all, the two well-known windows show as "—" placeholders. Every other agent's panel instead only draws a card for a window it actually has a tracked percentage for (`realWindows`, `views/limits.ts` — the same rule the side panel's own rate-limit bars use), so a Codex account tracking only a 30-day window gets no 5-hour/7-day placeholder cards that would read as if those windows were real and still loading. OpenCode never has a window, so it has no panel at all. When a non-Claude agent has no real window yet, its stat-card area shows one line, `stats.noUsageYet` ("No usage data for this window yet."), instead of any cards; its category-bar area below stays empty (no redundant second copy of the same message).

The analysis area is a row of stat cards on top, per-category horizontal bars below (one per window shown above them, same left-to-right order). Clicking anywhere in the area (other than a category bar row, which scrolls instead — see below) re-fetches `agent-sessions json stats` immediately rather than waiting for the next scheduled fetch (rapid clicks collapse into one, with a `cursor: progress`/dimmed state while the request is in flight). Same trade-off as the side panel's rate-limit view: this re-fetches the aggregation, not the underlying `rate_limits`/transcript data, which only change when claude itself writes new data.

**Stat cards**: one per window shown (§10.2 above). Each heading is followed by "resets in …" (a countdown). The top row is a usage-percentage bar; below it, a 2×2 labeled mini-table — "Cost $1,256.47", "Tokens 31.5M", "Calls 1,420", "Sessions 12" (light labels, bold values), each with a tooltip (e.g. tokens = input + output + cache-read + cache-create, for that window). **Cost and call/session counts are comma-grouped at 1,000 and above** (`usage.ts`'s `formatCost`/`formatNumber`, `Intl.NumberFormat` in the plugin's own display language — never a fixed locale); token counts stay abbreviated (`formatK`, "31.5M") since that's already a distinct, deliberate notation, not a plain count. Numbers come from `agent-sessions json stats` (§13.2). If a window's reset time has passed but a fresh `rate_limits` snapshot hasn't arrived yet, Python's `_roll_forward` (§13.2) has already advanced it to "the current window" server-side, so the card always shows the current one (a rolled-forward window shows "—" for usage percentage, since it isn't known).

**Pace projection**: one line under each card's usage bar (`renderPaceLine`), shown for every window (not just a fixed 7-day one). The pure function `weeklyPace(usedPct, start, end, now, windowCost)` (`views/manager-model.ts`) computes elapsed fraction `e` (how far into the window "now" is) and projects `usedPct / e`. A projection ≤100 shows "On track — about N% by the end of the window at this pace" (green). Above 100, it shows the time it would run out at this pace (`start + elapsed × 100 / usedPct`, `formatExhaustTime` — just the time when the exhaustion date is today, "tomorrow <time>" when it's tomorrow, otherwise "<weekday> <time>" via `formatWeekdayTime`, each in the locale's own hour cycle) and the margin to reset (`formatBeforeReset` — "At this pace you'll run out Tue 2:00 PM (2d 3h before reset)"; switches granularity by magnitude — days+hours at a day or more, hours+minutes under a day, minutes alone under an hour, "just before reset" under a minute — and omits a zero unit at whichever granularity applies, rather than a fixed two-unit template that could read "0 days 0 hours before reset"), plus a second line with a target for the remaining time ("Stay under Z% per remaining day (about $W/day)" — percentage only if cost can't be computed), in orange. For a window whose own length is a day or less (the 5-hour window), this second line switches its unit to "per remaining hour" instead (`weeklyPace`'s `guideUnit`) — "per remaining day" isn't a meaningful budget when the window itself never holds a full day. Missing `used_percentage` shows "Usage isn't known"; under 1% used (or effectively no time elapsed) shows "Under 1% used, so there is too little to project from" (too small a sample), both in a muted color. A tooltip carries the elapsed and used percentages.

**A used-up window**: when `json stats` marks a window `exhausted` (§13.2), the card reads 100% (`displayedUsedPct` — at least 100, since the vendor's own reading stays just below it), its bar turns red, and the pace line gives way to when it ran out (`exhaustedText`, red): "Used up 3:26 PM (2h 12m before reset)" / 「15:26 に枠を使い切りました（リセットの 2 時間 12 分前）」. The time is `exhausted_at`, formatted by `formatPastTime` (just the time today, "yesterday <time>", otherwise "<weekday> <time>"); the distance is `end − exhausted_at` through the same `formatBeforeReset` as the projection. With `exhausted_at` unknown the line is just "Used up". A folded panel's summary percentage follows the same rule.

**Per-category bars**: one per window shown above (a fixed 5-hour/7-day pair only for Claude; nothing at all for a non-Claude agent's panel with no real window yet, see above) — each a horizontal bar per category, the top 8 by cost (any session with no category, named or not, is folded into one "Other" bar via `categoryKeyOf`; values are $, comma-grouped at 1,000+, and percentage of that window's total). A real category's fill uses its chip's hue; "Other" is gray (`.is-neutral`). A category at $0 is omitted; if everything is $0, that bar shows "No usage in this window" — the bars are independent, so one can be empty while another isn't (e.g. nothing ran in the last 5 hours but the 7-day window has history). Clicking a bar scrolls to and expands that group (its own click handler stops propagation, so it doesn't also trigger the analysis area's click-to-refresh). Every bar calls the same pure function, `categoryTotals(rows, stats, window)` (`views/manager-model.ts`), once per window. Laid out side by side (`grid-template-columns: repeat(auto-fit, minmax(260px, 1fr))`, no container query needed) when there's room at a readable width, and stacked — in the same order as the stat cards above — when there isn't; a vertical divider between adjacent ones only appears when they're actually side by side (gated by a container query on the wrapper, not the individual bars' widths).

### 10.3 Layout, folding, and resizing

The analysis area's own heading (caret + "Analysis") toggles folding — only visible/meaningful with 0 or 1 agent enabled (§10.2's `is-split`; hidden entirely once there's more than one, since each sibling panel folds on its own instead). A drag handle, matching §8's detail-pane handle, sits between the table and analysis areas (minimum height 120px) and always resizes the *whole* area, split or not. Folded state (`managerAnalysisCollapsed`, single-panel case only) and height (`managerAnalysisHeight`, default 240px, always) persist in settings and survive a skeleton rebuild (e.g. a language switch). The handle is hidden only while the single-panel case is folded — always visible while split, since there's no whole-area fold to hide it for there.

### 10.4 The activity calendar (`agent-sessions-activity`)

Sessions' working time as a calendar (`views/activity.ts`; the pure parts in `views/activity-model.ts`). It opens from the Session Manager's toolbar (calendar icon), the side panel's ⋯ menu, and the command "Open activity calendar" (`openActivityTab`, one tab: an open one is brought to front).

- **Period modes** (a segmented toggle labelled "7d / Week / Day" (ja "7日枠"); the choice is saved as `activityMode`, default `session`): *session* (the "7d" window) is the 7 × 24 h period ending at a reset of the usage limit's 7-day window; *week* is Sunday 00:00 to the next Sunday 00:00 (local); *day* is one local day. `periodContaining(mode, at, resetAnchor)` gives the period holding `at`; `shiftPeriod` steps by 7 days (session, week) or one day. The session anchor comes from `json stats` (`pickResetAnchor`): Claude Code's 7-day window when Claude is enabled and the window is tracked (`used_percentage` not null, otherwise `end` is only "now"), else Codex's weekly window, else none, and with none a *session* period is a *week* (`effectiveMode`). Session periods step in absolute 7-day seconds, so they follow the reset exactly; week and day periods are built from local calendar days (`new Date(y, m, d + n)`), never 86400-second steps, so a daylight-saving period still starts at local midnight.
- **No future**: "next" is disabled once the period holds now (`canGoNext`); "Latest" returns to the period holding now.
- **Data layer** (`views/activity-data.ts`, apart from the view): the view asks the program for `json activity --raw` (§13.4: the unjoined runs and turns) and keeps the result in an in-memory `ActivityStore`, **per local day**. Everything drawn is computed from the store by pure functions: `joinRuns` (the same join as the program's `join_turns`, with the chosen gap and the one-minute minimum), `clipSpans` (to the period: a 7d window, a week, or a day), then the view's own filtering (listed sessions, agents on/off, title filter), cards, and day-mode columns. So changing the join gap, the mode, the agent switches, or the filter never calls the program: it recomputes from the store (`SessionsMemo` keeps the blocks per store version, gap and period, so toggling back and forth is a lookup) and redraws with the scroll position kept. `ActivityLoader.load(days, now, mode)` is the only place that calls the program, and only for the days `ActivityStore.plan` says are due, one call per run of consecutive days: `missing` (not loaded; days that haven't started are never asked for) when moving to another period, `open` (also days loaded before they ended, i.e. today or a day fetched part-way, which can have grown) for the automatic reloads, `all` for the reload button. Moving to a period with some days loaded draws those at once and fetches the rest. A run that crossed midnight sits in two days' entries and is merged once (`rawFor`, the longer copy); the latest copy of a turn wins. The plugin's join is tested against the program's own on a generated fixture (`test/fixtures/make-activity-fixture.py`) for 30 min, 1 h and 2 h. **Staying current** (the period reloads in place when the view becomes the active leaf again, 3 s after a session goes idle, and every 60 s while the period contains now; a hidden view never reloads; a failed background reload changes nothing) keeps working through the loader. The open details panel follows each reload: the block is found again among the recomputed blocks (`rematchSpan`: same session, the span overlapping the old one the most, ties to the closest start) and only its panel is redrawn (scroll position and unfolded responses kept; the session panel below is left alone).
- **Grid**: one column per local day the period touches (`periodDays`): seven for a week, one for a day, eight for a session period that starts mid-day (the part of the first and last day outside the period is dimmed). Each day is split into one lane per enabled agent (plus any other agent present in the data); in *day* mode there is one column per session instead (`dayColumns`: the sessions active that day, grouped by agent in lane order, then in session order; each column headed by the agent icon and the session name; the grid scrolls sideways when there are many). Each span is cut at local midnights into per-day pieces (`splitSpansByDay`) positioned by seconds since that day's midnight on a fixed 0–24 h axis (40 px per hour). **Session order**: every session has one fixed place in the left-to-right order (`compareSessions`): by `first`, when the session first worked at all (§13.4, not the first block of the period or the day; `buildSessions` takes the earliest run loaded when the program gives none), ties by id. Nothing the view changes (period, mode, join gap, agent switches, title filter) moves it, so two sessions side by side are in the same order in every hour, every day, every period, and in day mode's columns. Within a lane, overlapping pieces go side by side in that order: `layoutOverlaps` takes the pieces in session order and puts each in the leftmost column right of every overlapping piece placed before it; chains of overlapping pieces form clusters, and every piece of a cluster shares the cluster's widest column count, while a piece with nothing beside it is full width. A session's column can differ between clusters (it goes as far left as the order allows), but an earlier session is never right of a later one beside it. Keeping the order costs a column where sessions overlap in a staggered chain (A beside B, then B beside C needs three columns where packing by start time needs two); one fixed column per session for the whole day would keep blocks in place but makes most blocks a fraction of the lane even when nothing else runs beside them. A piece shows its label when `fitsLabel` says it is tall enough (and the cluster is at most three wide). Clicking a day header's date (a day that has started) switches to *day* mode on that date. Every block is drawn at least 6 px or 10 minutes tall, whichever is longer (`minBlockSeconds`); `expandForMinHeight` extends the drawn end (the true times stay on the span and in the tooltip) and the overlap layout runs on the extended pieces, so one-minute blocks never collapse and never hide each other.
- **Color**: a block takes its session's category color (the same palette slot as the category chip, `SessionIndex.categoryColorIndex`); without a category it takes its agent's lane color. Light and dark come from Obsidian's CSS variables plus a lightness switch under `.theme-light`.
- **Which sessions**: the same set the Session Manager lists, from one rule (`listedInManager`, `sessions/listing.ts`, also used by the manager tree, its per-category totals, and the side panel's recent list): an archived session is left out (the calendar has no Show archived switch), and so is an unnamed child session (started by another session: a sub-agent, `claude -p`, a Codex companion task); a child the user named stays. The index row decides; until the index knows a session, the `name` and `child` in the activity data stand in. A session's own sub-agent transcripts (`<id>/subagents/`) are not separate sessions: they stay part of that session's blocks. The cards' hours, counts and concurrency, the day counts, and the agent toggles follow the filtered set; the calendar redraws when the listed set changes (archiving, naming).
- **Header and now line**: no subtitle; the title carries an ⓘ icon whose tooltip explains a block (input to the agent's last output, plus sub-agent time, turns less than the chosen gap apart joined, local time). When the period holds now, a thin accent line (`placeNowLine`, position from the pure `nowLinePosition`) crosses today's column (the whole session-column row in Day mode) at the current local time, with a time label at the axis; the minute timer repositions it from the clock, never refetching, and a past period has none.
- **Cards**: per agent, hours (the union of all its spans, so overlapping sessions count once), the number of sessions, and the highest number of spans open at the same moment (`unionSeconds`, `maxConcurrency`). The title filter (name, label, category, id) applies to the cards, the day counts, and the grid alike.
- **Join gap**: a segmented control (30 min / 1 h / 2 h, saved as `activityGapMinutes`, default 30); the join happens in the plugin from the stored runs, so a change is instant (no request, no spinner, the scroll position and the open block stay). The silence rule inside a turn (30 minutes) is fixed (§13.4).
- **Agent switches**: each agent's summary card is its show/hide switch (`role="switch"`, `aria-checked`, click / Space / Enter): on is full strength with the agent's color bar and an open eye, off is dimmed and dashed with a closed eye and muted numbers. Hiding removes its lanes, blocks, and day-mode columns; the cards of hidden agents stay (to turn them back on) and show their numbers. The hidden list is saved (`activityHiddenAgents`); at least one agent always stays on (`toggleAgent`, `agentCardState`: the last card that is on is locked).
- **Interaction**: hover shows `HH:MM–HH:MM name` (Obsidian's `setTooltip`, true times). Clicking a block splits the view left/right: the calendar stays on the left, a details panel opens on the right (its width is `activityDetailWidth`, a % of the view, set by dragging the divider; "Close" returns to the full width). The panel splits top/bottom: the **block** above (the session's agent, category chip and name; the block's start–end and duration; then one row per human turn in order: its start–end, its duration (the work in it, idle stretches not counted), the input text (an answer to a question gets a small "Answer:" label), and the turn's final response, folded behind a `<details>` "Response" disclosure (closed on every open; opened it is a filled `background-secondary` box, muted, with a max height and scroll; rows are separated by spacing and a hairline, with no side borders); notifications and sub-agent runs are not listed) and the **session** below (the same `renderDetail` the side panel's and the manager's details panes use), with "Open session" (`plugin.openSession`) in the panel's bar. After each load the grid scrolls to half an hour before the first activity of the period (08:00 when there is none).

## 11. Names and categories

**Category** is everything before `: ` in a name (`tree.ts`'s `splitName`, the same rule the TUI and manager groups use). A name with no `: ` has no category.

**Display name**: a single pure function, `sessionDisplayName({name, label, agent, id})` (`name.ts`), decides what to show wherever a session needs a name — tab title (`views/terminal.ts`'s `getDisplayText()`, and `main.ts`'s deferred-tab fixup, above), side panel row, manager row and search-filter fallback, detail pane, notifications (`notifyIdle`, session analytics' modal title), and a newly-archived entry's cached name. The fallback chain: the session's own `name` (`/rename`, or Claude Code's/Codex's own title) → `label` (the auto-derived name — usually the first prompt, truncated) if that's real content → "New Claude Code session"/"New Codex session" (`common.newSession.<agent>`, by agent) if neither is. The session's own `id` is never shown as its name anywhere — a `label` that happens to equal `id` (Python couldn't extract anything real from this session, so it fell back to the id itself) is treated the same as an empty one. This applies uniformly to every state a session can be in: a deferred tab restored with no `Row` yet, a not-yet-resolved Codex placeholder (§7.7), and right after a restart, before the first scan completes — all of these just have an empty `name`/`label` for the moment, which the same fallback chain already handles by showing the agent's own name instead of "Untitled". "Rename" pre-fills from the session's own real `name` only (`TerminalView.displayName`/`rows.ts`'s `row.name ?? ""`), never through `sessionDisplayName`'s fallback chain — otherwise it would look like "New Codex session" was the session's actual stored name.

**Input**: both the new-session and rename dialogs use one combined field (`modals.ts`'s `buildComposedNameField`) for category and name together. A half-width `:` is recognized as a separator the moment it's typed, no trailing space required. A full-width `：` is only recognized once followed by a space (since an IME can produce `：` alone mid-conversion, before the rest of the input lands). The instant a separator is recognized, everything before it (the category text and the separator itself) is removed from the text field and shown instead as a confirmed chip (this also applies to a separator that arrives via paste, through the same `input` event path). Before a separator appears, a dropdown of matching existing categories (`filterCategories`) is shown; ↑↓ moves through it, Enter/Tab confirms the selection (turning it into a chip), Escape closes it. With the name field empty and the cursor at the start, Backspace turns the chip back into text, merged with the (already-empty) name field as one editable "Category: Name" string again — safe specifically because the name is already empty by the time Backspace can reach it (`tokenizeNameInput` and `filterCategories` are pure functions in `name.ts`). **Clicking the chip edits just the category, in place** (`beginEditChip`; reverting the chip to text would discard whatever the name field holds, which matters when renaming a session that already has a real name) — the chip is swapped for a small text input pre-filled with the current category and selected, the same suggestion dropdown anchored to it; confirming (a suggestion, Enter/Tab, or losing focus) replaces just the chip, Escape cancels with no change at all, and the name field itself is never touched by any of this. `sessions/name.ts`'s `applyChipEditResult(state, result)` is the pure function this delegates the actual state change to (`result: null` = canceled, unchanged; otherwise the new, trimmed category — empty removes it — with `name` always passed through unchanged), which is what's actually pinned in tests, not a parallel reimplementation of the same guarantee. Only the dialog's own button confirms the dialog; Enter in this field confirms a dropdown suggestion, not the dialog. `filterCategories` ranks a prefix match ahead of a substring-only match (both cases); each group keeps its own relative order.

The dropdown itself (`modals.ts`'s `buildCategorySuggest`) is a small shared component — each row is just its category chip (no separate label span repeating the same text) — arrow-key/mouse highlighting, click-or-Enter confirmation via a caller-supplied callback — used by this composed field, the "Move to category" dialog below, and `beginEditChip` (above), which all turn a confirmed suggestion into a chip. **It's portaled to `<body>`, `position: fixed`** (with many categories the dropdown can be taller than the remaining space below the input inside a short dialog, and `Modal`'s own chrome (`.modal`) would clip an overflowing `position: absolute` descendant to its rounded corners). Each time it opens, `computeSuggestPosition` (`ui/suggest-position.ts`, a pure function so this part is directly testable — `modals.ts` itself imports `obsidian` eagerly and can't be) computes its `left`/`width`/`top` from the input box's own `getBoundingClientRect()`, flipping to sit above the input instead (`bottom` set, `top` null) when there isn't room below it in the viewport but there is above; `z-index: var(--layer-tooltip)` keeps it above the modal itself. Because it isn't a normal descendant of the dialog, it isn't cleaned up when the modal's `contentEl` is emptied on close — every caller's `onClose` explicitly calls the suggest's own `destroy()` (or the field's, which delegates to it) to remove it from `<body>`.

The resulting name is `Category: Name` (or just `Name` with no category). The rename dialog pre-splits the current name via `splitName` into the chip and the remaining text.

Every text-input field in these three dialogs sits in a `Setting` given the `agent-sessions-wide-setting` CSS class (`modals.ts`'s `makeWide`) — Obsidian's own `Setting` control column shrinks to fit and right-aligns by default (meant for small controls like a toggle or a short dropdown, not a wide text field), which without this makes the input area appear squeezed to the right of the dialog. The class stacks the row (label above, full-width control below) instead.

**Move to category** (the row `⋯` menu's "Move to category…"; `rows.ts`'s `RowActions.moveToCategory`, `modals.ts`'s `MoveToCategoryModal`): a single category-only field — the session's own label is never shown for editing in this dialog. **Shows the current category as a chip** the same way the composed name field does, including the removable "×" (`appendChipRemove`, shared by both — clicking it clears the category outright) and the same click-to-edit-in-place (`beginEditChip`), for a consistent feel across every dialog with a category chip. Backspace with the input empty reverts the chip to editable text. Starts already chipped if there's a current category, since an existing one is itself already "confirmed". The same `buildCategorySuggest` dropdown opens on focus or click as well as while typing (there's no chip-vs-typing gate here — with only one field and no separate "name" part competing for the input, typing straight over an existing chip and confirming (a suggestion, or Enter/"Move" with nothing highlighted) just replaces it). Confirming composes `Category: Label` (or just `Label` with an empty category, removing it) and sends it through the exact same path as a rename (`plugin.renameSession`, `/rename` either way, regardless of agent). The label used is `categorizableLabel(row)` (`name.ts`): the name's own label if the session has already been named, otherwise the row's auto-derived label (its first prompt, truncated) — never `sessionDisplayName`'s "New Claude Code session"/"New Codex session" fallback, which isn't real content to categorize. The menu item is disabled when `categorizableLabel` is empty (a session with neither a name nor a first prompt yet): inventing a label just to attach a category to it would write meaningless content into the session's real name, so the action is unavailable until there's something real to categorize; "Rename" (which sets both at once) remains available regardless.

**Color**: each category gets a fixed palette index (0–11; `category.ts`'s `paletteHueDeg(index)` maps it to a hue in 30-degree steps from 0 to 330), recorded in `sessions.json`'s `categoryColors` (§3). `assignCategoryColor(colors, category)`: an already-assigned category keeps its index unchanged; a new one gets the lowest unused index, or — once all 12 are in use — whichever index is used least often (ties go to the lower index). `SessionIndex.categoryColorIndex(category)` returns the confirmed index if there is one, or computes (without writing) what it would be — used for the naming dialog's preview color before a scan confirms it. Every scan, `SessionIndex` runs `ensureCategoryColors` over any category present in the current session list that isn't yet confirmed, writing the results back to `sessions.json` under the lock (a failed lock is swallowed rather than raised, and retried on the next scan).

Chip rendering is centralized in `chip.ts`'s `renderCategoryChip(container, category, colorIndex)`, used identically by the naming dialog, side-panel rows, the manager's headings/rows/category bar, and the detail view (dark theme: `hsl(h 40% 50% / 0.18)` background, `hsl(h 45% 60%)` text; light theme (`.theme-light`): `hsl(h 50% 50% / 0.16)` background, `hsl(h 45% 32%)` text; the category bar's fill uses the same hue, `45% 60%` dark / `45% 32%` light). A chip has no `max-width` or ellipsis — it always shows the full text; only the name beside it (`flex: 1 1 auto`) shrinks to fit.

**Organize names and categories** (`ui/organize-modal.ts`, from the `⋯` menu of the side panel and the manager). A dialog that proposes `Category: Name` for a batch of sessions and applies only what the user ticks. The row menu's **Suggest name and category…** (second entry of the first group, after Move to category, for every session) opens the same dialog limited to that session (`new OrganizeModal(plugin, id)`): the start view has no "only unnamed" toggle and its intro speaks of this one session; Suggest still has to be pressed before anything is sent; the result is one row whose comment field is always shown, with **Suggest again** (the previous suggestion and the comment go back to the agent) and Apply. When the agent keeps the current name and category the row is unticked and the dialog says there is nothing to apply.

- *Selection* (`sessions/organize.ts`'s `selectSessions`): not archived, not a headless child, newest first, at most 30 (`ORGANIZE_BATCH_CAP`); incomplete sessions (no name, or no category by `splitName`) come before complete ones, and the "only unnamed or uncategorized" toggle (on by default) drops the complete ones.
- *Context*: per session (`toCandidate`, each field flattened and cut): the folder (vault-relative inside the vault, else its name; 80 characters), the current name, `Row.label` (first prompt; 300), the last three human prompts from `json detail`'s `recent_user` (240 each; falls back to `last_user` for Codex and OpenCode; `isHumanPrompt` drops injected tags, notifications and teammate messages once more) and `last_assistant` (300), through `SessionIndex.getDetail`, four at a time. The existing categories go in as `categoryProfiles`: up to 40, most used first, each with its session count and up to three example names (40 characters), so the model sees what a category is here (a project, a client, an area) and reuses it. Session text is quoted as JSON data and the prompt says to ignore instructions inside it.
- *Agent* (`sessions/organize-agent.ts`'s `pickOrganizeAgent`): Claude Code when enabled, else Codex, else OpenCode. The dialog shows "Suggestions by <agent>" (`agentLabel`) before anything runs, and explains when none qualifies (Suggest is disabled). Per-agent argv (`headlessArgs`) and output parsing (`parseAgentOutput`) are pure functions with tests; the prompt always goes in on stdin.
  - Claude Code: `claude -p --model sonnet --output-format stream-json --verbose --include-partial-messages --tools "" --strict-mcp-config --disable-slash-commands --no-session-persistence --settings '{"disableAllHooks":true}'`; the answer is the final `result` event (an error result throws its message). The model is the setting "Model for suggestions" (`organizeModel`: Sonnet by default, Haiku for speed); Sonnet is the default because Haiku's categories and names were too loose and too long.
  - Codex: `codex exec --skip-git-repo-check --sandbox read-only --ephemeral --ignore-rules --json -`; the answer is the last `item.completed` / `agent_message`; `error` and `turn.failed` events throw. No `-m`: there is no cheap-model flag that is valid for every account, so the user's configured model runs.
  - OpenCode: `opencode run --pure --format json`; the answer is the `text` parts joined; an `error` event throws. The default model runs (the Ollama launch setting is not used). `run` stores its session in OpenCode's database, so `backend/headless.ts` deletes it right after by the exact id printed in the events (`opencode session delete <id>`; best effort).
- *Engine* (`backend/headless.ts`'s `runHeadless`): spawns the argv with cwd `~/.agents/sessions/organize/` (no `CLAUDE.md` above it), 180 s timeout, killed on Cancel, stdout read as it streams (`streamedChars` counts answer characters arriving: Claude Code's `text_delta`s, whole messages for the others). The binary and env are resolved like a session launch (`resolveAgentBinary`, `loginEnv`, the agent's env setting, `withBinDirOnPath`). These runs never show up as sessions: Claude Code writes no transcript (and one that were written would carry `entrypoint: sdk-cli`, which `read_head_info` marks `child`, §3.3); Codex writes no rollout with `--ephemeral` (and an `exec` rollout has `source: exec`, which `codex/rollout.py` marks `child`); an OpenCode `run` session is marked `child` from its `permission` column (`opencode/db.py`'s `is_non_interactive`) and is deleted anyway.
- *Views*: the dialog shows exactly one of three containers (`showView`; pure `viewAfterRun` in `ui/organize-view.ts`). *Start*: intro, agent line, the "only unnamed or uncategorized" toggle, Suggest. *Working*: only the progress panel and Cancel; nothing of the start view or an earlier result. *Result*: the review table and its buttons (Apply selected, Suggest again for unchecked, Suggest all again, Cancel) plus a collapsed "Show log" disclosure holding the last run's log. A run (`runBusy`) goes from the current view to Working and then to Result when it produced rows; on error, cancel or an empty answer it returns to the view it came from, with the error in the status line and the log in the disclosure (the earlier result is kept).
- *Progress*: a spinner (CSS, stopped under `prefers-reduced-motion`), a live line ("<agent> is working… 12 s · 340 characters received") ticking every second, and a timestamped log of the steps (reading N sessions, asked the agent, received suggestions for N sessions, errors, cancel).
- *Prompt* (`buildPrompt`): the category is a project, client or area like the user's existing ones, never a kind of task; an existing category is strongly preferred (copied exactly) and a new one is allowed only when none fits, as a short noun (12 CJK characters or 3 words); the name is a noun phrase naming the task or topic, at most 20 CJK characters or 5 words / 32 characters, with no verb endings, no repeat of the category, no quotes, brackets, emoji or dates, in the conversation's language; `keep: true` leaves a good current name and category; the answer is a strict JSON array of `{id, keep, category, name, reason}` with a one-line reason.
- *Parsing* (`parseSuggestions`): the reply is read defensively (code fences, prose, an object wrapping the array), unknown or repeated ids and nameless entries (unless `keep`) are dropped, colons, quotes, brackets and emoji are removed from categories and names so the result splits back into the same pair, and the reason is flattened and capped at 100 characters. Names are not shortened here.
- *Validation* (`resolveSuggestions`, pure and tested with a fake `ask`): `checkSuggestion` names what is wrong with each answer (name over its limit, a name that ends like a sentence, a name that repeats the category, a new category over its limit or naming a kind of task, no category); one repair request (`buildRepairPrompt`) goes to the agent for those sessions only, with what to fix; then `finalizeSuggestion` enforces in code what can be: a kept answer takes the current category and name, a category is spelled like the existing one it matches (ignoring case, width and spaces), a new category is cut to its limit and a task-type one falls back to the current category, the category is taken out of the name, and the name is cut (characters for CJK, whole words otherwise). If the repair request fails the first answers are corrected in code. The same path serves **Suggest again** (`buildFollowUpPrompt`).
- *Review and apply*: one row per session, in columns: current (category chip and name on the first line, the first prompt below it in `--text-muted` at `--font-ui-smaller`) | → suggested category chip and name, with the model's one-line reason below in the same muted style | a round apply toggle (`ui/round-check.ts`: a 28 px circle, `role="checkbox"` with `aria-checked`, Space/Enter toggles, the whole cell is the hit area; on by default when the proposal changes the name); below 640 px each row wraps to current + toggle, then suggested, and the header row is hidden. The suggestion is read-only: the chip is a plain category chip and the name plain text; the model's answer changes only through a new suggestion. Existing categories keep their color; a new one is shown in the slot it will be assigned, previewed in row order by `SessionIndex.categoryColorPreview` without persisting. A ticked row reads as "will apply" (accent-tinted background, accent left border, the suggestion at full strength); an unticked row reads as "skip" (no tint, the suggestion dimmed and its name struck through). The per-row comment field shows only on unticked rows (its text survives re-ticking); the overall comment and **Suggest again for unchecked (n)** show only while at least one row is unticked (`reviewState` in `ui/organize-view.ts`), and **Apply selected** is disabled when nothing is ticked. **Apply selected** calls `plugin.renameSession` one session at a time (§6), so `/rename`, OpenCode's `sessions.json` name and the pending-name path behave as from the row menu. Nothing is applied before that.
- *Suggest again for unchecked*: unticked rows show a comment field, and an overall comment field appears below the list. The button re-runs the agent for only the unticked rows (`buildFollowUpPrompt`): each carries the previous suggestion and its comment, plus the overall comment, and the prompt asks for a different, better proposal. The returned rows replace those rows' fields (and are re-ticked when they change the name); ticked rows are untouched; a row the model skipped keeps its previous suggestion.

## 13. Aggregation

### 13.1 `agent-sessions json usage ID [--from ISO] [--to ISO]`

An `assistant` line's `message.usage` (`input_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`, `output_tokens`, `output_tokens_details.thinking_tokens`) recurs across several lines sharing the same `message.id`, with identical content. A line whose `message.model` is `<synthetic>` isn't a real API call. Sidechain (sub-agent) and meta lines aren't counted.

`agentsessions/usage/turns.py` reads a transcript from the start and cuts it into turns at each human prompt (`detail.is_human_prompt`); the `assistant` lines that follow accumulate into that turn's usage, de-duplicated by `message.id`. Usage before the first prompt goes into a synthetic pseudo-turn (`index -1`, `before_first: True`, `prompt: ''` — display text for that case is the caller's job; see `usage.beforeFirstPrompt` on the plugin side). Each turn carries `cost` ($, from `usage/pricing.py`), `tools: {name: count}` (`tool_use` blocks in `content`, counted by name, de-duplicated by `message.id`), and `models`. The `total` carries `cost`, `tools`, `duration` (seconds from the first prompt to the last assistant line), `first_ts`, `last_ts`, and `context_last` (the most recent call's `input + cache_read + cache_create`). If any turn has `estimated: true`, so does `total`. `--from`/`--to` filter by a turn's start time (inclusive on both ends). Output: `{"turns":[…],"total":{…},"from","to"}`; each turn is `{index, ts, prompt, calls, input, cache_create, cache_read, output, thinking, cost, tools, estimated, unpriced_calls, last_ts, context_last, models, before_first}` (Codex and OpenCode turns add `unknown_cost`; see §13.3). `turns` is always the complete list; only `total` reflects the filtered range.

The row menu's "Session analytics" (and the terminal tab's ⋯ menu, "Show session analytics") opens a modal (`src/usage/usage-modal.ts`, `width: 90vw; max-width: 1100px`) with a fixed header (title, copy, close), four summary cards (cost; tokens — total input, output below it; turn count; duration), an input bar (cache-read / cache-create / uncached shares, with counts in the legend), an output bar, a tool-use bar (top 12), and a turn table (# · time (locale-formatted date + time, `formatEpoch`) · prompt (truncated, full text on hover) · input · output · cost). Clicking a row starts a range; clicking another row ends it (highlighting the range), while clicking the start row again clears it. A click after a range is set starts a new one, and "Whole" returns to the whole session (`usage.ts`'s `nextSelection`). The cards and bars reflect the selected range, with a "#a–#b" subtitle. Numbers use k/M notation (`usage.ts`'s `formatK`). Range summing and the copyable Markdown rendering are pure functions in `usage.ts` (`sumRange`, `toMarkdown`).

### 13.2 `agent-sessions json stats`

Output: `{"windows":{"five_hour":W,"seven_day":W},"agents":{"claude":{"windows":{...}},"codex":{"windows":{...}}}}`, where `W = {"key","minutes","label_key"?,"start","end","used_percentage","exhausted","exhausted_at","total":{calls,input,output,cache_read,cache_create,cost,unknown_cost,unpriced_calls},"sessions":{id:{...same as total...}}}` — the same shape for every agent, so the plugin's analysis views (§10.2's stat cards/category bars, §8's rate-limit bars) can render any of them through the same code. `end` is `resets_at` (or the current time if absent); `start` is `end − minutes`. `used_percentage` comes from `rate_limits` (`null` if unavailable). `minutes` is the window's own length (300/10080 for `five_hour`/`seven_day`) — carried on every window, any agent, so a pace-calculation formula that only cares about window length can run against any of them uniformly, including a Codex window that isn't 5h or 7d at all (see below). `unknown_cost` is `true` when `total`/a session's own totals include a call whose model has no known price (§13.3) — that entry's `cost` is then a floor, not the true total; Claude's is always `false` since Claude pricing never reports unknown. Only an *enabled* agent (§3.3's `enabled_agents()`) gets an `agents.<name>` entry, and OpenCode never does: it has no rate-limit windows to report (§3.3).

Codex can report a rate-limit window that's neither 5 hours nor 7 days (real local data: this account's current, actual state is a single ~30-day/43200-minute quota — no 5h/7d tracking active at all). `agents.codex.windows` always has `five_hour`/`seven_day` (with `used_percentage: null` if this account isn't tracking that length right now), plus any *other* window found, keyed `window_<minutes>m` and carrying a best-effort `label_key` for the plugin to look up display text for a length it doesn't have a hardcoded string for (`window.30d` for a day-aligned length, `window.2h`-style for an hour-aligned one, `window.<n>m` as a last resort) — `minutes` remains the authoritative value either way. `end` is always the resolved absolute reset time (this is what the side panel's countdown reads for Codex, same as it already does for Claude's `end` — no separate `resets_at`-equivalent field was needed): a slot's `resets_at` (absolute epoch) is used directly when present; an older Codex CLI version's slot instead has `resets_in_seconds` (relative to that reading's own event timestamp — real local data confirms both formats exist, from different points in time) and gets resolved to the same absolute form. See `agents/codex/stats.py` for the full reasoning (window identification from each `rate_limits` slot's own `window_minutes`, never position; a single `primary`/`secondary` snapshot read together, never mixed across different points in time).

The top-level `windows` key is always Claude's, computed unconditionally regardless of which agents are enabled — kept for a plugin build that reads it instead of `agents.claude.windows`; the top-level key can be dropped once nothing reads it.

**Exhausted windows** (`exhausted`, `exhausted_at`; `usage.stats.exhaustion`/`with_exhaustion`, pure): Claude Code's `rate_limits.*.used_percentage` is `round(utilization × 1000) / 10` from the last *accepted* response's headers, so once a limit is reached the snapshot keeps the last value below it (typically 99) — the rejected request never produces a new one. The rejection is in the transcript instead: a synthetic assistant line (`model: "<synthetic>"`, `isApiErrorMessage: true`, `error: "rate_limit"`, HTTP 429) whose text reads "You've hit your session limit · resets 2:50pm (Asia/Tokyo)" (the 5-hour window) or "… your weekly limit …" (the 7-day window; also inside "You've hit your monthly spend limit · … · your weekly limit resets …"). `limit_hit_keys` maps such a line to its window key; a bare "monthly spend limit" and "Server is temporarily limiting requests (not your usage limit)" map to none. A window is exhausted when a hit falls inside `[start, end)` or `used_percentage` is 100 or more; `exhausted_at` is the earliest hit inside the window (`null` when only the percentage says so), and `used_percentage` is then reported as at least 100. Codex: a `token_count` whose slot for that window reads `used_percent` ≥ 100 is a hit for it; a rejected turn (`codex_error_info: "usage_limit_exceeded"`, on a `task_complete`'s `error` or an `error` event) doesn't name its window, so it counts for the window that is fullest in the latest snapshot (the shorter on a tie).

If `end` (`resets_at`) is in the past — right after a reset, before a fresh `rate_limits` has arrived — `_roll_forward(end, used_percentage, duration, now)` advances the window by whole multiples of its length (`math.ceil((now - end) / duration)`, so it copes with being more than one window stale) to produce "the current window"'s `end`. A rolled-forward window sets `used_percentage` to `null`, since the real value won't be known until a fresh `rate_limits` snapshot arrives. `start` follows from the new `end`, so cost aggregation only covers the new window (not the one before it). The side panel's rate-limit view (`views/limits.ts`, §8) reads `status/*.json` directly rather than going through `json stats`, so it carries its own copy of the same rule as a pure function, `rollForwardWindow(w, durationSeconds, now)`.

Aggregation source: `~/.claude/projects/*/*.jsonl` (sidechain lines included; a sub-agent transcript under `<project>/<id>/` is folded into its parent's `id`) with mtime newer than the 7-day window's start. `assistant` lines are de-duplicated by `message.id`, `<synthetic>` excluded, cost from `pricing.cost`.

Caching: per file, 10-minute buckets (`{bucket_start: {calls,…,cost}}`), the last read position (`offset`), a `schema_version`, the limit hits (`[[timestamp, window key], …]`, the 50 most recent), and the 200 most recent `message.id`s live in `~/.agents/sessions/stats-cache.json`. A grown file is read from `offset` onward (transcripts are append-only); a shrunk one is read from scratch. `schema_version` (`STATS_SCHEMA_VERSION`, own constant, versioned independently of `SCAN_SCHEMA_VERSION` above since this cache's shape is unrelated) protects the buckets themselves rather than the read position: an entry whose version is stale is treated as fully absent (a fresh read from offset 0, discarding its buckets) rather than incrementally appended to, since appending new, correctly-computed buckets on top of old, differently-computed ones would silently corrupt the totals — offset/mtime/size alone can't detect that a bucket already on disk was computed by logic that no longer matches. Window totals sum from the buckets (10-minute granularity). A corrupted cache (the whole file, or a single entry) is discarded and rebuilt. A second run typically finishes in under a second.

**Codex** (`agents/codex/stats.py`) computes the same `W` shape from the rollouts, with two differences from Claude's approach: (1) window identification — Codex's `rate_limits` has two positional slots, `primary`/`secondary`, whose meaning (which is the 5-hour window, which is the 7-day one) isn't fixed by position; real local data shows the same account reporting a 5-hour window as `primary` in one rollout and a 7-day window as `primary` in another, with a third case (a ~30-day/43200-minute quota on the free plan) matching neither. Each slot's own `window_minutes` is checked against the expected duration (within a tolerance, since real values wobble by a minute or two — 299 instead of 300) rather than trusted by position; a window kind found nowhere reports `used_percentage: null`, same as Claude's "no `status/*.json` yet" case. (2) no incremental cache — a rollout's `token_count` is a running total, not a per-call delta the way Claude's `message.usage` is, so recovering a delta for a line read from the middle of a file (as an offset-based cache would do) needs the running total immediately before it; every `json stats` call re-reads every rollout in range from the start instead, acceptable for a personal-use dataset's session count. Unknown-model cost is handled the same way as `json usage` (§13.3): a call on an unpriced model adds to `unpriced_calls` and sets `unknown_cost: true` on its bucket, its session and `total`, and is left out of `cost` (a floor, not the true total) rather than silently reported as `0`; the priced calls around it still count.

### 13.3 `usage/pricing.py`

`price_of(model) -> {input, output, cache_5m, cache_1h, cache_read, estimated}` ($/MTok). `cost(usage_dict, model) -> float`. Models are matched by longest-prefix:

- `claude-fable-5-1`, `claude-mythos-5-1`: input 10, output 50, cache-read 0.25 (an exception to the pattern below)
- `claude-fable-5`, `claude-mythos-5`: input 10, output 50, cache-read 1.0
- `claude-opus-5`, `claude-opus-4-8`, `claude-opus-4-7`, `claude-opus-4-6`, `claude-opus-4-5`: input 5, output 25, cache-read 0.5
- `claude-opus-4-1`, `claude-opus-4`: input 15, output 75, cache-read 1.5
- `claude-sonnet-5`: input 2, output 10, cache-read 0.2
- `claude-sonnet-4-6`, `claude-sonnet-4-5`, `claude-sonnet-4`, `claude-3-7-sonnet`: input 3, output 15, cache-read 0.3
- `claude-haiku-4-5`: input 1, output 5, cache-read 0.1
- `claude-3-5-haiku`: input 0.8, output 4, cache-read 0.08
- `claude-3-haiku`: input 0.25, output 1.25, cache-read 0.03

Cache-write cost is input × 1.25 for a 5-minute TTL, input × 2 for a 1-hour TTL (`cache_creation.ephemeral_1h_input_tokens`, if present, uses the 1-hour rate; the rest uses 5-minute). An unrecognized model is priced at the `claude-opus-5` rate with `estimated: true`.

`price_of`/`cost` take an `agent` parameter (default `'claude'`, so every pre-existing caller is unaffected). With `agent='codex'`, models are matched against `OPENAI_PRICES` instead (`gpt-5.6-sol`/`-terra`/`-luna`, `gpt-5.5`, `gpt-5.4`, `gpt-5-nano`, `gpt-5`; cache-read priced at input × 0.1, no separate cache-write tier) — an unrecognized OpenAI model returns `unknown: true` and `cost()` returns `None`, not a Claude-derived estimate: the two vendors' pricing bands don't overlap closely enough for a same-table fallback to be a reasonable ballpark. `agents/codex/usage.py` surfaces this as `unknown_cost: true` and `unpriced_calls: N` on the affected turn (and on `summarize`'s `total`); `cost` stays the priced calls only. OpenCode uses no price table at all: `agents/opencode/usage.py` sums the `cost` OpenCode stored on each assistant message (§3.3), which is `0` for a local model; a message with no numeric `cost` is an unpriced call the same way. Claude Code turns carry `unpriced_calls: 0` (an unknown Claude model is `estimated` instead).

The plugin shows such a cost with `usage.ts`'s `costView`, everywhere a session, range, category or window cost appears (Session analytics' card, table and Markdown copy, the details pane, the Session manager's 5h/7d cells, group rows, category bars and window cards): the priced part with a "+" when some calls have no price, "—" when none does, each with a tooltip saying how many of how many replies have no price. An older helper without `unpriced_calls` still gets the mark from `unknown_cost`.

### 13.4 `agent-sessions json activity --from ISO --to ISO [--gap-minutes N]`

Backs the activity calendar (§10.4), which asks for the days of its period that it doesn't have yet. `--from`/`--to` are required ISO 8601 (UTC when no zone is given); `--gap-minutes` defaults to 30. `--raw` returns the building blocks instead of joined `spans`: per session `turns` (`{start, end, prompt, kind, reply}`, every kind, including the unlisted `resume`) and `runs` (`{start, end, turn}`: each segment of each turn, `turn` being that turn's `start`, and each sub-agent run, `turn: null`), with no gap joining, no one-minute stretching, and no clipping (a run crossing the range's edge is returned whole). A reader joins them exactly as `join_turns` does (the plugin's `joinRuns`). The cache is the same either way.

```json
{"sessions": [{"id": "…", "agent": "claude", "name": "RIM: Notes", "label": "Notes",
               "category": "RIM", "child": false, "first": 1789900000.0, "spans": [{"start": 1790220000.0, "end": 1790221200.0,
                          "turns": [{"start": 1790220000.0, "end": 1790220900.0, "prompt": "fix the parser", "kind": "prompt"}]}]}]}
```

`first` is the start of the session's earliest turn or sub-agent run, inside the range or not (the calendar's session order, §10.4); it is in the `--raw` output too. `spans` are blocks `{start, end, turns}` (epoch seconds), sorted, clipped to the range; a session with no span in the range is left out. They are built from **human turns** (`sessions/activity.py`): a turn starts with a human input and lasts until the agent's last output before the next human input (or the end of the transcript), so a block is close to the real working time. Human input is what the person typed (a slash command they typed included) and their answer to a question the agent asked. Everything else that reaches the agent in between continues the current turn instead of starting one: injected notifications (another session's message, a finished background task, teammate messages), system reminders, the compaction summary, `isMeta` lines, a command's caveat and output, interruptions.

Inside a turn, a silence of 30 minutes or more between two records ends the activity there; the records after it open a new *segment* of the same turn (the agent carried on by itself, or a notification woke it), so idle hours are not counted. The segments of every turn, and the runs of a session's sub-agents, are the intervals that get joined: two less than `--gap-minutes` apart are one block; a block shorter than one minute is extended to one minute; a last turn whose final record is under two minutes old is taken to be still running and ends now. `turns` lists the human turns that have a segment in the block, one entry each: `{start, end, active, prompt, kind, reply}`, where `start`/`end` are the part of the turn inside the block (true times, even when the block is extended to one minute), `active` is the seconds of work in that part, `prompt` is the input (first 200 characters; a slash command is one line, `/model best`; for an `answer` it is the answer itself), `kind` is `prompt` or `answer`, and `reply` is the agent's last text answer in the turn (first 400 characters, main thread). Sub-agent runs and activity before any human input count toward the time but are never listed. A clipped block keeps the turns that touch what is left of it. What starts a turn and what counts as the agent's activity, per agent:

- **Claude Code**: the session's work is the union of its main thread's turns and its sub-agents' runs. A sub-agent transcript is any `.jsonl` under the folder named like the session next to `<id>.jsonl` (any depth); each is a run from its first to its last record, split where two records are 30 minutes or more apart, and is cached per file (path, size, mtime) like the main transcript. This matters because a session that delegates to sub-agents shows only seconds of main-thread activity while the real work happens in the sub-agent files. In the main thread, a `user` line starts a turn when it is the person's own input: its `origin.kind` is `human`, or (older transcripts, no `origin`) its text isn't an injected one (not starting with `<`, "Another Claude session sent a message:", "This session is being continued…", "[Request interrupted…", "Monitor event:"); a slash command line is read from its `<command-name>` and `<command-args>`. The answer to an `AskUserQuestion` (a user line whose `toolUseResult.answers` is set, or whose tool result starts "Your questions have been answered") also starts a turn, of kind `answer`. A command's caveat and output (`isMeta`, `<local-command-caveat>`, `<local-command-stdout>`) are skipped entirely. Every other `user` and `assistant` line is activity (sub-agent lines and tool results included).
- **Codex**: an `event_msg` `user_message` (or `item_completed` UserMessage) with real text starts a turn (injected context such as AGENTS.md and bare slash commands do not); every record is activity.
- **OpenCode**: a `user` message starts a turn; the `time_created` and `time_updated` of every `message` and `part` row are activity.

Activity before the first human input counts only when a transcript has none at all.

Name, label, and category are the ones `json scan` reports (`category` is the group before `': '`). The scan cache supplies the names. Turns are cached per transcript in `activity-cache.json` (next to `scan-cache.json`): `path → {version, size, mtime, turns}`, (each turn cached as `[start, end, prompt, kind, reply, segments]`) recomputed only when the size or mtime changed, the algorithm `version` (`ACTIVITY_VERSION`) differs, or the file was written within the last two seconds (the same racy-mtime guard as the scan cache); OpenCode has no file, so its entry is keyed by the session's last-updated time. A changed transcript is parsed again in full. Entries for transcripts that no longer exist are dropped. A transcript file last written before `--from` cannot hold activity in the range and is never opened.

### 13.5 Token efficiency (`json efficiency` and its dialog)

Shows where recent tokens could be saved, with evidence, and lets an agent fix the findings that live in files (`agentsessions/efficiency/`, `plugin/src/sessions/efficiency.ts`, `plugin/src/ui/efficiency-modal.ts`).

**Range.** Per agent, the first that applies: the 5-hour window when its usage is at or above the threshold (setting, 80%) or it is exhausted; the 7-day window likewise; otherwise the newest calls, sub-agents included, until their weighted tokens reach the budget (setting, 10,000,000) and at least the last 24 hours, going back at most 7 days; `range.basis` says which of the three set the start (`budget`, `min_day`, `max_week`), and the range line says it in words. `--from/--to` gives the range directly (`explicit`). The range is fixed once per run and returned as `range`.

**Weighted tokens.** `W = input + 1.25 × 5-minute cache writes + 2 × 1-hour cache writes + 0.1 × cache reads + 5 × output`, the same for every agent; hits are ranked by it, and dollars are added where `pricing.py` knows the model.

**Normalizing** (`normalize.py`). One record per transcript, main or sub-agent: calls (`assistant` lines grouped by `message.id`, the last line's usage, `<synthetic>` left out), tool calls (kind, target path relative to the session's folder, a hash of the first two words of a command), tool results measured from the `tool_result` block the model saw (a `<persisted-output>` preview, not `toolUseResult`), edits as hashes of their old and new text, human prompts as an estimated length (`ascii/4 + other/1.5`), the gap since the agent's last output and a flag for naming a file the agent touched later, events (compaction, interruption, team start, limit hit), the links from an `Agent` tool call to its sub-agent's transcript, and the preamble's skill count and instruction file sizes as Claude Code recorded them. Teammate transcripts (first line `<teammate-message…`) are their own chain kind.

**Tasks** (`tasks.py`). A turn runs from one human prompt to the next. Sub-agent calls join the turn whose `Agent` call started them; teammate calls join the turn their time falls in. Baselines come from the 14 days before now, whatever the range: the median prompt length `L_med`, the median starting prompt `L1_med`, and the median calls per turn `C_med` (sub-agents included). Below 100 prompts (60 starting prompts) the rules that need them stop and `baselines.disabled` says which. A turn starts a new task at a session's start, or 30 minutes or more after the agent's last output when it touches none of the current task's files. Rework candidates, judged from structure only: a short prompt (at most half of `L_med`) within 10 minutes that edits again a file the previous turn edited; an edit that restores text an earlier edit replaced; a turn after an interruption. Nothing compares the words a person wrote, so the same conversation in another language gives the same tasks and hits.

**Detectors** (`detect.py`, `impact.py`). E01 large tool results read again by later calls (the fix goes to the instruction file that owns the file read, or the files the chain was working on, by the same rule as E08); E02 a task with ten or more calls above 60% of a 1M window (200K when the window isn't known); E03 unrelated tasks in one conversation (needs the model); E04 a cache rewritten after a pause longer than its TTL; E05 a model or effort change that rewrote the cache; E08 the same files read at the start of three or more sessions in a folder (the fix targets the `CLAUDE.md` of the repository or folder that owns the file); E14 a preamble 10,000 tokens above the user's usual for the same folder and Claude Code version; E16 correction round trips (needs the model). Each hit has a content-derived id, an impact in weighted tokens (and dollars), a saving rate, and a remedy: `fix` (`add`, `trim` or `move`, with at most two target files) or `habit`. The breakdown gives every call to the confirmed hit that costs it the most, teammates to `team`.

**Cache** (`cache.py`). One file per transcript under `~/.agents/sessions/efficiency/cache/`, keyed by path, size, mtime and version; a file written in the last 2 seconds is read again; entries of transcripts that are gone are removed. A record over 1 MB is merged into 10-minute buckets. Tasks and hits are recomputed on every run. At most 200 sessions or 2 GB are parsed per run.

**What is sent** (`excerpt.py`, `report.py`). `summary` (range, totals, breakdown, baselines, the 20 largest tasks, 40 hits, masked session names and folders, instruction file sizes, skill count) and `excerpts` (up to 8 tasks, those needing the model first: up to 8 prompts of 600 characters, the first 200 characters of each turn's last reply, the tool calls without their results), read back by byte offset and masked (secrets, e-mail addresses, URL paths, the home folder; paths in the vault made relative, others cut to their last two parts). Together at most 60,000 characters: the tasks with the smallest impact go first, then prompts are cut to 300.

**Codex and OpenCode** (`codex_read.py`, `opencode_read.py`, `sources.py`). Both are read into the same records as Claude Code's transcripts, so tasks, baselines and detectors are shared. Codex: a call is a `token_usage_record` (0.156 on) or a `token_count` whose `last_token_usage` adds to the running total (older rollouts); `input − cached − cache_write` is the uncached input and reasoning is part of the output; `apply_patch` is an edit (file lines, hashed `-`/`+` lines), `exec_command` is read, search or exec by the program it starts with, the code mode's `exec` is exec (web when it calls `tools.web__…`); prompts are the typed `user_message` / `UserMessage` items, one per turn; `compacted` lines and `turn_aborted` events are compactions and interruptions; a rollout whose `source.subagent.thread_spawn.parent_thread_id` names a thread joins it. OpenCode: a call is a `step-finish` part, with `reasoning` outside the output (weighted at 5 too), its message's provider, model and agent, and its recorded cost; tool parts are tool calls, a `compaction` part a compaction, `MessageAbortedError` an interruption, a `parent_id` session a sub-agent. Where the agents differ: the instruction file is `AGENTS.md` for Codex and OpenCode (E01, E08 owners; E14 moves a file over 20 KB); E04 for Codex is a call reading less than 30% of its input from the cache after a pause longer than the model's retention (30 minutes from gpt-5.6, 5 before), with no `fix`; OpenCode has no E04 (retention is the provider's) but its E05 also counts a switch of agent. Dollars: Codex from `pricing.py`'s OpenAI table (none for an unknown model), OpenCode its own recorded cost, impact without dollars.

**Panes.** What may be sent is split by provider: each session belongs to the provider it spent the most weighted tokens with, and `panes[]` (`key` `claude`, or `<agent>-<provider>`) carries that provider's sessions' totals, breakdown, hit ids, `summary` and `excerpts` — no other provider's session names, folders or hits. `model` is the model the analysis asks for (Codex: `config.toml`'s `model` when its `model_provider` is the pane's, else the provider's most used model; OpenCode: the provider's most used model) and `local` whether the provider runs on this machine (`ollama`, `lmstudio`, or an `opencode.json` provider whose `baseURL` is a loopback address). The top-level `summary` and `excerpts` are the first pane's.

**Analysis** (`sessions/efficiency.ts`). Only when the user presses Analyze in a pane: the prompt (English rules, the data between markers, the reply shape, the UI language for the text) goes on stdin to the pane's agent (`runHeadless`, five minutes): `claude -p` with Sonnet or Opus, `codex exec -m <model>` (and `-c model_provider="…"` for a provider other than OpenAI), `opencode run --model <provider>/<model>`; a Codex or OpenCode run that used a tool is reported in the log and above the results (`usedTools`) in an empty folder, `~/.agents/sessions/efficiency-run/current/` (`inRunFolder`: created empty before the run, removed afterwards whatever happens, a second concurrent run refused; the fixed name leaves Claude Code a single empty project folder for it). A reply that isn't the JSON object is asked for once more. The reply is checked against what was sent: unknown hit ids and quotes not found in the cited prompt or reply of the finding's tasks are removed; `fix` stays only when the change and targets match the statistics; sentences with numbers the statistics don't have, and any `/clear` advice, become the detector's canned text; impact is recomputed. Hits the reply leaves out stay as canned findings, except dismissed ones and those needing the model. The result goes to `last-<pane>.json` (the earlier one to `prev-`), and the analysis's own tokens and cost (`headlessUsage`) are shown.

**Fixing.** A `fix` card's button shows the agent, the new session's name, the files and the request (editable), then calls `newSession(name, agent, {prompt, permissionMode: "plan", remember: false})`: a session in the vault, in plan mode or the agent's nearest (Claude Code `--permission-mode plan` before `--`; Codex `--sandbox read-only --ask-for-approval on-request` before `--`, since it has no flag to start in Plan mode; OpenCode `--agent plan` before `--prompt`), that shows a diff and waits for approval. The request's third step says how each agent goes on to write (Codex asks for approval; OpenCode needs a switch to the build agent). The request lists the files that may change, the change kind's rule, the prohibitions, how to undo, and that the change applies to new conversations.

## 14. statusLine

`agent-sessions status` (`hooks.format_status_line`) writes one line for Claude Code's status line:

```
[<submit-key symbol> · ]<model> · <effort> · ctx NN% · rc ●/○
```

- Model is `model.display_name`, or "Default" if unavailable. Effort is `effort.level` (if it's a dict) or `effort` itself (if a string), or "Default" if unavailable.
- `ctx` is `context_window.used_percentage` (rounded), or "—" if unavailable.
- `rc` reflects whether the matching `session_id` in `~/.claude/sessions/*.json` has a `bridgeSessionId` (`live.live_sessions`) — no match, no ledger entry, or not connected all show `○`; only a connected session shows the green `●` (the same rule as the rc badge in the side/manager detail view).
- The submit-key symbol (macOS: `⏎`/`⇧⏎`/`⌃⏎`/`⌥⏎`/`⌘⏎`; other platforms: the shorter `⏎`/`S-⏎`/`C-⏎`/`A-⏎`; `keys.ts`'s `submitKeyStatuslineSymbol(key, isMac)`) is prepended, with a `· ` separator, only when `AGENT_SESSIONS_ID` is set (a session the plugin's daemon started) and `~/.agents/sessions/ui.json` has a `submitSymbol` (written by `plugin/src/backend/ui-state.ts`'s `writeUiState(runtimeDir, submitKey, language, isMac)` on every `onload` and settings save, passing `Platform.isMacOS`). It's omitted whenever `AGENT_SESSIONS_ID` is unset, `ui.json` is missing or unreadable, or `submitSymbol` is absent.

`agent-sessions status` also writes the JSON on stdin, verbatim, to `status/<session_id>.json` (temp file + rename; §3).

### 14.1 OpenCode's status line

OpenCode has no command-based status line setting; its own bottom line is internal. It does have TUI plugins, which render into named slots of the screen (`app`, `app_bottom`, `home_bottom`, `home_footer`, `home_logo`, `home_prompt`, `home_prompt_right`, `session_prompt`, `session_prompt_right`, `sidebar_content`, `sidebar_footer`, `sidebar_title`). Agent Sessions installs one, `agent-sessions-tui.jsx` (`agents/opencode/plugin_js.py`'s `TUI_PLUGIN_JSX`, a string in a `.py` module like the status plugin), that shows the same items as the Claude Code line, in the `app_bottom` slot:

```
[<submit-key symbol> · ]busy|idle|waiting   (the state label in the display language: 動作中/待機/許可待ち in Japanese)
```

- **Where.** `app_bottom` is a full-width row under the whole screen, below OpenCode's own footer (path, version), so it reads as a status line. `session_prompt_right` is the right end of the prompt's meta row, which already shows agent, model and variant on its left; a status line there would repeat them and would be squeezed by a narrow terminal. The row is empty on the home screen (no session there) and shows only on a session screen.
- **How it loads.** OpenCode loads a TUI plugin only from the `plugin` array of `tui.json` (spec or `[spec, options]`, a relative path resolves against tui.json's folder); nothing in a folder is discovered, and a module is either a server plugin or a TUI plugin, never both. So the file lives at `$XDG_CONFIG_HOME/opencode/agent-sessions-tui.jsx`, outside `plugins/` (whose files load as server plugins), and `"./agent-sessions-tui.jsx"` is kept in `plugin` by the managed tui.json writer (§7.7, §5) only while that file exists — an entry naming a missing file would have OpenCode fail to load it. On every load, while OpenCode is enabled, the plugin first runs `setup --opencode --update-only` against whatever program `agentSessionsPath()` names (the bundled install or `~/bin/agent-sessions`; files are rewritten only when their text differs), then syncs tui.json against the files present (`refreshOpencodeFiles`); enabling OpenCode installs the files before syncing too. The default export is `{ id: "agent-sessions", tui }`; `tui(api)` calls `api.slots.register({ slots: { app_bottom(ctx) { … } } })`.
- **No build step.** The file is JSX with a `/** @jsxImportSource @opentui/solid */` pragma. The `opencode` binary compiles JSX itself when it loads a file, resolving `@opentui/solid` internally, and its Solid transform makes expressions in the JSX reactive, so the row updates as the session state changes. No `node_modules` is needed; `node:fs`, `node:os` and `node:path` are imported.
- **Data.** It comes from the TUI's own state (`api.route.current`, `api.state`); nothing is polled. Session: the route's `sessionID` (the row is empty on any other route). State: `waiting` while a permission or question is pending (`api.state.session.permission`/`question`), `busy` while `api.state.session.status` isn't idle (busy or retry), otherwise `idle`. Model, variant (effort), folder and context use are not repeated: OpenCode's prompt row already shows agent, model and variant (the variant only when the model has one), and its footer shows the folder and the tokens and context percentage used — OpenCode draws that footer itself, with no slot or setting to shorten its path.
- **Submit-key symbol.** Read from `ui.json`'s `submitSymbol` (§14, `AGENT_SESSIONS_RUNTIME_DIR` respected, re-read at most every two seconds), and shown only when `AGENT_SESSIONS_ID` is set, i.e. in a session the plugin's daemon started, exactly as `agent-sessions status` does. Without `ui.json` or the variable, the line is just the state.
- **Nothing throws into OpenCode.** Every read is guarded; a failure renders an empty row. The `rc` mark of the Claude line has no counterpart, and the state carries no ●/○ so it isn't read as one; busy and waiting are set apart by colour instead.
- **Lifecycle.** Installed, refreshed on a program update (also for a status plugin installed before the status line existed), and removed together with the status plugin (`setup --opencode` / `--update-only` / `--remove-opencode` / `--remove`, §5); the tui.json entry follows OpenCode being enabled (added at startup and on enabling, taken out with the keybinds when OpenCode is switched off or Remove runs). A status line file without the marker line is never overwritten or removed.

## 17. i18n

### 17.1 The plugin (TypeScript)

`manifest.json`'s `description` is always English (`Run Claude Code, Codex, and OpenCode sessions as terminal tabs, with a session list, usage analytics, and a daemon that keeps sessions running.`). The UI itself supports Japanese and English. The language setting has three values: Auto (default — follows `window.localStorage.getItem("language")`), plus one per registered locale.

`src/i18n/index.ts` exposes `t(key, vars?)`. Every user-facing string — views, menus, dialogs, settings, notifications, modals, tooltips — goes through `t()`. Changing the language fires `settings-changed`, and every view rebuilds its skeleton from scratch.

Each language is one file, `i18n/locales/<code>.ts`, exporting a `Partial<Record<MessageKey, string>>` plus a `<CODE>_SELF_NAME` autonym (its own name for itself — `"English"`, `"日本語"` — shown in the language-setting dropdown regardless of the current display language, so a locale is legible to a reader of that language even if they can't read whatever's currently selected). `locales/en.ts` is the base language: its own dict is declared as a plain object literal (not `Partial`), and `MessageKey` is derived from its keys (`keyof typeof en`) — every other locale's dict is checked against that key set at the type level (assigning an object literal with an unknown key to a `Partial<Record<MessageKey, string>>` is a compile error) and, at runtime, `t()` falls back to `en`'s value for any key a locale hasn't filled in yet, so a locale can start out partial and grow one key at a time. `index.ts`'s `LOCALES` registers each one (`[{code: "en", selfName: EN_SELF_NAME, messages: en}, {code: "ja", …}]`); `Lang` and the settings tab's language-dropdown options (`languageOptions()`) are both derived from this table, so adding a language is a new `locales/<code>.ts` file plus one line in `LOCALES` — nothing else changes.

`auto` resolves to a concrete language by matching Obsidian's `getLanguage()` against `LOCALES`' codes by prefix (longest code first, so a future more specific locale like `zh-TW` would win over a shorter `zh` that's also a prefix match for the same Obsidian string) — no match, including `null`, falls back to English.

### 17.2 Python (CLI, TUI, hooks, statusLine)

`agentsessions/i18n/` provides the same kind of `t(key, **values)` for strings a human actually reads outside the plugin: the TUI screen, CLI stdout/stderr, the statusLine, and the display labels in `json` output (`status_label`, distinct from the raw `status` value — see §5). It intentionally doesn't cover comments, docstrings, or internal log/exception text (nobody reads `daemon.log` or a Python traceback in a chosen language) — those are plain English. It also doesn't use `gettext`/`locale`; the tables are small enough that plain dicts are simpler and add no dependency.

Each language is one file, `i18n/locales/<code>.py`, exporting a `MESSAGES` dict — `en.py` is the base language (every key `t()` is called with must exist there) and every other locale's fallback for a key it doesn't define. `i18n/__init__.py`'s `_TABLES` registers each one (`{'en': en.MESSAGES, 'ja': ja.MESSAGES}`); adding a language is a new `locales/<code>.py` file plus one line there. Nothing outside `agentsessions/i18n/` changes — every caller does `from … import i18n` and then `i18n.t(...)`, and that keeps working whether `i18n` is this package or, as before, a single module.

English is the default. The language is chosen in this order:

1. If `AGENT_SESSIONS_ID` is set (a session launched by the plugin's daemon) and `~/.agents/sessions/ui.json` has a `language` naming a *registered* language, that value — the plugin resolves `auto` to a concrete value before writing it (§17.1), so this matches the plugin's own display language.
2. Otherwise, the first of `LANG`, `LC_ALL`, `LC_MESSAGES` that is set is matched against the registered languages by prefix, case-insensitively (`ja_JP.UTF-8` → `ja`). No match (e.g. `fr_FR`, with only `en`/`ja` registered) falls back to English. With none of the three set, English.

A CLI invocation with no session context (outside a plugin-launched terminal — an interactive `agent-sessions` in a plain shell, for instance) falls straight to step 2, i.e. the shell's own locale. So does `agent-sessions json …` spawned by the plugin (it runs with Obsidian's own environment), which is why `json live` carries both the raw `status` and the display `status_label`.

One Japanese string is deliberately not translated: `OTHER_GROUP`, the literal `"その他のセッション"`, shared by `config.py` and `plugin/src/sessions/tree.ts`. It's persisted as a key in `sessions.json`'s `folded`, so translating it per language would un-fold the group whenever the language changes. Both the TUI (`tui/app.py`'s `_group_label`, mapping `OTHER_GROUP` to `t("tui.other_group")`) and the plugin (`t("group.other")`, §10.1) show a language-appropriate heading rather than this literal — only the persisted identifier itself stays untranslated.

## 18. Error handling

| Situation | Behavior |
|---|---|
| Can't reach the daemon | Tries to start it; after 3 failures, the exit screen shows why (Python missing, socket couldn't be created) |
| `claude` not found | The exit screen shows "claude not found" with a link to settings |
| `--resume` fails (transcript gone) | Shows Claude's own output as-is, with "Start as new" added to the exit screen |
| `json scan` fails | The list keeps its last successful result; a `Notice` shows the first line of stderr |
| `sessions.json` is corrupted | Moved aside to `.broken-<timestamp>` and reinitialized |
| `keybindings.json` can't be read | Settings shows "unreadable"; changes away from `enter` are blocked |
| `sessions.json.lock` can't be acquired in 2 seconds | The write is abandoned with a `Notice`; a lock older than 10 seconds is treated as abandoned and removed |
| Two daemons start at once | The later one fails to `flock` and exits immediately; the plugin waits 1 second and reconnects |
| `exited.json` is corrupted | Moved aside to `.broken-<timestamp>`, the daemon starts with an empty one |
| `stats-cache.json` is corrupted | The affected file (or entry) is discarded and rebuilt |
| WebGL unavailable | Falls back to the canvas renderer (logged only) |

## 19. Platform support

- **macOS**: the primary platform.
- **Linux, including Linux Obsidian running under WSLg on Windows**: supported. The daemon, CLI, and their Python-side platform branches are exercised in CI (below). A few platform-specific choices:
  - `_claude_pids()` (`sessions/live.py`) resolves `ps` via `shutil.which('ps')` rather than assuming `/bin/ps`, and calls it with `-eo pid=,args=` (works on both GNU/procps and BSD `ps`). A minimal environment with no `ps` at all falls back to a plain liveness check (`_alive(pid)`) — the same result, just without the process list.
  - `bin/agent-sessions`'s shebang is `#!/usr/bin/env python3` rather than a hardcoded `/usr/bin/python3`, since some minimal Linux images (e.g. `python:3.10-slim`) only have `python3` at `/usr/local/bin`.
  - `scan()`'s cache trusts a file's `mtime`/`size` to mean "unchanged" — except within `RACY_WINDOW` (2 seconds) of the current time, which it always re-reads regardless of what the cache says. Some Linux filesystems (observed reliably in Docker's default `/tmp`, essentially never on macOS's APFS) coalesce back-to-back writes to nearly the same `mtime`, which would otherwise make an actively-updating transcript look unchanged and return stale cached content — the same failure mode "racy git" addresses for git's own index.
  - The daemon's socket lives under `~/.agents/sessions/` rather than inside the vault partly because `AF_UNIX` path length is capped at 104 bytes on macOS and 108 on Linux, and a vault path can be long.
  - The terminal's key routing, submit-key labels, default font, and default login shell all branch on platform — see §7.2.1 and §15.
  - Claude Code calls the built-in editor as `<editor> -g <file>:<line>`. Sessions survive Obsidian's exit and reattach with replay when Obsidian runs in its own scope, as GNOME starts apps; started as a systemd *service* unit, Obsidian's exit takes the daemon (same cgroup) down with it. The extra checks for Linux Obsidian under WSLg are in [`testing.md`](testing.md#4-wslg-checks).
- **Windows (native: Windows Obsidian with the agents on Windows)**: supported for Claude Code, Codex and OpenCode, on Windows 10 1809+ (for ConPTY) and Windows 11. Details in §19.1.
- **An agent inside WSL**: supported only with Obsidian in the same WSL2 distribution (Linux Obsidian under WSLg), which is Linux on both sides; its checks are in [`testing.md`](testing.md#4-wslg-checks). Windows Obsidian with an agent in WSL1 or WSL2 is not supported: the agent's hooks, status line, transcripts and processes live on the Linux side, where the plugin cannot start, observe or reattach the session, and under WSL2's default NAT networking the editor round trip cannot reach Windows' `127.0.0.1`. The reasoning is in [`principles.md`](principles.md#4-supported-platforms-are-the-ones-where-agent-and-plugin-share-an-os).
- Obsidian desktop only (`isDesktopOnly: true` in `manifest.json`), since the plugin spawns processes and opens local sockets — neither is available to a mobile or web build. Minimum Obsidian version 1.8.7 (`minAppVersion`): deferred views (§7.5, §23) arrived in 1.7.2, and `getLanguage()` (§17) in 1.8.7.
- Python 3.9+, standard library only: `bin/agent-sessions` runs through `#!/usr/bin/env python3`; a copy the plugin installed names the interpreter it found (§20.1).
- On any other platform (`isSupportedPlatform`: anything but desktop `darwin`, `linux` and `win32`, so mobile and other systems) `onload` stops after loading settings: a notice and a one-line settings tab say why, and nothing else is registered or started.

### 19.1 Windows

The daemon's Unix-only pieces are replaced one by one; the protocol (§4.2), the daemon's session logic and the plugin are shared.

- **Pseudo terminal** (`agentsessions/daemon/conpty.py`, behind `ptyproc.py`): ConPTY through `ctypes`, so the standard-library-only rule holds. Windows' `select` only accepts sockets, so each session's ConPTY output is read by a thread that writes into a socket pair whose other end sits in the daemon's `select` loop like any other fd. Children run in a job object with kill-on-close, so none outlives the daemon. Terminate closes the pseudo console (the child gets `CTRL_CLOSE_EVENT`); kill terminates the job.
- **Starting the daemon**: detached, without a console window, and broken away from the caller's job object when the job allows it, so sessions survive closing Obsidian and a new window reattaches with the replay of §4.3.
- **Transport** (`agentsessions/transport.py`, `plugin/src/backend/transport.ts`): loopback TCP on `127.0.0.1` with a random port. `daemon.sock` and `plugin.sock` are not sockets there but endpoint files holding `{port, token, pid}`. A client first sends the 32-hex-digit token and a newline; a wrong token closes the connection. The token takes the place of the 0600 mode a Unix socket has. Unix keeps Unix sockets.
- **Process checks** (`agentsessions/procs.py`): `os.kill(pid, 0)` is never used — on Windows it terminates the process. Liveness is `OpenProcess` + `GetExitCodeProcess`, and the process list (executable names, in place of `ps`) is a Toolhelp snapshot.
- **Encoding**: stdio is reconfigured to UTF-8 and the launcher sets `PYTHONUTF8=1`; Japanese Windows defaults to cp932.
- **CLI**: the terminal UI (`agent-sessions` with no arguments, `curses`) and `agent-sessions attach` (`termios`) are not available. The other commands work, the built-in editor included: `agent-sessions-code` → `plugin.sock` endpoint → editor pane → Send → exit 0, through the same TCP + token transport.
- **Install** (§20.1): the program goes to `%LOCALAPPDATA%\agent-sessions` (else `~\.agents\sessions\app`) with `bin\agent-sessions.cmd` (sets `PYTHONUTF8=1`, runs the Python found on the bundled script) and the editor shim `bin\agent-sessions-code.cmd`. The plugin runs `python <script>` directly, because Node's `execFile` refuses `.cmd`, and with `windowsHide` so no console flashes (`plugin/src/backend/windows.ts`).
- **Python and `PATH`**: Python is looked up through the `py` launcher (`py -3`), python.org's folders (`%LOCALAPPDATA%\Programs\Python\Python3xx[-arm64|-32]`, `%ProgramFiles%\Python3xx`) and `python.exe` on `PATH`; the Microsoft Store's 0-byte `python.exe` alias is never used. `PATH` is re-read from the registry (user and machine, via `reg.exe`) plus WinGet's `Links` folder, `~\.local\bin` and `%APPDATA%\npm`, so a program installed while Obsidian runs is found without a restart.
- **WinGet buttons**: the install dialog shows **Install Python with WinGet** when Python is missing and **Install Claude Code with WinGet** when Claude Code isn't found, running `winget install --exact --id Python.Python.3.13` (or `Anthropic.ClaudeCode`) `--scope user --silent --accept-package-agreements --accept-source-agreements --disable-interactivity` — per user, no administrator prompt, and only on a click. Without WinGet the dialog explains updating "App Installer".
- **Codex and OpenCode**: found like any program — `PATH` (registry and the extra folders above, with `PATHEXT`), so npm's `codex.cmd`/`opencode.cmd` in `%APPDATA%\npm`, an `.exe` from WinGet, Scoop or Chocolatey, and OpenCode's `~\.opencode\bin`. The daemon starts a `.cmd`/`.bat` through `cmd.exe /d /s /c` (`conpty.py`'s `resolve_command`), escaping each argument that holds a `cmd.exe` metacharacter, space or tab the same way as `cmdShimArgument` below (`daemon/cmdline.py`; plain words stay as they are), so a session name such as `R&D: 50%` in `--name=` reaches the agent intact; the plugin, which runs a shim for `--version` and for Organize (`codex exec`, `opencode run`, `opencode session delete`), builds one verbatim `cmd.exe /d /s /c` line itself (`windows.ts`'s `cmdShimInvocation`: each argument quoted for the C runtime, `cmd.exe`'s metacharacters escaped twice, once for the `/c` line and once for the shim's own `%*` line). Their files are where they are on Unix, under the home folder: `%USERPROFILE%\.codex` (`CODEX_HOME`), and OpenCode's `%USERPROFILE%\.local\share\opencode` and `%USERPROFILE%\.config\opencode` (`XDG_DATA_HOME`/`XDG_CONFIG_HOME`). The process table holds executable names only, so a Codex session's `pid` is not inferred (§3.3) and OpenCode's fallback looks for `opencode.exe`; process trees come from the same Toolhelp snapshot. Codex's new-session id comes from the `session_meta` match alone (no open-file inspection), and folders are compared with `paths.same_folder`. Codex's `--no-daemon` (§7.7) matters most there: without it the TUI first installs Codex's shared background app-server, which refuses a package laid out differently from npm's (WinGet's: "the CLI package does not match this platform or executable"). A slash command's submit key goes to Codex in a write of its own after the paste (`terminal/command-chunks.ts`): the console delivers the paste as keystrokes, and Codex takes an Enter right behind a burst of keys as part of a paste. `agent-sessions new` passes on Windows' own variables (`SystemRoot`, `USERPROFILE`, `APPDATA`, `LOCALAPPDATA`, `TEMP`, `PATHEXT`, `ComSpec`, …; `launch.WINDOWS_INHERITED_ENV_KEYS`) where Unix passes the login shell's few, and names the `.cmd` shim. The built-in editor shim is `agent-sessions-code.cmd` in `VISUAL` (and `EDITOR` for OpenCode) for every agent. OpenCode splits that variable at every space and runs it through `cmd.exe` with its temp file unquoted, and Codex splits it at unquoted spaces (`winsplit`), so a shim folder with a space is named by its 8.3 form, keeping the base name Claude Code looks for `code` in (`windows.ts`'s `windowsEditorShimPath`), and OpenCode gets `TEMP`/`TMP` in 8.3 form when they have a space (`main.ts`'s `editorEnv`).
- **Hooks and `statusLine`**: Claude Code runs them through Git Bash when it is installed and through PowerShell otherwise (Git for Windows is optional). The commands therefore name the launcher unquoted with forward slashes (`C:/Users/…/agent-sessions.cmd hook`), shortened to its 8.3 path when the path contains spaces — the one form both shells run. An install path may contain spaces but none of `"`, `%`, `!`, `^`, `&`, `|`, `<`, `>`, `` ` ``, `$`, `;`.
- **Also run on Windows** (disclosed in the README): `reg.exe`, `py.exe`, and `winget.exe` only on a click. The plugin listens on `127.0.0.1` only.
- **Suspend**: ConPTY has no job control, so Ctrl+Z reaches the agent as a key and §4.3's suspend handling does not run.
- **Tests**: the CI job `python-windows` (§22) runs on `windows-latest`. `AGENT_SESSIONS_OUTFILE` makes `plugin/esbuild.config.mjs` write `main.js` somewhere other than the plugin folder.

## 20. Install, uninstall, and setup

`install.sh [vault]` (or `AGENT_SESSIONS_VAULT=<vault> install.sh`, which takes priority over the argument): symlinks `bin/agent-sessions` and `bin/agent-sessions-code` into `~/bin`, and with a vault symlinks `plugin/` into `<vault>/.obsidian/plugins/agent-sessions`, warns (without failing) if `~/bin` isn't on `$PATH` or `plugin/main.js` hasn't been built, and finishes by calling `agent-sessions setup` (§5) with any remaining arguments to reconcile Claude Code's hooks and statusLine.

`uninstall.sh [vault] [--force] [--purge]`:

1. Checks `daemon --running-count`. With one or more sessions still running, it asks for confirmation (`--force` skips the prompt) before proceeding; aborting leaves everything untouched.
2. `daemon --stop` (a no-op if the daemon isn't running).
3. `agent-sessions setup --remove` (§5) — removes only this project's own hook entries, statusLine, the submit-key and editor-key `keybindings.json` entries, the marked lines in Codex's `config.toml`, OpenCode's `tui.json` keybinds (restored to the user's previous values) and status line entry, OpenCode's status plugin and status line (only files carrying the marker line), and (with a vault) the agent skills (§20.2, only files carrying the marker); other tools' and the user's own entries are always left alone.
4. Removes the `~/bin/agent-sessions` and `~/bin/agent-sessions-code` symlinks, and with a vault `<vault>/.obsidian/plugins/agent-sessions`. A path that exists but isn't actually a symlink (replaced by hand) is left in place, with a note.
5. Only with `--purge`: also deletes `~/.agents/sessions/` (or `$AGENT_SESSIONS_RUNTIME_DIR` if set — the same variable `agent-sessions daemon` reads for its default `--runtime-dir`) and, with a vault, `<vault>/.agents/sessions/` — daemon runtime state and session bookkeeping (folded groups, archive, category colors), respectively.

Both scripts are `#!/bin/sh` (POSIX, checked with `dash -n`/`sh -n`) and safe to run more than once — running either again when there's nothing left to do just reports that.

### 20.1 Installing from inside the plugin

A plugin installed from Community plugins arrives as `main.js`, `manifest.json`, and `styles.css` only, so the program ships inside `main.js`: `esbuild.config.mjs`'s `bundledBackend` serves the virtual module `virtual:agent-sessions-backend` — `BACKEND_FILES` (every `.py` under `agentsessions/` plus `bin/agent-sessions` and `bin/agent-sessions-code`, as plain text keyed by their path in an install directory) and `BACKEND_VERSION` (the plugin version plus a hash of those files). Nothing is downloaded; the code a user runs is the code in the reviewed release. `backend/bundle.ts` holds everything short of the UI and has no `obsidian` dependency.

- **Where** (`installCandidates`, `chooseInstallDir`): the first usable of `$XDG_DATA_HOME/agent-sessions` (only if absolute), `~/.local/share/agent-sessions`, `~/.agents/sessions/app`. A candidate is skipped if its path has anything outside `[A-Za-z0-9._/+@,:~-]` (it goes into a double-quoted hook command and, unquoted, into `$VISUAL` — a space in `~/Library/Application Support` or in a home directory would break both), if it is the vault or inside it, or if its nearest existing ancestor isn't a writable directory. Checking creates nothing.
- **Python** (`findPython`): the login shell's `python3` (`locateProgram`, the same search as the agents' binaries, §7.7), then `/opt/homebrew/bin/python3`, `/usr/local/bin/python3`, `/usr/bin/python3`; the first reporting 3.9+ wins. On macOS `/usr/bin/python3` is a stub until the Command Line Tools are installed, and running it opens an installer dialog, so it's tried only once `xcode-select -p` succeeds.
- **Layout** (`writeBundle`): the repository's own — `bin/`, `agentsessions/`, plus `install.json` (`{version, python}`). The launcher's shebang is replaced with the interpreter found, so hooks and the daemon run under it whatever `PATH` they inherit; `bin/*` are made executable. Files go to a staging directory first and are swapped in per top-level entry, so a failed write leaves the previous version intact and a module removed upstream doesn't linger.
- **Hooks**: with Claude Code enabled, the install runs `<launcher> setup --command <launcher>`, naming the launcher through `$HOME/…` when it's under the home directory (`hookLauncher`). With OpenCode enabled it also runs `<launcher> setup --opencode`, and enabling OpenCode in the settings tab runs the same command (`main.ts`'s `installOpencodePlugin`); disabling it runs `setup --remove-opencode`, which removes only that file. On load, an enabled OpenCode whose status plugin the plugin never installed (first-run detection just enabled it, with the program already there) gets `setup --opencode` once too (`applyAgentConfigOnce`, recorded as `opencode` in `agentConfigApplied`; the install and switching OpenCode on record it as well). `installOpencodePlugin` reads the `opencode-plugin: <status>` line and says what happened in a notice (installed, updated, already up to date, a foreign file left alone, or the error) — a plugin folder that can't be written is reported and never fails the rest of the install. It runs with OpenCode's `XDG_CONFIG_HOME` (§7.7).
- **Which program runs** (`main.ts`'s `agentSessionsPath`): the settings path if set; else `~/bin/agent-sessions` if it exists (`install.sh`); else the installed copy. `backendAvailable()` is whether that file exists. While it's `false`, the index's `scan`/`live`/`detail` return empty results instead of failing, and the side panel's empty state offers the install.
- **Updates**: `onload` finds the install (`findInstalled` over the same candidates) and rewrites it when `install.json`'s version differs from `BACKEND_VERSION`, keeping its interpreter (and, with OpenCode enabled, running `setup --opencode --update-only`, so an existing plugin file matches the new program and none is ever created by the silent refresh); if that interpreter is gone it's left for the user to reinstall. The agent skills are written on the same occasion, and also on every load when it was written for something else (§20.2).
- **UI**: the side panel's empty state and **Settings → agent-sessions program** open `InstallBackendModal`, which shows the location, the Python, the Claude Code change, and (with OpenCode enabled) the OpenCode plugin files it adds (status plugin and status line) — the `install.opencode` row (or why Python or a location couldn't be found, with a "Check again") before anything is written. The settings row reinstalls or removes a copy the plugin installed; removing stops the daemon, runs `setup --remove` (which also deletes OpenCode's status plugin and status line and the agent skills in the vault), and deletes the files (`removeBundle`, which leaves the directory if something else lives in it). A program set in settings or linked by `install.sh` is only reported there. The dialog also lists the vault folders the agent skills go into (`install.skills`, or that no agent is enabled), and the install runs `setup --skills` (§20.2).

### 20.2 Agent skills

Two skills ship inside the program, each a folder of templates under `agentsessions/skills/` (bundled into `main.js` with the `.py` files, and the `.md` files of those folders with them: `plugin/esbuild.config.mjs`), and are installed by `setup --skills` into the vault, as *project* skills. `skills.SKILL_NAMES` lists them; `skills.template_files(name)` is every file in a skill's template folder, `SKILL.md` first. All of a skill's files are rendered, written, marker-tagged and removed alike.

**`agent-sessions`** (`SKILL.md` only) lets agents started in the vault read usage, look at other sessions, and start a session:

| Part of the skill | Does |
|---|---|
| Usage statistics | `agent-sessions stats` (5-hour/7-day windows per agent) and `agent-sessions show` (a session's tokens, cost, tools) |
| Other sessions | `agent-sessions sessions` and `show` (names, agents, folders, status, last messages) |
| Start a new session | `agent-sessions new` (§5.1): a session in a folder (default: the caller's), optionally named, on any enabled agent (default: the caller's own), Claude Code optionally with Remote Control; `--prompt` only with text the user gave. The body says to do this only when the user explicitly asks |

**`agent-sessions-help`** (`SKILL.md` and `reference.md`) answers questions about using the plugin in the user's language. `SKILL.md` is short: its `description` makes agents use it for questions about using Agent Sessions in Obsidian (side panel, Session Manager, tabs, categories, renaming, organize, restart, the built-in editor, the welcome guide, usage and limits, settings, install, update and removal, supported platforms, troubleshooting), and its body says to read `reference.md` first, answer in the user's language with the UI labels of the user's language, say "not documented" rather than guess, say plainly when a setup is unsupported, and point to the `agent-sessions` skill for what the agent itself can do (usage numbers, listing sessions, starting one on request) while leaving renaming, organizing and settings to the user. `reference.md` holds the facts by task, with the exact English and Japanese labels of menus, settings and commands; `tests/skills/test_skills.py` checks that those labels still match `plugin/src/i18n/locales/en.ts` and `ja.ts`. It names no launcher and no agent set, so its copies are the same whichever agents are enabled.

**Rendered for the enabled agents.** Each file is a template; `skills.render(name, launcher, agents)` fills it for the agents `setup --skills` receives in `--agents`, so the text names only enabled agents. Lines between `{{if cond}}` and `{{endif}}` (or the same pair inside a line) are kept when `cond` holds (`claude`, `codex`, `opencode`, `multi`, `windows`, `late`; `&`, `|`, `!`). In the rendered text: the `description` and the body name only the enabled agents; `--agent` lists their ids in `new` and `sessions` and is left out when one agent is enabled; `stats` and the 5-hour/7-day windows appear only with Claude Code or Codex enabled, and a note says OpenCode has no windows when OpenCode is enabled (with no other agent, `stats` is not offered at all); `--remote-control` and the Remote Control URL appear only with Claude Code, the note that Codex cannot be named at launch only with Codex, and the note that a session is recorded after its first message only with Codex or OpenCode (named as enabled). Every copy carries the same text, whichever folder it is in. `install` renders once per run and writes each wanted folder's files when their text differs, so adding or removing an agent rewrites every remaining copy as well as adding or deleting that agent's folder.

Both skills may be invoked by the model (so statistics and session lookups work without being asked by name); starting a session is limited by the body's own instruction, not by a per-agent switch (`disable-model-invocation` and Codex's `agents/openai.yaml` policy are not used). The text is English whatever the UI language is; the agent answers in the user's language. Arguments: Claude Code appends what follows `/agent-sessions` as `ARGUMENTS: …` when the body has no placeholder; Codex and OpenCode give the model the text after the skill's name. The `agent-sessions` body names the launcher by an absolute path chosen at install time (`$HOME/…` when under the home directory) in double quotes, and its frontmatter carries `name` and `description` plus the Claude Code key `argument-hint`, which Codex and OpenCode ignore; the help skill's frontmatter is `name` and `description` only.

**Earlier versions** installed three skills (`agent-sessions-new`, `-stats`, `-info`, the first with a Codex `agents/openai.yaml`). Every install removes those folders wherever they are, but only files carrying the marker.

**Where.** Claude Code reads `<vault>/.claude/skills/`; Codex reads `<vault>/.agents/skills/` (and `.codex/skills/`) and not the Claude folder; OpenCode reads `.claude/skills/`, `.agents/skills/` and `.opencode/skills/`, and lists a name that appears in two of them once. So each enabled Claude Code or Codex gets its folder, and OpenCode gets `.opencode/skills/` only when it is enabled alone (`skills.wanted_dirs`); and no agent lists a skill twice. Nothing is written to `~/.claude`, `~/.agents`, `~/.codex` or `~/.config/opencode`. Agents started in a folder other than the vault do not see the skills.

**Marker.** Every file written carries `agent-sessions:managed` (an HTML comment after the frontmatter in `SKILL.md`, at the top of `reference.md`; a `#` comment in `openai.yaml`). Each file is judged by its own marker: a file at one of our paths without it is someone else's and is never overwritten or removed, and the skill's other files are still written; `setup` reports it (`foreign`). Removal deletes our files (all of both skills'), then the skill folders and the `.claude`/`.agents`/`.opencode` folders it leaves empty, and nothing else.

**When.** There is no setting: the skills belong to the program. `main.ts`'s `installAgentSkills` runs `setup --skills` against the program `agentSessionsPath` resolves to (the bundled install, `~/bin/agent-sessions` or the settings path) and, when that file does not exist, does nothing, so the vault is never written to without a program. It runs after the install dialog's install and on Reinstall (always), whenever an agent is enabled or disabled (always, so a disabled agent's copy goes), and on every load unless the skills are current: `settings.agentSkillsStamp` records the program version (`BACKEND_VERSION`), the launcher named in the skill and the sorted set of enabled agents of the last successful run, and a load whose current values differ (a plugin update, a different launcher, changed agents) runs `setup --skills` again and saves the new stamp; a load whose values match runs nothing. A failing run leaves the stamp alone, so the next load retries. The refresh of the bundled program after a plugin update goes through the same call, and creates the skills when they are missing (`--update-only` applies to OpenCode's status plugin file only). `setup --remove --vault …` (Remove) takes the skills away and the stamp is cleared. `syncAgentSkills` (`backend/agent-skills.ts`) holds the decision. The old `installAgentSkills` setting is ignored when saved data is read.

### 20.3 Welcome guide

**Flow.** `ui/onboarding-model.ts` (pure, no `obsidian`) holds the steps (`language`, `about`, `setup`, `first-session`, `tabs`, `rename`, `editor`, `more`, `whats-new`), their states (pending, done, skipped), the saved progress (`settings.onboardingProgress`, validated on load by `sanitizeProgress`), the resume rule (`resumeProgress`: only when the guide's session is gone are the unfinished session steps asked again), `WHATS_NEW` (items keyed by the version that introduced them) and `shouldOpenOnStartup`. A first install runs every step; an update run is `setup` (program not installed) and `whats-new` (items since `onboardingShownVersion`), and nothing opens when there are none. `ui/onboarding-flow.ts` holds the modal's pure helpers (moving between steps, steps an agent cannot do, install commands, picture timeout).

**Modal.** `ui/onboarding-modal.ts` renders the step being shown and saves the progress after every change. The language step is a dropdown (Auto with the resolved language, English, 日本語), written in the language currently in effect, and applies the choice at once (`applyLanguage` plus `settings-changed`). `setup` reuses `installPageState`, `openInstallBackend`, `detectAgents`, `setAgentEnabled` and `requestSubmitKey`; a missing agent shows its vendor's install command to copy (nothing is run for the user; `agentInstallHelp`: on Windows `npm install -g @openai/codex` and `npm install -g opencode-ai`, and for Claude Code the WinGet button of §19.1 instead). `main.ts` decides at startup (`maybeShowOnboarding`): open from the top, open the update run, or show one notice offering to continue an unfinished run. The modal and the notice are for the main window only.

**Coach and tracker.** The operation steps hand over to `ui/onboarding-coach.ts`, a small draggable window in the main window that never takes focus. `sessions/onboarding-tracker.ts` (pure) turns events into "this step is done": the guide's session going `busy`/`shell` → `idle` (`registry.onIdle`), the active tab (`active-leaf-change`), a changed name or category on the index (`sessions/onboarding-watch.ts`) and the built-in editor's `send` result (`handleEdit`). Only events after a step was entered count, so nothing is ticked by an action the user did not take. The first session is started without a name, so nothing is typed into it. Codex and OpenCode offer the tab switch only (`stepAvailableFor`).

**Pictures.** `ui/onboarding-image.ts` draws an `<img>` (loaded eagerly, since a lazy picture below the modal's visible area never starts; `referrerpolicy="no-referrer"`; no `fetch`) from `https://raw.githubusercontent.com/kulikala/obsidian-agent-sessions/<manifest.version>/docs/onboarding/<lang>/<scene>.png` (`onboardingImageUrl`) in a fixed-ratio frame, with a text description while loading, a note after an error or 10 seconds, and a link that turns `onboardingImages` off; with the setting off there is no `<img>`. `ONBOARDING_SCENES` is the one list of scenes. A development build (`__AGENT_SESSIONS_DEV__`, an esbuild define) reads `onboardingImageBase` from the saved data to point the pictures at another folder; the production bundle has no code that reads it.

The guide adds no logic of its own to installing: the setup step calls `openInstallBackend`, the agent toggles call `setAgentEnabled` (the settings tab's own handler, with its Codex/OpenCode/skill side effects and the keep-one-enabled rule), and the submit key goes through `requestSubmitKey` (same choices, confirmation, write and sync as the settings tab; `cmd+enter` stays macOS-only). The install status comes from the single function `installPageState`.

## 21. Release process

The plugin version lives in `plugin/manifest.json`, mirrored at the repo root (`manifest.json`) and tracked per-version in `versions.json` (the minimum Obsidian version each plugin release requires). `cd plugin && npm version <patch|minor|major>` runs `plugin/version-bump.mjs` as npm's `version` hook: it writes the new version into `plugin/manifest.json`, copies that file to the repo root (the review bot and BRAT only read the root copy), and — only if the version is new — records `{version: minAppVersion}` in the root `versions.json`. The hook then `git add`s all three files so they land in npm's version commit. `plugin/.npmrc` sets `tag-version-prefix=""`, so the git tag `npm version` creates is the bare version number (e.g. `0.1.1`, not npm's default `v0.1.1`) — exactly matching `manifest.json`'s `version`, which Obsidian's release tooling expects.

Pushing the resulting tag runs `.github/workflows/release.yml` (on any tag): it checks out the repo, runs `npm ci` and `npm run build` in `plugin/` (Node 20), and creates a **draft** GitHub Release for that tag with `main.js`, `manifest.json`, and `styles.css` attached. A maintainer reviews and publishes the draft by hand — nothing here publishes automatically.

## 23. Verification and Obsidian's quirks

Hands-on verification goes through the Obsidian CLI (`obsidian plugin:reload id=agent-sessions`, then querying and driving the already-running Obsidian instance's commands and DOM). Before and after, `document.querySelectorAll(".modal-container").length === 0` checks that no modal was left open. Any tab or session created as a side effect is folded/`forget`-ten afterward.

Things worth knowing:

- **`Modal.open()`** stores the selection it restores on close in `this.selection` — a `Modal` subclass must not reuse that field name for something else.
- **Deferred views**: a tab never brought to front is a `DeferredView`, whose icon and title come from whatever was last saved, not computed live (§7.5, §12) — they only update when written directly into the DOM.
- **`ResizeObserver` doesn't fire on a hidden element**: a background tab or a folded panel either reports zero size or isn't observed at all. The terminal's `ensureAttached()` only runs once it sees a non-zero size for the first time, so a tab staying disconnected until it's brought to front is expected behavior, not a bug (§7.1).
- **`tui: fullscreen`**: Claude Code redraws its own screen and keeps its own scroll position, so nothing accumulates in xterm's scrollback (`buffer.length === rows`). Marker-based jumping is assumed not to work in this mode, and falls back to sending Claude's own scroll keys instead (§7.3).
- The Obsidian CLI's synthetic events don't reliably trigger `showAtMouseEvent` (a right-click menu), so that path is checked by hand instead.

**Before reloading the plugin**: `plugin.reloadSafety()` (`main.ts`; the pure part in `terminal/reload-safety.ts`) returns `{editorOpen, recentKeyMs, drafts}` so whoever is about to reload can tell whether text is being typed: `editorOpen` is true while a built-in editor pane is open in any tab; `recentKeyMs` is the time since the last keydown in a terminal tab or the editor pane (`noteKey`, one number written per keydown; `null` before any); `drafts` names the sessions whose prompt line holds unsent text (`TerminalView.promptHasDraft`).

## 24. Security and privacy

Everything this project writes outside the vault lives under `~/.agents/sessions/` (the daemon's runtime state — see §3's table) with the containing directory at mode 0700 and the sockets at 0600, so only the invoking user's own processes can reach them. On Windows the endpoints are loopback-only TCP ports (`127.0.0.1`) and every connection must first present the random token from the endpoint file, which sits in the user's profile; a wrong token closes the connection. Session bookkeeping inside the vault (`<vault>/.agents/sessions/sessions.json`) holds only folded-group names, the archive list, and category-color assignments — no transcript content or prompts.

Two features send session text, each only on the user's explicit action. Organize names and categories (§11): when the user presses Suggest (or Suggest again for unchecked; also from a row's "Suggest name and category…" for one session), excerpts of up to 30 sessions (folder, first prompt, last three prompts, last reply, and the existing category names with example session names) go to the user's own agent CLI (Claude Code `claude -p`, else Codex `codex exec`, else OpenCode `opencode run`, headless), under the user's account. Token efficiency (§13.5): when the user presses Analyze, the masked summary and excerpts of that agent's own conversations (at most 60,000 characters, no tool results or file contents) go to that same agent and provider (`claude -p`, `codex exec`, `opencode run`; a local provider's conversations to its local model), run in an empty folder that is removed afterwards; the statistics cache holds no conversation text. Nothing is sent otherwise.

The plugin also writes the `agent-sessions` and `agent-sessions-help` skills into the vault's own skill folders (§20.2) whenever the program is installed, marked so that only its own files are ever changed or removed. Claude Code's own files (`~/.claude/projects/*/*.jsonl`, `~/.claude/sessions/*.json`) are read-only from this project's point of view; nothing here ever writes to them. `~/.claude/settings.json` and `~/.claude/keybindings.json` are the two exceptions — `agent-sessions setup` edits `settings.json`'s hooks and `statusLine`, and the plugin can edit `keybindings.json`'s `Chat` context when the submit key isn't `enter` or the editor key isn't `ctrl+g` — Only entries this project recognizes as its own are ever touched or removed; `settings.json` is also copied to a timestamped backup (`settings.json.bak-<timestamp>`) before `setup` or `setup --remove` writes it. `keybindings.json` edits are limited to the `Chat` keys of the submit key (two) and the editor key (two) (plus `$schema`/`$docs` when missing) and take no backup.

The daemon's per-session output buffer (up to 1 MiB) lives in the daemon process's memory only; it is never written to disk. `daemon.log` holds only the daemon's own operational messages (start/stop, errors) — not session output — since `--detach` redirects the daemon process's own stdout/stderr there, not a child PTY's. No API key, token, or credential is handled by this project directly; `claude` manages its own authentication, and this project only launches it and relays its terminal I/O.
