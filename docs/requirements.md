# Agent Sessions requirements

Opens and manages Claude Code, Codex, and OpenCode CLI sessions inside Obsidian. Three pieces make up one tool: the plugin (Obsidian), the daemon, and the CLI/TUI.

## Terms

- **Session**: one Claude Code, Codex, or OpenCode conversation. For Claude Code, `~/.claude/projects/<project>/<id>.jsonl` is the source of truth and the ID is Claude Code's own session ID; for Codex, `~/.codex/sessions/**/rollout-*.jsonl` and the ID is Codex's own thread ID; for OpenCode, a row of its SQLite database `~/.local/share/opencode/opencode.db` (`$XDG_DATA_HOME/opencode/`) and the ID is OpenCode's own session ID (`ses_…`).
- **Agent**: which CLI a session belongs to — Claude Code, Codex, or OpenCode (R-M).
- **Name**: the name set via `/rename` (Claude Code: the transcript's `custom-title` line; Codex: its own thread name; OpenCode: its own session title, or a name set in the plugin). A name of the form `Category: Name` groups by everything before `: `.
- **Running**: a session whose PTY the daemon is holding.
- **Status**: for Claude Code, the value it writes to `~/.claude/sessions/<pid>.json` — `busy`/`shell`/`idle`/`waiting` (waiting on a dialog for an answer); Codex has no such ledger file and is inferred from its transcript's tail instead; OpenCode's comes from a status plugin the program installs into OpenCode's config (design §3.3).
- **Attach/detach**: a tab connecting to, or disconnecting from, a running session's PTY. Detaching doesn't stop the session.

## Scope

| Area | Covered here |
|---|---|
| Session list GUI, terminal, daemon, restore, fonts, renaming, state display and notifications, path linking, `@` insertion, jumping to prompts/responses, CLI/TUI | R-T, R-S, R-D, R-A, R-N, R-C (design §4–§12) |
| Multi-agent (Claude Code / Codex / OpenCode): settings, auto-detection, launch, display | R-M (design §3.3, §7.7) |
| The built-in editor (inside the plugin) | R-E (design §7.4) |
| Token aggregation (per-session and by range), 5-hour/7-day window statistics, Stretch your usage limit (token efficiency analysis) | R-S12, R-S13, R-S17 (design §13) |
| Remote Control server, scheduled-run display | R-S20, R-S21 (design §8, §9) |
| Uninstalling | R-U (design §20) |
| Platform support (macOS, Linux, Windows) | R-P (design §19) |
| Release process | R-REL (design §21) |
| An IDE bridge (accept/reject diffs, live selection updates) | Undecided. Out of scope |

Agent CLIs other than Claude Code, Codex, and OpenCode (agy, …) are a future direction (design §25); the data model and screens carry a general `agent` field, not just these three.

## Requirements

### R-T Terminal

- R-T1 A tab is dedicated to one CLI agent (Claude Code, Codex, or OpenCode — R-M) — it never falls back to a plain shell. When the agent's process exits, the tab shows an exit screen (Resume / Close).
- R-T2 Font family and size are configurable. Each tab can also change its own size (Cmd +/Cmd −/reset on macOS, the non-macOS equivalents in R-T5c) independently, and keeps that size across a restore.
- R-T2a Terminal padding is configurable: comfortable (default), compact, or none — "none" is meant for laying tabs out in splits.
- R-T3 No clipped characters at the right edge. No flicker while a session is active. Japanese text, emoji, and box-drawing characters keep correct widths.
- R-T4 Colors follow Obsidian's own theme (light/dark) and update when the theme changes.
- R-T5 Every key Claude Code itself uses (Esc, Ctrl+C, arrow keys, Tab, and more) always reaches the terminal — Obsidian's hotkeys never intercept them.
- R-T5a One **submit key** setting (Enter/Shift+Enter/Ctrl+Enter/Option+Enter/Cmd+Enter, default Enter; Cmd+Enter is macOS-only — R-T5c). Any other Enter combination becomes a newline. Applies to every agent's tab; Claude Code's and Codex's own keymaps are rewritten to match (R-M10), OpenCode's isn't (R-M11).
- R-T5b Changing the submit key writes to Claude Code's own `keybindings.json` (`Chat` context) immediately — not only at startup or through a separate confirmation step — and also cleans up any stale alternate-submit binding left over from a past choice or version. The settings tab shows the result (written / already matched, nothing to write / couldn't be written) every time, re-reads the file every time it opens and offers to reconcile a mismatch, and explains that the change affects Claude Code everywhere, including sessions started outside Obsidian, where whether a real terminal can even tell the chosen key apart from plain Enter depends on that terminal. When Codex is also enabled, the same action syncs its own config too (R-M10), and the explanation names both.
- R-T5c On platforms other than macOS, Ctrl (not Cmd) is Obsidian's own hotkey modifier, and Claude Code itself uses many Ctrl combinations. The default routes every Ctrl-combination to the terminal; only Ctrl+Shift+C (copy selection), Ctrl+Shift+V (paste), Ctrl+Shift+=/−/0 (font size), Ctrl+Shift+W (close tab), Ctrl+Shift+P (command palette), Ctrl+Tab, and Ctrl+, go to Obsidian instead. Plain Ctrl+W and Ctrl+P (which Claude Code's own input line can use for word-delete and history) always reach the terminal.
- R-T5d The submit-key setting offers Cmd+Enter only on macOS (a non-macOS Super/Windows key doesn't reliably reach the browser — a window manager can intercept it first); the button/statusLine symbols and labels for the other four choices are shown in a form appropriate to the platform.
- R-T6 Multiple tabs stay independently stable when open at once. Closing a tab leaks no output and leaves no memory behind.

### R-M Multi-agent (Claude Code / Codex / OpenCode)

- R-M1 Settings has an "Agents" section: a sub-heading for each of Claude Code, Codex, and OpenCode (icon + name, its enabled toggle on the same row), then that agent's own path (empty = auto-detect), multi-line environment variables (`KEY=VALUE` per line), and detection result (OpenCode also has its launch option, R-M12) — not one flat list where agents' identically-named fields are told apart only by position. At least one agent stays enabled at all times. A disabled agent's path/environment/detection rows are dimmed, not hidden.
- R-M2 The first time the plugin ever runs with no saved agent settings, it auto-detects each agent — a login shell's `command -v`, then the same probe in an interactive shell (catches a version manager like mise/asdf/nvm/volta whose shell integration only loads interactively), then a list of common install locations aware of those version managers — and enables whichever it finds; if none is found, Claude Code stays enabled. Each agent has its own "Find again" button that re-detects just that one agent any time and shows the result and detected version, without changing any toggle itself (unless it found a still-disabled agent, which shows an inline "Enable" button next to the result).
- R-M3 Starting a new session offers a choice of agent only when more than one is enabled (with exactly one enabled, that one is used without asking); the choice made is remembered as the default for next time.
- R-M4 Claude Code, Codex, and OpenCode sessions are listed, sorted, grouped, and filtered together — no agent-specific split in the side panel or the Session Manager. A small icon (not a brand logo) on each row and in the detail pane shows which agent a session belongs to.
- R-M5 The submit-key setting and Enter interception (R-T5a–d) apply to Claude Code, Codex, and OpenCode tabs (R-M10, R-M11).
- R-M6 Renaming/compacting an existing session (R-S6) works the same way regardless of agent, except that OpenCode has no `/rename`: its name is kept by the plugin and shown in place of OpenCode's own title, and nothing is sent to the OpenCode TUI. A session can be named at the moment it's created in every agent: Claude Code (`/rename` once it is ready), Codex (`/rename` as soon as its input box is on screen and empty, before any message; checked again, and sent once more if Codex didn't take it, once the session is linked to its thread id) and OpenCode (the name is held by the plugin and attached once OpenCode's session id is known). The name shows in the tab title and the side panel from the start.
- R-M7 The detail pane's model/effort badges fall back to the most recent turn's values (from `json detail`) for an agent whose status line the plugin doesn't read (Codex, OpenCode); "Default" if neither that nor statusLine has a value.
- R-M8 A binary resolved through a version manager may need its own directory on `PATH` at launch (e.g. a `#!/usr/bin/env node` wrapper script) — every launch prepends it, regardless of how the binary was found.
- R-M9 A new Codex or OpenCode session's real (thread / session) id isn't known when the tab opens — Codex creates its transcript only after the first turn, and OpenCode can't be told an id. The plugin starts it under a placeholder id. The plugin keeps polling to learn it for as long as the tab stays open, and once learned, that id becomes the session's permanent identity everywhere (tab, row, one-session-one-tab matching) — the same as Claude Code's session id always is.
- R-M10 The submit-key setting also applies to Codex, by writing its own `config.toml` (under `CODEX_HOME`, default `~/.codex`) — one fixed key pair whenever the setting isn't Enter (`tui.keymap.composer.submit`/`tui.keymap.editor.insert_newline`, since Codex's own keymap has no Cmd/Super modifier to bind a per-choice key to; the plugin's own key interception translates whichever of the 4 non-Enter choices is configured into the same bytes either way), removed again when it's set back to Enter. Every line this writes is marked so `uninstall.sh`/`setup --remove` can clean it up without disturbing anything else in the file; a pre-existing, unmarked key for the same purpose is never overwritten (a warning names it instead). Independently, if Codex's own `status_line` isn't set at all, the plugin writes a default one that mirrors Claude Code's own statusLine content — never overwriting an already-set one, the plugin's own past write included. This happens when the program is installed or reinstalled (the install dialog and the welcome guide), when Codex is switched on (first-run detection included), and on load for an enabled Codex the plugin has never set up; once done, a load doesn't add a `status_line` the user removed. Codex's own terminal-title text (R-A1's title-based signal) is read but never written to.
- R-M11 OpenCode's keymap is never rewritten: it submits on Enter and takes Ctrl+J as a newline. The tab sends Enter (`\r`) for the chosen submit key and a newline (`\n`) for every other Enter combination, whatever the setting is.
- R-M12 OpenCode has a launch option: start it directly (`opencode`, or `opencode --session ID` to resume), or through `ollama launch opencode --model M -y -- …` to use a local model. The model is picked from `ollama list` or typed in; starting through Ollama with no model chosen is refused with a notice rather than opening Ollama's own picker.
- R-M13 OpenCode's busy/idle/waiting state comes from a small OpenCode plugin the program installs (`~/.config/opencode/plugins/agent-sessions.js`) when OpenCode is enabled, and updates with the program; Remove and `setup --remove` delete it. A file that isn't ours is never overwritten. Without the plugin, a running turn is still detected from the database, but waiting is not.
- R-M14 The OpenCode session list shows top-level sessions with at least one user message; sub-agent sessions, archived sessions, and sessions started by `opencode run` are not listed. OpenCode has no rate-limit windows, so it has no limit bars or window statistics; its per-session token usage and cost come from the figures OpenCode stores.

### R-S Session management (GUI)

- R-S0 Three views: the **side panel** (right sidebar — nav, list, detail, and rate limits; the list/detail split is draggable, and the detail area keeps the dragged height across restarts), the **Session Manager** (a main-area tab — the full session tree and management actions; the default view for a new tab), and the **terminal** (a main-area tab).
- R-S1 The manager's tree is ordered "category groups → Other (uncategorized and unnamed sessions, one section) → Archive (only when 'Show archive' is on)". Each section is ordered by last-updated, most recent first. Groups and Other are individually foldable, and folded state persists.
- R-S2 Last-updated is the time of the last user message or assistant response — not a hook or notification timestamp, and not a file's own mtime.
- R-S3 A child session (`entrypoint` other than `cli`, an `agent-setting` line present, or `sessionKind: bg`) is excluded from Other unless it has a name.
- R-S4 The side panel's list is "open tabs → running (no tab) → recent, N items". Every open tab is under "open tabs", including one whose session has no record yet (a new session before its first message, a Codex/OpenCode tab not yet linked to its id): it shows the agent, state and the name it was given, and is replaced in place by the real row once there is one. Each row shows a category chip, then the name with the category stripped, then a relative last-updated time ("just now" / "N min ago" / "N h ago" / "yesterday" / "N d ago", falling back to a locale-formatted short date past a week, e.g. "9/25" or "2025/09/18" with the year included once it's not the current one; the absolute date and time is in a tooltip). Status stays in sync, the frontmost tab's row is highlighted (bold, a background, and a left accent bar — still distinguishable from an asking/waiting row's own, more urgent styling when both apply at once), and clicking a row switches to that tab. The name never shrinks past a minimum width — if the row gets too narrow to fit everything, the time is what disappears, not the name. The rate-limits area shows usage percentages and a countdown to reset (no "resets in" label, just the time itself) for every enabled agent (a small agent icon at each row's head), laid out so all the bars are always the same length regardless of how wide the percentage/countdown text is. Each row's own window label is always the compact form ("5h"/"7d"/"30d"; the long form, e.g. "5-hour window", is in a tooltip instead; too narrow an area for the long form to ever be worth showing directly, unlike the manager's own wider stat cards). Claude always shows its 5-hour/7-day pair; another agent shows one row per window it actually reports a tracked percentage for — the usual 5h/7d pair, a single non-standard window (e.g. a 30-day-only plan), more, or none. Clicking the area re-reads/re-fetches the latest usage data immediately, for every shown agent.
- R-S4a With no sessions at all in any of the three sections, the list shows a centered wordmark, a one-line description, and a "New session" button in place of being blank. If no agent is enabled, or none of the enabled agents' binaries can be found, that button is replaced with one that opens settings instead. The rate-limits area is unaffected either way — it's shown whenever there's usage data on disk to show, regardless of the session list.
- R-S5 Clicking a row opens that session's tab. **If a tab for that session already exists, the view switches to it** — opening from the list never creates a second tab for the same session (splitting or duplicating a tab intentionally can, per R-N4).
- R-S6 Every row's right edge always has a `⋯` (rename via `/rename`; move to category, disabled when the session has neither a name nor a first prompt yet to attach one to; compress via `/compact`, disabled if the last command already was `/compact`; archive, or unarchive if already archived; restart session, when running (ends the agent and resumes the same conversation in the same tab, to pick up changed settings, hooks, skills, or environment; asks first if the session is busy); end session, when running; session analysis; copy ID). Right-click opens the same menu. No session-level action lives in the nav row (new/manager/`⋯`).
- R-S7 A new session comes from a dialog with a single combined input: a category chip, then free text for the name (typing a suggestion, `:`, or pasting a `Category: Name` string all recognize the category and strip it from the text). The name is optional — a session can start unnamed. The rename dialog uses the same input, pre-split into the current category and name. Naming is reflected in the tab title immediately, even for a tab never brought to front. Category color is fixed and shared between the side panel and the manager. New sessions always start in the vault's root folder. If a name was given at creation, Claude Code gets `/rename` right after starting, Codex as soon as its input box is ready, and OpenCode gets the name when its session id is known (R-M6).
- R-S8 Renaming (`/rename`) and compressing (`/compact`) apply immediately by sending the command to the session. With no open tab, the plugin attaches temporarily; if the session isn't running at all, it's started in the background, the command is sent, and it's stopped again with `/exit`. A draft in progress is stashed before sending, Claude Code only (it restores the stash automatically afterward) — skipped for any other agent, whose own keybinding for it isn't known (R-M5).
- R-S9 Management state (folded groups, archive, category colors) lives in `<vault>/.agents/sessions/sessions.json`.
- R-S10 Opening the manager never starts `claude`. **Only choosing "New" or clicking a row starts a session.**
- R-S11 The detail pane (shared by the side panel and the manager) shows the name, badges for model/effort/rc (rc: a hollow circle when disconnected or unknown, a solid green circle when connected), the session's state (its icon, name and a one-sentence explanation, with a tag for its attention kind, Needs input or Needs review, when it has one), a context-usage donut (with a separate mark right after a compact), total tokens and cost, the most recent prompt and response (truncated, click for the full text), tools, folder, and ID. With nothing selected, it shows the frontmost tab's session.
- R-S12 The manager is the **usage-analysis** view: a session list on top, a resizable analysis area below (height persists; the whole area's own resize and click-to-refresh apply regardless of how many agents are shown). With 0 or 1 agent enabled, analysis is one panel under a single "Analysis" heading that folds the whole area (state persists). With more than one agent enabled, that single wrapper is gone: each agent gets its own independent, top-level panel with its own heading ("Claude Code analysis"/"Codex analysis", icon included), always stacked one on top of the other regardless of width; each panel folds on its own (persisted per agent), independent of the others, and a folded panel still shows a small usage percentage next to its heading. Claude's panel always shows its 5-hour/7-day pair, even as placeholders before the first fetch; every other agent's panel only shows a stat card and a per-category cost bar for a window it actually has tracked usage for (not a fixed 5-hour/7-day pair, and no placeholder for a window it was never tracking at all; a window's own length picks its label, e.g. "5-hour window"/"7-day window"/"30-day window"; a one-line message instead of any cards when that agent has no tracked window yet), counting only that agent's own sessions. Cost and call/session counts of 1,000 or more are comma-grouped throughout the analysis area (and everywhere else a raw, non-abbreviated count or a dollar amount is shown — tables, cards, bars, the detail pane, the session-analysis modal, tooltips), in the plugin's own display language. The list itself stays one combined, agent-mixed table regardless (not split by agent) — a sortable table (state mark, name, last-updated, model, effort, 5h cost, 7d cost, folder — full model/effort values in a tooltip; group headings show a category chip, count, and 5h/7d totals; rows are at least 32px tall, with columns wide enough that their own header text and typical values never clip, and that never overlap; a category name never appears twice in one row — inside a group, rows show only the name), with each row's 5h/7d cost attributed to its own agent. Sorting by last-updated shows the grouped tree; sorting by 5h/7d cost flattens it, descending (also per-row-agent-aware). Keyboard: ↑↓/Enter/`/`. The toolbar has icon buttons (new, rescan), a name filter, a status-filter menu (all / needs input / needs review / running / done / archived, matching Claude's own app's filter — the selection persists), and a "Show archive" toggle in `⋯` (governs whether archived sessions are included when the status filter is "all"). The side panel is the **current-work** view.
- R-S13 "Session analytics" (from the row menu and the session tab's `⋯` menu) opens a fixed-header modal (90% of the screen's width) with cost/tokens/turn-count/duration cards, input/output/tool-use bars, and a turn table (prompt truncated, with cost). Clicking rows selects a range. Numbers use k/M notation.
- R-S14 "Move to category…" (from the row menu) is a single category-only field: focusing or clicking it shows a dropdown of existing categories (with their color chip and count), narrowed as you type (a prefix match ranked ahead of a substring-only match); freehand text for a new category is also accepted; confirming empty removes the category, leaving just the session's label. The current (or just-confirmed) category shows as a colored chip in the field, removable via a small "×" on it or Backspace, the same way the naming dialog's category chip works; the suggestion dropdown is never clipped by the dialog's own height, however many categories there are. Confirming applies through the same path as a rename (R-S8). The session's own label (its name, minus any category, or — if it hasn't been named yet — its auto-derived label from the first prompt) is never shown for editing here; "Rename" is for that.
- R-S15 Wherever a session's name is shown (tab title, side panel, manager, detail pane, notifications, row menu, an archived entry's cached name) — a single rule, applied everywhere: the session's own name if it has one, otherwise its auto-derived label if that's real content, otherwise "New Claude Code session"/"New Codex session"/"New OpenCode session" (by agent). The session's own id is never shown as its name anywhere, including for a deferred tab, a not-yet-resolved Codex session, or right after a restart before the first scan completes — none of these ever show a placeholder built from the id.
- R-S16 "Organize names and categories" (the `⋯` menu of the side panel and the manager) proposes `Category: Name` plus a one-line reason for up to 30 recent, non-archived sessions, by default only those lacking a name or a category, from each session's folder, first prompt, last three prompts and last reply, and the existing categories with example names, using one headless agent run with no tools and no saved session: Claude Code (Sonnet by default; the setting "Model for suggestions" can switch to Haiku) when enabled, else Codex (`codex exec`), else OpenCode (`opencode run`). The dialog names the agent, and says so when none is usable. It shows progress (spinner, elapsed seconds, a timestamped log), can be cancelled, and lists one row per session: current category chip and name, first prompt, suggested category chip (the color it will get once created, not persisted) and name with the reason, and a checkbox. Names are short noun phrases (at most 20 CJK characters or 5 words), categories are the user's existing projects or areas where one fits, and a new category is a short noun; the limits are checked after the answer (one repair request, then cut in code). Unticked rows can take a comment, and **Suggest again for unchecked** re-runs the agent for only those, with the previous suggestion and the comments, leaving the ticked rows as they are. Only the ticked rows are applied, on **Apply selected**, through the same rename path as the row menu. The row menu's **Suggest name and category…** opens the same dialog for that one session. Nothing is renamed or sent before the user presses Suggest and Apply, and the run never appears in the session list.
- R-S17 "Stretch your usage limit…" (the `⋯` menu of the side panel and the manager, and the command palette) shows where recent tokens could be saved:
  - R-S17.1 The range is chosen per agent: the 5-hour window when its usage is at or above the threshold or it is exhausted, else the 7-day window likewise, else the newest calls up to the budget in weighted tokens and at least the last 24 hours, at most 7 days back. The dialog shows how far back the range reaches, the session count and the tokens, and in "Details" the window's usage (when known).
  - R-S17.2 The statistics (`agent-sessions json efficiency`) use only Python's standard library and no network, and count every agent's tokens as the same weighted tokens.
  - R-S17.3 The dialog judges nine fixed checks: eight areas and the waste the agent finds that fits none of them (up to three issues). The agent judges every check from a digest of all tasks in the range; the statistics' hits go along as hints and never decide a check. A check is "Not applicable" only when the range lacks what it is about (for example no cache records).
  - R-S17.4 Before sending, each pane's "Details" show the destination (agent and model), the amount (estimated tokens, the number of conversations, the number of requests) and the usage limit, and offer the exact text of every request; only **Analyze** in that pane sends: one request judging all nine checks, or, for a digest over 60,000 characters, several requests by period (at most ten), each judging all nine, in turn. Stopping keeps nothing of the run.
  - R-S17.5 Only the masked digest is sent: per task its id and session, per turn the prompt (up to 600 characters), the start of the reply (200 characters) and the turn's numbers and paths. Each request is within 60,000 characters; secrets, e-mail addresses, URL paths and the home folder are masked, and no tool output or file content is sent.
  - R-S17.6 Each reply is checked: an issue's evidence keeps only task ids that were sent (an issue left without evidence is dropped), quotes must come from what was sent, and a sentence with a number that was not sent is dropped. The tokens an issue could save are computed by the plugin from the evidence tasks' numbers, per check, never taken from the model. Several requests' replies are merged in code, the same whatever order they finish in.
  - R-S17.7 After an analysis, its own cost (when known) is shown.
  - R-S17.8 Each issue has the next step, what happened, its cause, quotes when there are any, and the tokens fixing it could save.
  - R-S17.9 **Ask the agent to fix it** starts a new session in the vault with a request shown and editable first; one issue at a time; only the files the request names by absolute path (at most two) may change.
  - R-S17.10 The request, in the UI language, lists the files that may change, the kind of change (add, trim, move), that nothing is written before a diff is shown and approved, that removed lines appear in the diff, what must not be done, and how to undo. Claude Code starts in plan mode, Codex with a read-only sandbox that asks for approval, OpenCode with its `plan` agent.
  - R-S17.11 Issues about habits (switching conversations, choosing models) show advice only, no button; issues about how requests are written offer a request template to copy.
  - R-S17.12 No text, request or model finding recommends `/clear`; switching conversations is "start a new conversation in a new tab".
  - R-S17.13 Findings about requests state what happened and what it cost, never blame, and never point out a typo on its own.
  - R-S17.14 It opens from the `⋯` menu of the side panel and the manager, and the command palette.
  - R-S17.15 The statistics are cached per transcript; an unchanged transcript is not read again; reading stops at 200 sessions or 2 GB and the dialog says so.
  - R-S17.16 The threshold (50–95%), the budget (1,000,000–100,000,000 weighted tokens) and the analysis model (Sonnet or Opus) are settings; out-of-range values fall back to the defaults.
  - R-S17.17 The README's Disclosures, `principles.md` 5, `design.md` and this page say what is sent, when, where, and what is kept.
  - R-S17.18 Every failure (program missing or too old, agent unavailable, no data in range, statistics failure, model failure or time-out, a reply that cannot be read twice, usage limit with its reset time, cancel) says what happened and what to do next, and keeps the saved result.
  - R-S17.19 A conversation's digest goes only to that conversation's own agent and, for Codex and OpenCode, its own provider (a local provider's to its local model); what one pane sends names only that provider's sessions.
  - R-S17.20 The last result per pane (agent, and provider for Codex and OpenCode) is saved and shown the next time the dialog opens for an overlapping range.
  - R-S17.21 The analysing agent finds no unmasked conversation text within reach: it runs in an empty folder made fresh for each run and removed afterwards, and the statistics cache holds no conversation text.
  - R-S17.22 No statistic depends on the words a person wrote: the same conversation in another language gives the same tasks, hits and impact. Only record formats the agents write and the masking patterns are matched.
  - R-S17.23 Claude Code, Codex and OpenCode conversations are analysed alike: Codex and OpenCode split their conversations by provider and the dialog analyses the provider each used most (one tab per agent); detectors whose signal an agent does not record (E04 for OpenCode) do not run for it.
- R-S18 A dialog opened from a menu item, a command or a button is titled with that item's label, word for word — the same message in every language, so the two cannot differ. A trailing ellipsis on a menu item ("Move to category…") is not part of the title. A per-session dialog shows the session on a second line under the title. Several items that open one dialog share one label (the side panel's and the manager's `⋯` menus and the command palette all say "Stretch your usage limit…"). A confirmation raised by changing a control (a dropdown, a toggle) has no title, only its message. The welcome guide, which also opens by itself, is titled with its own name. A unit test (`plugin/test/ui/dialog-title.test.ts`) lists every such dialog and fails when a title is set from any other message.
- R-S19 Every dialog spaces its content on one scale of Obsidian's spacing variables (4, 8, 12, 16, 24 px; `design.md` §16.2), with room to breathe vertically: 24 px above and below the content and between its blocks, 24 px on each side of the divider above the closing button row and none between fields, the title 8 px above the session line, a label 8 px above its field, 16 px inside every bordered or tinted block (rows, summaries, panels, cards) and between its parts, and no padding of the plugin's own added to the modal's. The "Stretch your usage limit" dialog keeps its width when its content starts to scroll, keeps each screen's button (Analyze, Stop analysis, Analyze again) in view in a bar pinned to its bottom while the rows scroll under it, every check row has a second line (its issues' titles, "Reading", or what the check looks for) so the rows are of one height, and at about 400 px wide a row's state moves under its text instead of squeezing it.
- R-S20 The side panel's nav has an **rc** toggle (Claude Code enabled) that runs one Remote Control server in the vault: `claude remote-control --spawn=same-dir --permission-mode auto`, retried without the permission mode when Claude Code rejects it. Only a click starts it; loading the plugin, rescanning the daemon's list and the server ending never do. The toggle shows off, starting, listening and down; a click starts, restarts or stops it (asking first when sessions started through it are working); a right-click opens its terminal. The `⋯` menu offers "Copy the connection link" while the server is listening. A down server restarts with the sessions of the last four hours.
- R-S21 A Claude Code session with a running process and scheduled work (`/loop`, a cron job, a wakeup) shows a schedule badge with its tasks, each schedule in words and the next run. A scheduled turn that ends while the tab is not in front sets the status "Scheduled run finished" (`looped`), in the Needs review group, until the tab is brought to the front.

### R-D Persistence and restore

- R-D1 Closing a tab doesn't end the session (detach). It stays listed as running, and reopening it shows the continuation.
- R-D2 Restarting Obsidian restores every open tab to the same session. A restored tab connects only **when it's brought to front** — restoring never connects everything at once.
- R-D3 If the daemon is still alive, restoring reconnects and replays the recent output. If not (e.g. the machine restarted), it starts with `claude --resume <id>`, plus `--remote-control=<name>` when the session has a name and resuming connects Remote Control.
- R-D4 A session only ends via "End session" or `claude` exiting on its own.

### R-A State, notifications, and status

- R-A1 A tab's icon differs by state (connecting, working, running a shell command, asking a question — waiting for an answer, e.g. AskUserQuestion or a permission prompt — unread response, editing, just-compacted, waiting, detached, exited, error). Color and motion (spin/blink/pulse) distinguish them further, and motion respects `prefers-reduced-motion`. Side-panel and manager row marks share the same icon, color, and motion as the tab. The manager (`layout-dashboard`) and side panel (`list-tree`) icons differ from the terminal's own. These fine-grained states are further classified into groups matching Claude's own app's status buckets — needs input (asking), needs review (unread response, just-compacted), running (connecting, working, running a shell command), done (idle, editing, detached, exited) — with icons, colors, and tooltips aligned to Claude's own app for each group; an archived session always shows as its own group (an archive-box icon), regardless of its last-known state. For an open Codex tab specifically, "working"/"asking" also react live to Codex's own terminal-title text (its busy spinner, and its own "blocked on input" marker) on top of the daemon's own status — whichever says so first wins; this needs nothing configured (it degrades to the daemon-only signal alone if Codex's title isn't showing that information for any reason).
- R-A5 A session asking a question or with an unread response is visible even when its tab isn't in front: the side panel's "open tabs" heading shows a badge with the number of sessions needing input and the number needing review (each omitted at zero; clicking opens the highest-priority target), the manager's group headings show the same priority mark, and list rows highlight asking (strong background, color bar, bold) more strongly than needing review (weaker background).
- R-A2 A background session becoming unread triggers an Obsidian notification (can be turned off); clicking it switches to that tab.
- R-A3 Claude Code's `statusLine` (below the session, in Claude Code's own UI) shows the submit-key symbol (only when launched from the plugin, first in the line), model, effort, context-usage percentage, and rc. An unavailable model or effort shows "Default". OpenCode gets a status line row under its own footer showing the submit-key symbol and whether the session is busy, idle or waiting. Codex gets its own `status_line` set to model with reasoning effort and context used, only when the user hasn't set one. The plugin reads model and effort only from Claude Code's statusLine (R-M7).
- R-A4 State comes from `~/.claude/sessions/<pid>.json` (written by Claude Code) and the JSON `statusLine` receives — never inferred from on-screen text.

### R-N Navigation and references

- R-N1 A file path printed in a session's output (e.g. `path/to/note.md:12`) that resolves inside the vault becomes a clickable link, opening in Obsidian's editor (at that line, if given).
- R-N2 "Insert current note as `@`" inserts the open note's path (relative to the session's working folder) as `@path`. An editor selection appends `#L<start>-<end>`.
- R-N3 Buttons jump to the previous prompt, next prompt, and last response. When Claude Code is in full-screen mode (`tui: fullscreen`), these send Claude's own scroll keys (page up/down, jump to end) instead.
- R-N4 The same session can be shown in more than one view (split right, split down, duplicate tab). Opening from a list always moves to an existing tab rather than creating a new one.
- R-N5 While the built-in editor is open, key input goes to the editor, not the PTY.

### R-C CLI/TUI (`agent-sessions`)

- R-C1 One executable, `agent-sessions` (`agent-sessions-code`, the `$VISUAL` entry point for the built-in editor, is a thin wrapper around it).
- R-C2 No arguments opens the TUI. Selecting a session and pressing Enter attaches if it's running, or launches it with `claude --resume` if not. The TUI has no management actions (rename, archive, …).
- R-C3 Subcommands: `daemon` (the PTY owner; `--detach`, `--running-count`, `--stop`), `json` (`scan`, `live`, `detail`, `usage`, `stats` — what the plugin itself consumes), `attach`, `hook` (`Stop`/`SessionEnd`/`SessionStart` matcher `compact`/`UserPromptSubmit`), `status` (`statusLine`), `edit` (the built-in editor's receiving end), `setup` (reconciles the hooks and `statusLine` in `settings.json`; `setup --opencode` installs OpenCode's status plugin only; `setup --skills` / `--remove-skills` install and remove the agent skill; `setup --remove` reverses all of it), `new`, `sessions`, `show` and `stats` (R-C7).
- R-C4 The TUI's side panel adapts its width to the terminal's; below a threshold it can switch to a panel-only view, so no state is simply unreachable for being too narrow.
- R-C5 Scanning, last-updated computation, child-session detection, and prompt/response extraction are implemented only in Python. The plugin displays JSON it receives; it doesn't duplicate this logic.
- R-C6 CLI, TUI, and statusLine text are bilingual (Japanese/English), selected independently of the plugin's own UI language — see R-L2.
- R-C7 Agents running under Agent Sessions can start a session (`new`: folder, name, agent, Claude Code Remote Control, first message; exit `0` confirmed, `1` started but unconfirmed, `2` not started), list sessions with their status (`sessions`), read one session's usage and last messages (`show`), and read the 5-hour/7-day windows (`stats`). Two skills ship with the program and are installed with it: `agent-sessions`, which calls these, and `agent-sessions-help`, which answers questions about using the plugin from a reference file next to its `SKILL.md`. They are installed — when the plugin installs, reinstalls or updates the program, and on load when the plugin version, the launcher or the enabled agents differ from the last write — as project skills in the vault only, in the folder each enabled agent reads; nothing is written to the vault while no program is installed, a skill file we did not write is never overwritten or removed, and disabling an agent or removing the program removes ours.

### R-E Built-in editor

- R-E1 Claude Code's Ctrl+G (`$VISUAL`) opens the plugin's built-in editor.
- R-E2 The editor supports paste, `@`-based file completion, and autosave while typing. Minimal Markdown awareness is enough.
- R-E3 **The session's own output stays visible and scrollable while editing** — the editor doesn't cover the terminal.
- R-E4 "Send" confirms the edit and, for a prompt edit, submits it immediately. "Back to input" (Esc) returns to the input line with the content kept, without submitting.

### R-L Language

- R-L1 The plugin's UI supports Japanese and English. The "Language" setting: Auto (follows Obsidian's own language), Japanese, or English; default Auto. The extension's own description (`manifest.json`) is always English.
- R-L2 The CLI, TUI, and statusLine output are independently bilingual (Japanese/English; see R-C6). Selection order: a plugin-launched session matches the plugin's own resolved display language; otherwise the environment's `LANG`/`LC_ALL`/`LC_MESSAGES` decide, defaulting to English. Internal log and error text (not meant for a chosen-language audience) stays English regardless.

### R-G Welcome guide

- R-G1 A step-by-step welcome guide opens by itself on first install (from the language step), and after an update only when the new version has items to show (`WHATS_NEW`) and the user keeps "Show the welcome guide after updates" on; after the workspace is ready, in the main window only, never on an unsupported platform. An unfinished run is resumed from a one-time notice at the next start, from the "Continue the welcome guide" command or from the settings tab; "Start the welcome guide from the beginning" runs it again.
- R-G2 It asks for the language first, explains what the plugin is, offers the program install and the agents (official install commands to copy; on Windows, WinGet for Claude Code and npm's commands for Codex and OpenCode), sets the enabled agents and the submit key through the same code paths as the settings tab, and walks the user through starting a real session, switching tabs, renaming and the built-in editor, ticking each step only when the user does it.
- R-G3 Its pictures are loaded from GitHub only while the guide is open, pinned to the plugin version, images only; the setting "Load the guide's pictures from GitHub" turns it off (descriptions are shown instead). A picture that does not load within 10 seconds is replaced by a note.

### R-U Uninstall

- R-U1 `uninstall.sh <vault>` removes only what this project added: its own hook entries and `statusLine` in `~/.claude/settings.json` (backed up first), its own submit-key entries in `~/.claude/keybindings.json` (the same six-key `OWNED_KEYS` set the plugin's own cleanup uses, R-T5b — only those still holding their canonical value), the daemon (stopped cleanly first), OpenCode's status plugin if it carries our marker, the agent skills in the vault if they carry our marker, and its own symlinks (`~/bin/agent-sessions`, `~/bin/agent-sessions-code`, `<vault>/.obsidian/plugins/agent-sessions`). Every other tool's hooks, `statusLine`, and keybindings entries are left untouched. Running it again when nothing is left to remove is safe and reports as much.
- R-U2 `--force` skips the confirmation prompt that otherwise appears when sessions are still running.
- R-U3 `--purge` additionally deletes the daemon's runtime directory (`~/.agents/sessions/`) and the vault's session bookkeeping (`<vault>/.agents/sessions/`); without it, both are left in place.

### R-P Platform support

- R-P1 macOS is the primary platform. Native Windows 10/11 desktop is supported for Claude Code, Codex and OpenCode installed on Windows (the daemon holds sessions in a ConPTY and talks over loopback TCP guarded by a token; an agent installed by npm as a `.cmd` shim or as an `.exe` is found on `PATH`); it needs Windows 10 1809+ (for ConPTY) or Windows 11. The terminal UI and `agent-sessions attach` are not available on Windows (no `curses`/`termios`). Linux — including Obsidian running under WSLg on Windows — is supported: the daemon, CLI, and their platform-specific code paths (process listing, shebang, racy-mtime cache handling, socket path length, default shell, terminal key routing) run in CI on Linux. Python 3.9+, standard library only, resolved via `$PATH` (on Windows: the `py` launcher, python.org folders, then `PATH`, never the Microsoft Store alias). Obsidian desktop only (`isDesktopOnly`), minimum version 1.8.7.
- R-P1a On Windows the plugin can install Python and Claude Code with WinGet (per user, no administrator prompt) from the install dialog, only on a click; it reads `PATH` from the registry so a program installed while Obsidian runs is found; Claude Code's hooks and `statusLine` are written in the one form both Git Bash and PowerShell run; output is UTF-8; the plugin shows no console windows.
- R-P2 Claude Code always launches in interactive mode (`claude`), never the Agent SDK — this preserves interactive-only features such as `/remote-control`.
- R-P3 Files Claude Code writes are read-only from this project's point of view; nothing here modifies them.
- R-P4 The plugin, daemon, CLI, shared library code, tests, and this design documentation live together in one repository.

### R-REL Release process

- R-REL1 Bumping the plugin's version keeps `plugin/manifest.json`, the repository root's `manifest.json` (a copy read by the community-plugin review tooling and BRAT), and the root `versions.json` (minimum Obsidian version per release) all in sync in one step.
- R-REL2 Pushing a version tag builds the plugin and publishes `main.js`, `manifest.json`, and `styles.css` as a **draft** GitHub Release — nothing is published to users until a maintainer reviews and publishes that draft by hand.
- R-REL3 Every push and pull request runs the Python test suite on both Linux and macOS, and the plugin's type-check and test suite on Linux, in CI — a merge is never based on a suite that only ran on one platform.

## Acceptance checks

- Ten tabs, open for an hour: no flicker, no clipped edges, no cross-talk between tabs.
- Closing and reopening a tab replays the last screen and accepts input right away.
- Restarting Obsidian restores every tab to the same session, connecting each one only as it's brought to front.
- Clicking the same session twice in a list never opens a second tab.
- A background tab that starts asking for input changes its icon and raises a notification.
- Changing the font in settings updates every open tab.
- The `agent-sessions` TUI stays usable at a terminal width of 60 columns.
- `uninstall.sh` run twice in a row is a no-op the second time, and leaves other tools' Claude Code configuration untouched throughout.
